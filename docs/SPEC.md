## 1. What Kiln 4 is
Kiln 4 compiles the Herdr team way of working (72 h on CT101, 2026-10-26..29) into one Claude Code plugin in `/DEV/kiln` (GitHub kiln, own marketplace). Thin layer over Herdr 0.9.5 + Claude Code + Codex + agy natives. No Teams/Workflow machinery. Concepts migrate, machinery does not.
- Bridge tab (boss names it; default `bridge`): **boss** (owns the conversation with Fred and relays the agreed brief to its orchestrator; nobody else talks to Fred; **the brainstorm happens here, with the boss** [R], no brainstorm tab) → **orchestrator** (the boss's manager; owns the whole loop: scope, authority, acceptance; never designs; launches only phase managers, decides and accepts) → **gravedigah** (the orchestrator's hands: does all its hands-on work, i.e. launches and closes its workers (the fresh-builder read included), delegated reads, phase prep, seat mechanics, dialogs; owns the watcher [R]; Fred 2026-10-30, the CT101 Robin pattern: in run 4 the orchestrator did this work itself and gravedigah sat idle). Nomenclature [R, Fred 2026-10-29]: these three role words are the fixed addresses (the old words director, super and helper are retired: "super" confused the operator); every other persistent seat is a *manager* (one per phase tab) and every other seat a *worker*, except **Chunk Norris** (per-milestone, summons workers).
- One tab per phase, standing manager each (persistent-mind real session): research → plan → build+review → verify → deploy, plus **council**. Fresh workers in their own panes (never native subagents), silent, bounded packet, result + status file. **Lifetimes [R, Fred 2026-10-29]:** a tab and its manager open when the orchestrator first needs that phase and are **never closed** (an idle pane costs nothing; a closed owner cost dogfood 1 its research owner); a worker is closed only when its owner **accepts** its result, never when it merely reports, so fix rounds reuse the same worker and context; Chunk Norris is closed when the build manager accepts the milestone.
- **Owner-driven ("agent-driven development", Fred 2026-10-29)**: each phase artifact has one persistent owner seat, and *the owner answers, the file remembers*. Whoever needs something from another phase asks its owner with a `question` row (Chunk Master → architect, → build manager, → research; any manager → any owner) instead of reading its files; the owner's `answer` row points at the file section that holds the details, so readers open the file for the details of an answer, and otherwise for the structured parts (Done-when, named seams, ADRs) or when the owner is gone. Files stay the durable record across rotations; they are the owner's memory, not the source of truth while the owner is alive. **Write before act** (from Master Roshi's remark, 2026-10-29): a persistent mind is volatile (rotation, compaction, crash) while others act on what it holds, so any state another seat will act on is written to the owner's file before anyone acts on it, and the row only points there. This covers every form it takes: an answer that changes a contract (ADR in `decisions.md`, chunk `decisions.md`, `brief.md`); a ruling after an escalation; a chunk cut (`brief.md` before the implementer starts); an accepted chunk or milestone (`build.md` before the next brief); a milestone boundary (`slice/<M>/packet.md` before Chunk Master starts); pending request ids (handoff before the turn ends). Readers act on the file text, never on a row's headline or a pane's words. Explanations that add nothing to the file need no write. The test of the rule: kill any persistent seat at any moment and its replacement resumes the same agreement everyone else is acting on. The per-phase folder separation stays as it is.
- **Addresses**: the ledger `to:` field and every card address a seat by its tab/role (`boss`, `orchestrator`, `gravedigah`, `research`, `plan`, `build`, `verify`, `deploy`, `council`); the display name (Oracle, Robin, Lucius...) is the boss's choice, cosmetic, shown only in the pane label. Chunk Master (Chunk Norris) and Gravedigah keep fixed names. A spec or card that still says "super" or "director" is stale.
- **Observer** (Fred, 2026-10-29): **Master Roshi**, an Astra bot of Fred's, watches everything the team does and may, rarely, leave a comment. Read-only, never a Kiln seat, never addressed by cards or packets, no inbox. Seats treat a comment from him as advice to weigh, never as a work order; only Fred's words and the owner chain give orders.
- **Team folder and start** [step 5, 2026-10-29]: one team folder (`KILN_HOME`) per team holds the ledger, seats, cards, routing choice and one folder per phase (`bridge/`, `research/`, `plan/`, `build/`, `verify/`, `deploy/`, `council/`); a persistent seat's root is its phase folder, so the hand-off table's paths are relative to the team folder and product code changes only through worktrees of the product repo. `kiln start` (unsandboxed, run by the operator or the maestro) creates the folder, trusts it once for Claude, records the lane and `bosses` choice in the team folder (the launcher reads it over the plugin default), opens the Herdr workspace with the bridge tab and launches boss, orchestrator and gravedigah. **Codex seats run unsandboxed** (`-s danger-full-access`; Fred, 2026-10-30: the CT101 team ran GPT without a sandbox and it worked; Kiln's workspace-write sandbox blocked the Herdr socket for workers and caused the "permission profile" start failures, so research was blind in run 2). Kiln's fence hook is the write guard; the Codex sandbox is not relied on. The orchestrator launches each phase manager when its phase is first needed (council manager at the first council question) and never closes it (Lifetimes above); nobody launches a seat before it has work. Product repo [review + live probe 2026-10-29]: `kiln start` creates the team's integration branch `kiln/<team>` from the project HEAD, checked out as the worktree `build/trunk`; slices and chunks are worktrees under `build/`; the build manager merges slices into `build/trunk`; the operator's own checkout is never written, and delivery names the branch for the operator to merge. Codex seats on the build, verify and deploy tabs get the repo's git common dir as an extra root, because Codex workspace-write keeps `<root>/.git` read-only (documented, https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots, retrieved 2026-10-29) and a probe showed commit and worktree add work once the git dir itself is a root. The launcher creates a missing phase tab itself; a manager's address is its phase name; `--route <key>` picks any routing entry (council lenses, research keys) so cards name keys, never models. Cards: one shared `cards/common.md` (rules every persistent seat follows, one copy) plus one role card per seat kind (`cards/<kind>.md`, role lines only), family-neutral except one wait line, chosen by the launcher from role and tab (a missing card refuses the launch); the start hook injects common + role card + identity, pending ids and handoff. Workers get no card: every packet names the shipped `cards/worker.md` rules.
- **Smoke run 1 rulings** [2026-10-29, `/home/dev/.cache/kiln4-test/smoke1/`]: full loop ran (brief → research → plan + council → build M1 → verify → deploy, 70 rows, ~75 min) and delivered; the operator's checkout stayed untouched. `team close` closes the seat's pane too (a closed seat left running is memory: ~0.7 GB per Codex seat, 18 leaked seats OOM-killed the build manager on the 32 GB container). Every seat's handoff file is per address (`<root>/handoff-<address>.md`), since seats may share a phase root. A launch whose seat already has unread rows prompts it once with `inbox` after start (a relaunched seat otherwise idles). Wait pid markers are for Claude background waits only; a Codex seat waits in the foreground, so at its Stop no wait is live and the hook never reads a pid from a sandbox namespace. The fence allows a Bash command it cannot parse unless its raw text names a Herdr typing or wait subcommand; then it asks to split the command. Lens lists come from `kiln route <list>` (one line per entry), so a lane with one conceptual seat runs one.
- Kiln itself is spec-driven: per-phase hand-off table (artifact, producing seat, accepting seat, completion evidence) **written before any code** [R]; the operator's post-plan choice (consult me / run automatically) is a field in the brief [R]; run one = automatic.
- Bosses/managers never do real work; trivial work stays where it lands. Fred must SEE every packet (ledger + packet files); only wake plumbing may be invisible. Rules supersede, never stack; a guard that refuses normal work is a defect; count refusals in the first runs.

## 2. Messaging and waking (✓ = verified)
- Send = append one row to the ledger (`id, from, to, kind, task, headline, path, time, cites`); kinds request/done/question/answer/update; `done`/`answer` cite the row they close (`cites`), which must be addressed to the sender, and go back to its sender. Nothing typed. Boss ledger-only + Herdr notification.
- **Inbox contract** [R]: a row is *received* when the seat's inbox marks it read (at Stop or on wake), *completed* when a `done`/`answer` cites it. Pending (received, not completed) request ids are listed in the seat's handoff; on rotation the new seat inherits them by ack; the old seat stops marking. Test: row arriving during listener re-arm, busy→idle transition, rotation.
- Receiver busy → Stop hook refuses the stop while rows are unread → reads, acts. Receiver idle, Claude → `asyncRewake` listener (armed at SessionStart, re-armed at each Stop; exits 2 on a row) ✓ wakes < 1 s; the listener lives at most 280 s (Claude enforces the hook `timeout`, 300 s as proven), so it writes a pid marker (`$KILN_HOME/listeners/<addr>.pid`) and **`send` nudges a Claude receiver exactly like a Codex one when the receiver is idle and its listener marker is dead** [2026-10-29, found at step 3]: one `herdr agent prompt <seat> inbox`, no retry; seat acts only if its card says inbox rows are its work orders ✓. Receiver idle, Codex → one fixed nudge `inbox` via `herdr agent prompt` when `herdr agent get` shows idle/done; **lost-wake window** [S]: if the receiver was `working` at send time, `send` re-checks once after a short delay and nudges if the row is still unread and the seat is now idle (Claude needs none: its re-armed listener catches the row). A failed/stalled nudge is reported by `send`, never retyped. Codex manager waits in the foreground with `--timeout` (deaf for one bounded wait, accepted); parallel workers: one `herdr agent wait` per worker in sequence is fine for v0 (bounded by timeouts).
- **Workers and questions** (Fred, 2026-10-29): a worker sends exactly one kind of row, `question`, to any persistent seat (owner of the thing it needs: its launcher, the tab manager, the architect, research, the gravedigah for environment trouble), in its own words; it then writes `HH:MM question: #id` in its status file and ends its turn. It never waits on anyone, never sends `done`/`update`/`request`, never messages a worker, never nudges (its sandbox cannot reach Herdr), and never receives a row: **the `answer` to a worker's question goes to the worker's launcher**, recorded in the question row (`via`) when it is written, so the answer routes from the row and not from a seat file that may be gone [kernel test + review 2026-10-29]; the launcher, already waiting on the worker, sees the status, runs `team relay <id>` (one nudge to the question's receiver; a card rule, since no hook can know a relay is owed; when the worker asked its own launcher there is nothing to relay, and the launcher's self-addressed `answer` is written already read, so the trace stays whole and its Stop never blocks on itself), waits (bounded) for that `answer` row, and resumes the same worker with one prompt pointing at the answer; if the answer changes the scope, the launcher re-briefs instead. Questions to the launcher itself need no row: the status line is enough. Workers otherwise never message; status file ends `HH:MM done:` / `question:`; manager waits on Herdr (Claude: background `herdr agent wait --timeout`, then ends its turn; Codex: foreground), reads the file; Herdr `done` is never proof.
- Dead/blocked seats: one **detached watcher process** (started by the gravedigah, not an agent turn) [R] on Herdr events `agent_status_changed`/`pane_exited`, appends a `question` row to the orchestrator. Ships in v0 (Fred, 2026-10-29): a detached listener on Herdr `events.subscribe` (`pane.agent_status_changed`, `pane.exited`); on a Kiln seat `blocked` or pane exit it appends one `question` row to the orchestrator. No polling, no retries, no decisions.
- Seat states: acting (working) / waiting (one wait armed, turn ended) / idle. A seat is never `working` while it waits. **Wait contract** [S]: "armed" = a live wait process; its exit (result, timeout, or worker `blocked`) clears it and the manager handles each case: result → read the status file; timeout → decide (extend once, or question up); blocked → read the pane; answer only a trust prompt for a team folder; anything that widens access goes up to the operator, and nobody answers a prompt meant for the operator. Never re-arm a lifecycle wait on a worker whose status file is absent; use a bounded file wait instead. **Waiting for a persistent seat** [R, Fred 2026-10-30, ported from using-herdr after run 4's orchestrator polled the ledger in 30-min loops]: a phase or council result arrives as its cited done/answer row; the waiting seat ends its turn and the row wakes it; Herdr waits are for workers only, a manager's pane state proves nothing (a Claude manager with background waits shows done), and no loop polls the ledger or a file for a reply. **Short panes** [R, same; Fred watches the panes]: no progress messages; a seat writes a line in its pane only when it acts or decides, detail lives in files. A Claude worker ends its turn with no background command still running.
- Team tool keeps: `send` (append + Codex nudge), `inbox`, `overdue`, ledger. Removed: held queues, admission/confirming, retries, steer-while-working, wake-watch, stuck scans, **and the request-count refusal** [R] (three strikes live in the build manager's card, see §5).

## 2b. Exchange formats and budgets (Fred, 2026-10-29: "tight, lean protocol for all communications and knowledge transfer")
One shape per exchange, fixed sections, a line budget; a seat that needs more splits the work, never the format. Readers open only what the row points at.
| Exchange | Shape | Budget |
|---|---|---|
| Ledger row | `kind`, headline (one line, what and why now), `path` to the file | headline ≤ 100 chars |
| Packet (manager → worker) | `## Goal` (outcome) · `## Context` (paths, interfaces, facts it cannot find alone) · `## Constraints` (writable scope, hard lines, each once) · `## Done when` (checks it runs, result file) | ≤ 60 lines; no transcript, no history |
| Result (worker → launcher) | answers first, then `verified` vs `inferred`, changes, checks run, skipped, open points, evidence paths | ≤ 40 lines; `status.txt` one line `HH:MM done:` / `question:`. Every round is its own request row with its own packet, result and status files (`fix<n>-packet.md`, `result-fix<n>.md`, `status-fix<n>.txt`), so a late `done` or status line from an earlier round can never close the current one |
| Question / answer | one question, the decision it blocks, the options with a recommendation first; the answer is the file section (write before act) + one row | question ≤ 10 lines; answer row points, never explains at length |
| Card (SessionStart) | role, root, inbox, parent, pending ids, open items, "this is enough; read rules, ledger and panes only where an item points you" | ≤ 40 lines; whole start read ≤ ~5K tokens (§7.4). The standing part of a card changes only at rotation; everything volatile travels in rows and files, never in the card text |
| Handoff (persistent seat) | objective · latest user intent · constraints with source · decisions · verified state (paths) · remaining work and blockers · next exact action · pending request ids · artifact paths and session ids | ≤ 60 lines; detail lives in linked files |
| Report up (manager → orchestrator, orchestrator → boss) | what is done (evidence path), what is open, what needs a ruling, one line each | ≤ 15 lines; one `done` per milestone, not per chunk |
| Boss → Fred | one line plus the receipt path; questions one at a time, recommendation first | as short as the decision allows |

## 3. Hooks (three scripts, shared logic, one adapter per CLI; identity from `seat.json`)
Every hook **exits 0 at once unless the session has a Kiln `seat.json` matching its pane env** [R], so Fred's own sessions and the paused CT101 team never see them. **No leak into non-Kiln sessions** (Fred, 2026-10-29), by construction:
- Claude: hooks are never installed in `~/.claude/settings.json` or any project settings; the launcher passes them inline with `--settings` to the seat's own process only. A Claude session not started by the launcher has no Kiln hook at all.
- agy: no hooks, ever.
- Codex: the only shared surface is the user-level `~/.codex/hooks.json` (the sole unattended option, §3 probe). Each entry's command is a guard, not the hook: `sh -c '[ -n "$KILN_SEAT" ] && [ -f "$KILN_SEAT" ] && [ -n "$KILN_PLUGIN" ] || exit 0; exec "$KILN_PLUGIN/hooks/<event>.sh"'`. Without the `KILN_SEAT` variable, which only the launcher sets through Herdr `--env`, the hook is one `sh` test and exit 0: no file read, no output, no state, under 5 ms. The install merges into the existing file and never removes a non-Kiln entry; uninstall removes only entries whose command contains `KILN_SEAT`.
- Every hook script repeats the same guard as its first line (defence for a hand-copied config), then checks that `seat.json.pane` equals the pane env before doing anything else.
- Kernel test (§7.4) includes the negative: a plain `codex exec` and a plain `claude -p` outside Herdr, with the Kiln hooks installed, produce no Kiln output, no ledger row, no file; a marker written by the hook body must be absent.
| Hook | Event | Seats | Checks |
|---|---|---|---|
| stop | Stop (Claude, Codex) | all but agy | refuse only on: unread inbox row; a live worker of mine (a child seat of role worker, not closed by `team close`, whose status file has no terminal `done:`/`question:` line) with **no** wait armed; a rotation I own (matched by my session id, never by pane) not yet acked by the replacement. A pending `question` may stop; honour `stop_hook_active`: a continued Stop never refuses, and rows already unread then get one delayed wake at listener expiry, never a loop [review 2026-10-29]. [R: "armed wait unfinished" and "new seat must act" removed] [2026-10-29 review: "finished request with no done" removed from the hook, since the only evidence it could use is a worker's status line, which is never proof (§2); it stays a card rule] |
| fence | PreToolUse | Bash: **bosses and managers only** [R]; writes: **all seats** [R] | Bash: `herdr agent wait`/`pane wait-output` without `--timeout`; Claude foreground wait (a Claude seat's background wait is the Bash tool's `run_in_background: true`, which notifies the seat when the wait ends; a shell `&` is not a wait because nothing wakes the seat [review 2026-10-29]); typing (`agent prompt`/`send-text`/`send-keys`) into the boss or any pane outside the seat's own workers; the target is the first argument after the subcommand, taken literally, and help is exempt only in that position (Herdr 0.9.5 honours `-h`/`--help` only there; after the target, `send-keys` types `-h` and `send-text` types `--help`) [live probe 2026-10-29]. No poll-loop regexes in v0. Edit/Write/NotebookEdit/apply_patch: inside the seat's declared roots (root, extra roots, its own handoff file by exact path, Claude's scratchpad; the card is read-only and never writable). Matchers limit the hook to Bash and the write tools; the log keeps refusals and errors only. **Read-only workers [R, Fred 2026-10-30]:** every seat runs open (Claude in the operator's bypass mode with every tool, Codex `danger-full-access`); freedom is guided by the packet, not by locks. A reviewer or council/opinion seat is launched `--read-only` (gate runners and verify workers are not: running builds creates files, and their cards forbid product edits): it reads anything and runs anything, but the fence lets it write only its run folder (plus its handoff file and scratchpad); builders keep root + extra roots. Shell writes are not parsed, so the launcher records the worktree state of a read-only seat at launch (HEAD, `git status --porcelain`, the tracked diff and the contents of untracked non-ignored files, hashed, excluding the seat's own run folder) and `team close` refuses to close it as accepted when that state changed ("worktree changed: reject this review"); `--force` overrides. A retained reviewer re-reads fixes, so its owner runs `team check <address>` when each review result arrives (a changed worktree rejects that review) and `team mark <address>` before prompting it for a re-read, which re-records the fingerprint (the implementer's fix is then the baseline) [review 2026-10-30, Master Roshi]. Coverage claim scoped [S]: the fence catches edit-tool writes only; no OS sandbox is relied on (Codex seats are unsandboxed since 2026-10-30) and no shell parsing, ever. |
| start | SessionStart | persistent seats | inject the card (= handoff/start card): role, root, inbox, parent, pending request ids, open items, "this is enough; read rules/ledger/panes only where an item points you" |
Not shipped: PostToolUse logging, UserPromptSubmit/PostToolBatch reminders, extra PreCompact (keep handoff plugin's), model-switch hooks, subagent/team events, semantic judgments, any agy hook (agy = a one-shot headless command, never a seat [R]). Deny messages phrased per family.
- `seat.json` (launcher-written): address, name, role, family, tab, writable root(s), inbox path, parent, model/effort (from routing), card and handoff paths, pane, workspace; for a read-only worker also `read_only` and `worktree_mark`. **One source of truth** [review 2026-10-29]: a seat's workers are the seats whose `parent` is its address (`seats/*.json`), and its pending ids are computed by `team pending` (rows to me, received, not cited by a done/answer); neither is stored twice. The plugin ships `routing.toml` and the schema inside `plugins/kiln/` and resolves them from its own location, so a frozen copy runs alone. **Launcher = executable family contract** [S]: before splitting a pane it makes sure Claude seats meet no directory-trust dialog: Claude's trust carries down from a trusted parent (live probe 2026-10-29, Claude 2.1.312: a child of a trusted folder opened directly, an untrusted folder showed the dialog), so the launcher checks the root and its parents read-only and writes `projects[<root>].hasTrustDialogAccepted` in `~/.claude.json` (observed record; lock, atomic replace, one backup, re-check before start) only when none is trusted; a seat that cannot write it (a sandboxed Codex manager) refuses with the fix named. Team bootstrap (step 5) puts every seat root under one team folder, trusted once by the bridge's unsandboxed launch, so later launches never write. Codex: inside a git project Codex 0.165 shows the trust dialog and applies it to the main repository root, worktrees included, and a `-c projects` override does not suppress it; with the main root saved as trusted a worktree opens directly (live probes 2026-10-29, smoke run 1 stalled on it), so `kiln start` saves `[projects."<project main root>"] trust_level = "trusted"` once (append if absent, one backup) and the launcher never writes Codex config. Outside git, Codex shows no trust dialog and runs Kiln's user-level hooks in untrusted folders (kernel runs 1–2 and live probe 2026-10-29), and a Codex sandbox keeps `~/.codex` read-only, which made the earlier Codex pre-trust break every sandboxed launcher [kernel rerun 2026-10-29]; it emits the native flags from the pinned `families.md` (Codex manager and worker: `-s danger-full-access -c approval_policy=never` (since 2026-10-30; see `families.md`); Claude: `--model --effort --settings`; **no `--permission-mode`**: a Kiln Claude seat inherits the operator's default mode (bypassPermissions on this host, as CT101 ran), the fence is the control; `acceptEdits` was rejected because every manager action is a shell command and would prompt [review 2026-10-29]), installs the hooks for that family, and the first test launches one seat per family in a fresh folder: card received, one permitted write, one Herdr call, resume with the same identity. Herdr `--env` per pane ✓ reaches hooks on all three CLIs. **Herdr socket from a Codex sandbox** ✓ (2026-10-29): `herdr` calls fail with `PermissionDenied` under plain `workspace-write` and work with `sandbox_workspace_write.network_access=true`; so every Codex seat that launches, waits or nudges (bosses, managers, Chunk Master, gravedigah) carries that flag, and Codex workers, which do not, can still append a `question` row (file write) while their nudge fails loudly on stderr; the launcher's wait sees the `question:` status anyway. Codex hooks ✓ (probe 2026-10-29, nine runs on Codex 0.165.0, `/home/dev/.cache/kiln4-fable/codex-hooktrust-oYoi0g/hooktrust.md`): hooks in a fresh worktree run unattended only with `--dangerously-bypass-hook-trust` on the `codex` launch **and** either user-level `~/.codex/hooks.json` or a project `.codex/hooks.json` under a main repo persisted as trusted in `config.toml`; trusting an enclosing parent folder does not cover a worktree, and `-c projects...` overrides are ignored. **Scope caveat and resolution** (Master Roshi via Fred, 2026-10-29): the bypass flag skips review for *every* enabled hook source of the process, so a project `.codex/hooks.json` inside a seat's worktree would run unreviewed. Second probe (`/home/dev/.cache/kiln4-fable/codex-hooktrust2-HySZGy/hooktrust2.md`, 18 runs): Codex persists hook trust in `$CODEX_HOME/config.toml` as `[hooks.state."<hooks.json path>:<event>:<i>:<j>"] trusted_hash = "sha256:…"`, keyed by source path, event and position with a hash of the definition and **no cwd**; one review covered two fresh worktrees and a plain folder with no bypass; a changed definition is skipped again; unreviewed project hooks stay skipped even in a trusted project. **Decision**: Kiln installs its hooks once at user level (`~/.codex/hooks.json`, merged with what is there; stable guard commands resolving the script through `$KILN_PLUGIN`; they exit 0 without a Kiln seat), **Fred reviews them once in the Codex TUI (`/hooks`, trust), and the launcher never passes `--dangerously-bypass-hook-trust`**; `launch install-hooks` prints the one-time review step, and `launch` warns (never refuses) when `config.toml` holds no `hooks.state` entry for a Kiln definition. A changed Kiln hook definition means one more review, by design. No per-project trust edits, no foreign-hook guard needed: Codex's own review does that job.
- Rotation [S]: the outgoing seat is identified by its session id (both CLIs send it in every hook payload), recorded by `rotate` in `rotations/<addr>.json` with the old pane; the guard keeps accepting the old pane until the ack, for the fence and for a Stop that evaluates only the rotation condition (the outgoing seat never marks or is told to mark the replacement's rows), and the replacement is never refused for the rotation. The hook entry command execs `$KILN_PLUGIN/hooks/<event>.sh` with `KILN_PLUGIN` set per pane by the launcher (exit 0 when unset), so a frozen copy runs its own hooks whatever copy installed the entries; nested CLIs started inside a seat run with `env -u KILN_SEAT`. The handoff plugin's `rotate` keeps its ack-only first turn; **the rotate script publishes the ledger ack from its own receipt** (no duplicate obligation on the new seat), then releases continuation and inbox work; the new seat's start injects the handoff; its stop refuses only on unread rows. ## 5. Council tab and fix rounds
**Council protocol [R, Fred 2026-10-30, after scoped opinions of Astra, Sol and Fable and Master Roshi's thoughts; supersedes the collector merge and the two modes]:** the standing council manager (Opus med, like every manager) coordinates only: it frames one bounded question (decision wanted, constraints, facts, links, the asker's mandate), launches one fresh seat per preset line (never assumes a count: a lane may list one), records; it never gives an opinion, a blend or a verdict. **Asking:** the asker sends its question straight to the council seat with the decision wanted and its mandate (the orchestrator launches the council manager at the first question); the plan manager asks the plan-approval council, the build manager a three-strikes council, and any manager (research included) may ask one when it has a real direction question. **Seats:** fresh panes per question; by default two experts of different families picked by the kind of question through the routing presets (`conceptual` = Astra+Fable for direction, `operational` = Sol+Opus for "does it run"); all four only when direction and feasibility cannot be separated; Argon in parallel on a public-only packet, round 1 only, attributed, no vote, never counted in an agreement. **Operator choice:** a named composition ("only these seats") or a model swap is obeyed without reconfirming (the boss records it in its intent file and relays it to the orchestrator, which passes it to the council manager) (a swap is a launcher override; cards unchanged; provenance keeps the model that ran); the boss explains the presets once per session. **Round 1:** one packet, blind; each answer gives its recommendation, evidence marked verified/inferred, main trade-off, deciding unknown, and what would change its mind. **Exchange:** one targeted round, only on the disagreement that could change the decision: each affected seat keeps, revises or withdraws its position with evidence; then stop (more debate does not add correctness). **Record** `council/<q>/result.md`: explicit agreements (silence is not agreement), every idea attributed, conflicts side by side with their evidence, what the exchange changed, failed seats; no blend, ranking or verdict. **Ruling:** the asker rules (it owns the work and its context; no judge seat) in `council/<q>/ruling.md`, one line per decision point: AGREED (marked verified or unverified: two agreeing models can both be wrong), CALL (one-sentence why, the losing idea named) or OPEN (no evidence settles it; names the test or source that would); by default it selects one answer and adds cited named steals from the other, a rewrite only when both are rejected; a split on a fact gets a test or a source before the ruling; the ruling ends with the next action and what would reopen it. A CALL picks the asker's next step among the options offered: it adds no promise to the brief, and any later reviewer may challenge it against the brief [R, Fred 2026-10-30: run 4's brainstorm-close CALL made a supervisor a requirement and the plan then refused to cut it]. **Escalation:** OPEN items and any CALL touching the operator's goals, budget, permissions or a trade-off he declared his go up one step at a time: asker → orchestrator → boss → operator, the last step only when the boss cannot answer from what the operator already said; the asker's ruling headline reads "council <q>: N agreed, N calls, N open"; the orchestrator rules escalated items it can, from its scope for technical OPEN items and only from the brief or the operator's written words for his goals, budget, permissions or trade-offs. Fixed rules decide only where acceptance criteria exist (the three-strikes blocking test below). **Plan-approval question [R, 2026-10-29; defect defined R, Fred 2026-10-30]:** a *defect* is only a brief promise the plan would fail to deliver, with evidence; any other idea is recorded and the asker may leave it out with one line, no debate (run 3: council ideas became added mechanisms). Besides defects, the council is asked *what can be removed, and which brief promise would then fail*; never "what is a simpler equivalent" of a mechanism inside pinned contracts (dogfood 1: that wording let every cut be refused as "already ruled"). Defects return to the architect's workers; the asker accepts each proposed cut unless it quotes the brief line that would then fail; an error the brief rates cheaper never refuses a cut, nor does an earlier council ruling. Automatic conceptual council at **plan approval only** [R, Fred 2026-10-30: "forcing a council at that step, I'm not sure"; the brief-close council is dropped]; every other council (brief questions, research, milestones) is on demand by the manager that has the question. Escalation (Fred, 2026-10-29): **three strikes, you are out** (three passes, blocking only, owner routes). A pass = one implementation or fix followed by one review. Pass 1 build→review; pass 2 fix→review; pass 3 fix→review: if the third review still carries a blocking finding, the chunk is escalated (three reviews, two fix rounds, the third verdict decides). A finding is *blocking* only if it cites: a requirement/Done-when of the chunk not met; a reproduction (failing command); an external interface or seam the plan names (§5a) violated; a security or data-loss risk. Anything else is minor → `backlog.md`, chunk accepted. **Backlog exits** (Fred, 2026-10-29): (1) the build manager reads `backlog.md` when writing each next brief and folds items touching the same files into that chunk; (2) a backlog chunk clears the rest at the end of each slice; verify accepts a slice only when `backlog.md` is empty or every remaining item is marked `deferred` with a reason; (3) deferred items are listed in `delivery.md` for Fred. The reviewer never escalates, it rejects with its blocking findings. The build+review manager owns the chunk, counts passes in `build.md`, and on the third rejection has Chunk Norris write the five-line note (asked / failed / suspected cause) and routes: brief at fault → re-cuts the chunk itself; plan at fault → `question` to the council (conceptual by default, operational if "it runs wrong"), the manager owns the ruling; council says the plan changes → plan manager writes one ADR in `decisions.md`, re-plans only the affected rows, finished work stands, the chunk returns with a fresh three-pass budget. One message up per step, no new seats.

## 5a. Brief and plan contracts [R, Fred 2026-10-29, after dogfood 1]
Dogfood 1 turned a one-page brief into a 232-line plan and a 575-line first chunk. Three independent reviews (Fable, Astra, Sol) then a second council (Astra conceptual, Sol and fresh Opus operational) agreed: the growth came from Kiln's own instructions, not from a model family. Four drivers were replaced; nothing was added (no size limit, no subtraction seat: "restrict the content, don't cap the size").
- **Brief** (boss, with Fred): what must be observably true (promises), the accepted limits, and **which error is cheaper** (e.g. for the watcher: a duplicate alert costs the orchestrator one glance; a missed death costs a silent stall; the watcher burns zero model tokens while nothing happens). No "how" unless the mechanism is itself Fred's requirement; a promise that research finds expensive goes back to Fred as a question, never becomes a mechanism. An unchecked adjective ("small") is not a constraint.
- **Plan** (plan manager; what one good engineer would hand a colleague who builds it in order from the current code). *Must contain:* each capability's Done-when as **one observable sentence** (what a user or the operator sees when it works) serving a brief promise; how to prove it belongs to build and verify [R, Fred 2026-10-30, after run 3's traceability table and V1–V7 evidence programme]; the external facts build relies on (Herdr calls/events, ledger row, seat file, shared code) with their evidence; the seams two chunks or an existing tool share, with why each needs agreement now; each decision with its reason and the alternative dropped; the accepted limits and cheaper error as the brief states them; the first path exercising the outcome end to end; an estimate of the build's size (exceeding it later needs one line of why, not a veto). *Must not contain:* internal function signatures, file-internal structure, test-fixture design, timings or numbers no evidence gives, mechanisms no promise needs. **Every mechanism names the promise it serves; if no promise needs it, it is cut.** Design questions from research are the plan owner's to decide with evidence; the orchestrator is asked only for scope or authority. ADRs record consequential accepted choices once; no decisions are written to fill a section.
- **Orchestrator** accepts a plan by a **fresh-builder read** [R, Fred 2026-10-30]: someone who never saw the brief could start building from the plan alone, and every brief promise has its capability; plus evidence and the council ruling; no trace table is asked for. It picks among options it was offered or routes the question (to the plan owner, research, council, or through the boss to Fred). It **never adds a mechanism or a number** (dogfood 1: an invented pacing bound became an ADR, a pinned delay sequence and a test). A new ruling replaces the old one.
- **Build**: the milestone packet carries plan rows and named seams, not internal pins; of the §5 blocking reasons, the interface one applies only to a named external seam, never to an internal pin (unmet Done-when, failing reproduction and security or data-loss risks block as before). **Chunk rule** (Astra wording, 2026-10-29): a feature chunk is the smallest end-to-end observable outcome demonstrable from the current code, with the tests and scaffolding needed to prove it; independently demonstrable outcomes are split, acceptance conditions stay together, and fixtures or foundations are never a chunk on their own. A maintenance chunk (tidy, backlog) names its improvement and how it is verified while preserving behaviour.
- **Check in the next plan-only run**: a fresh builder can find the outcome, the seams, the first end-to-end result and whom to ask from the plan alone; zero orchestrator rulings introducing a mechanism or number; ≤3 architect passes; every plan mechanism names a promise; compare commitments (not only length) with dogfood 1's plan §§9–12.

## 5b. Build tab: Fred's implementing loop (verbatim, 2026-10-27, `bridge/fred-answers.md` §2) + the seats that run it
> A slice is cut into small chunks just in time; each chunk is built test-first, proven by the tests, reviewed by the other model family, and closed only when no checked finding is left open.
> Per chunk: 1 Brief: Chunk Norris writes one brief from the code as it is now; what must be true, never how. 2 Build: a fresh implementer writes a failing test, then the minimum code, until the test passes. 3 Gate: the full check set must pass before any model reads the diff. 4 Review: a reviewer from the other family, with Argon alongside, reports findings and gives no verdict. 5 Check findings: nothing fixed on a reviewer's word alone; a finding a test can show gets a test that fails first; one no test can show goes to the boss. 6 Fix: the same implementer fixes only accepted findings, gate reruns, the same reviewer rereads the fix; [three strikes, §5, supersedes "two fix rounds"]; then split or re-brief. 7 Close: gate passing, nothing open, commit.
> Per slice: first chunk = thin end-to-end path through every layer; later chunks deepen it. Then a simplify audit chunk, then the milestone review, boss decides. At the end: one fresh-user trial runs the real thing.

Seats, three levels (decided B, Fred 2026-10-29: "Chunk Master summons"; each level does as little as possible; as-run CT101 evidence in `/home/dev/.cache/kiln4-fable/codex-buildwiring-kF6AvX/build-wiring.md`, where the manager launched everything and the loop eroded under that load):

Flow:
1. **Milestone, just in time.** The build manager cuts milestone M from the plan and what is built (first milestone = thin end-to-end path through every layer), writes `slice/<M>/packet.md` (goal, Done-when, plan rows and named seams, pointers to arch doc and ADRs, the `build.md` state line, backlog items touching M), opens the slice branch, launches Chunk Master. A packet that forces Chunk Master to rebuild context by reading the world is a defect of the packet.
2. **Chunks, rolling.** Chunk Master cuts the next chunk only after the previous closed, from the code as it is now: one `brief.md`, what must be true never how, cut by the §5a chunk rule (smallest demonstrable end-to-end outcome; never a fixture-only chunk). Then steps 2–7 of the loop above, each step one worker, gate before any model reads the diff, Argon alongside every review, findings checked test-first (a finding no test can show goes to the owner by `question`), same implementer fixes, same reviewer rereads, three strikes counted in `decisions.md`. Close = `report.md` to the manager (`done` row); the manager commits the exact files on the slice branch and appends `build.md`.
3. **Milestone end.** After the last chunk: the tidy chunk (simplify audit, same loop), then the milestone review (reviewer + Argon on the whole slice diff against Done-when and named seams). Blocking findings (§5 definition) become fix chunks through the normal loop, then one re-review of the delta; review → fix → re-review → fix → re-review: a blocking finding on the third review is the third strike, Chunk Master writes the five-line note and the manager routes as in §5. Minor → `backlog.md`; the backlog chunk clears it before `done`; verify accepts only with an empty or all-deferred backlog.
4. **Done.** Chunk Master sends `done` with the milestone report; the manager merges the slice branch to main, writes one `done` up, cuts M+1, launches a fresh Chunk Master. The fresh-user trial runs once at the end of the plan, launched by the manager.
5. **Questions** go to owners directly (§1, §2): Chunk Master → architect/research/manager; workers → any owner, relayed by Chunk Master. Three-strikes escalation stays the manager's (§5).
- Parallel chunks only with disjoint files, one Chunk Master per parallel chunk, same milestone packet; v0 runs chunks serially.
- Files: `build/slice/<M>/{packet,report}.md`, `build/slice/<M>/review<n>/`, `build/chunks/<id>/{brief,decisions,report}.md, impl/, gate/, review/, findings/, fix<n>-packet.md, status.txt`; `build.md`; `backlog.md`.
