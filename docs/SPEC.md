## 1. What Kiln 4 is
Kiln 4 compiles the Herdr team way of working (72 h on CT101, 2026-10-26..29) into one Claude Code plugin in `/DEV/kiln` (GitHub kiln, own marketplace). Thin layer over Herdr 0.9.5 + Claude Code + Codex + agy natives. No Teams/Workflow machinery. Concepts migrate, machinery does not.
- Bridge tab (boss names it; default `bridge`): boss (owns the conversation with Fred and relays the agreed brief to its orchestrator; nobody else talks to Fred; **the brainstorm happens here, with the boss** [R], no brainstorm tab) → orchestrator (the boss's manager; owns the whole loop) → helper (plumbing, delegated reads, phase-prep chores, owns the watcher [R]).
- One tab per phase, standing manager each (persistent-mind real session): research → plan → build+review → verify → deploy, plus **council**. Fresh workers in their own panes (never native subagents), silent, bounded packet, result + status file, closed when accepted.
- **Owner-driven ("agent-driven development", Fred 2026-10-29)**: each phase artifact has one persistent owner seat, and *the owner answers, the file remembers*. Whoever needs something from another phase asks its owner with a `question` row (Chunk Master → architect, → build manager, → research; any manager → any owner) instead of reading its files; the owner's `answer` row points at the file section that holds the details, so readers open the file for the details of an answer, and otherwise for the structured parts (Done-when, pinned contracts, ADRs) or when the owner is gone. Files stay the durable record across rotations; they are the owner's memory, not the source of truth while the owner is alive. **Write before act** (from Master Roshi's remark, 2026-10-29): a persistent mind is volatile (rotation, compaction, crash) while others act on what it holds, so any state another seat will act on is written to the owner's file before anyone acts on it, and the row only points there. This covers every form it takes: an answer that changes a contract (ADR in `decisions.md`, chunk `decisions.md`, `brief.md`); a ruling after an escalation; a chunk cut (`brief.md` before the implementer starts); an accepted chunk or milestone (`build.md` before the next brief); a milestone boundary (`slice/<M>/packet.md` before Chunk Master starts); pending request ids (handoff before the turn ends). Readers act on the file text, never on a row's headline or a pane's words. Explanations that add nothing to the file need no write. The test of the rule: kill any persistent seat at any moment and its replacement resumes the same agreement everyone else is acting on. The per-phase folder separation stays as it is.
- **Addresses**: the ledger `to:` field and every card address a seat by its tab/role (`director`, `super`, `research`, `plan`, `build`, `verify`, `deploy`, `helper`); the display name (Oracle, Robin, Lucius...) is the boss's choice, cosmetic, shown only in the pane label. Chunk Master (Chunk Norris) and Gravedigger keep fixed names.
- **Observer** (Fred, 2026-10-29): **Master Roshi**, an Astra bot of Fred's, watches everything the team does and may, rarely, leave a comment. Read-only, never a Kiln seat, never addressed by cards or packets, no inbox. Seats treat a comment from him as advice to weigh, never as a work order; only Fred's words and the owner chain give orders.
- Kiln itself is spec-driven: per-phase hand-off table (artifact, producing seat, accepting seat, completion evidence) **written before any code** [R]; the operator's post-plan choice (consult me / run automatically) is a field in the brief [R]; run one = automatic.
- Bosses/managers never do real work; trivial work stays where it lands. Fred must SEE every packet (ledger + packet files); only wake plumbing may be invisible. Rules supersede, never stack; a guard that refuses normal work is a defect; count refusals in the first runs.

## 2. Messaging and waking (✓ = verified)
- Send = append one row to the ledger (`id, from, to, kind, task, headline, path, time, cites`); kinds request/done/question/answer/update; `done`/`answer` cite the row they close (`cites`), which must be addressed to the sender, and go back to its sender. Nothing typed. Boss ledger-only + Herdr notification.
- **Inbox contract** [R]: a row is *received* when the seat's inbox marks it read (at Stop or on wake), *completed* when a `done`/`answer` cites it. Pending (received, not completed) request ids are listed in the seat's handoff; on rotation the new seat inherits them by ack; the old seat stops marking. Test: row arriving during listener re-arm, busy→idle transition, rotation.
- Receiver busy → Stop hook refuses the stop while rows are unread → reads, acts. Receiver idle, Claude → `asyncRewake` listener (armed at SessionStart, re-armed at each Stop; exits 2 on a row) ✓ wakes < 1 s; the listener lives at most 280 s (Claude enforces the hook `timeout`, 300 s as proven), so it writes a pid marker (`$KILN_HOME/listeners/<addr>.pid`) and **`send` nudges a Claude receiver exactly like a Codex one when the receiver is idle and its listener marker is dead** [2026-10-29, found at step 3]: one `herdr agent prompt <seat> inbox`, no retry; seat acts only if its card says inbox rows are its work orders ✓. Receiver idle, Codex → one fixed nudge `inbox` via `herdr agent prompt` when `herdr agent get` shows idle/done; **lost-wake window** [S]: if the receiver was `working` at send time, `send` re-checks once after a short delay and nudges if the row is still unread and the seat is now idle (Claude needs none: its re-armed listener catches the row). A failed/stalled nudge is reported by `send`, never retyped. Codex manager waits in the foreground with `--timeout` (deaf for one bounded wait, accepted); parallel workers: one `herdr agent wait` per worker in sequence is fine for v0 (bounded by timeouts).
- **Workers and questions** (Fred, 2026-10-29): a worker sends exactly one kind of row, `question`, to any persistent seat (owner of the thing it needs: its launcher, the tab manager, the architect, research, the helper for environment trouble), in its own words; it then writes `HH:MM question: #id` in its status file and ends its turn. It never waits on anyone, never sends `done`/`update`/`request`, never messages a worker, and never receives a row: its launcher, already waiting on it, sees the status, waits (bounded) for the `answer` row citing the question, and resumes the same worker with one prompt pointing at the answer; if the answer changes the scope, the launcher re-briefs instead. Questions to the launcher itself need no row: the status line is enough. Workers otherwise never message; status file ends `HH:MM done:` / `question:`; manager waits on Herdr (Claude: background `herdr agent wait --timeout`, then ends its turn; Codex: foreground), reads the file; Herdr `done` is never proof.
- Dead/blocked seats: one **detached watcher process** (started by the helper, not an agent turn) [R] on Herdr events `agent_status_changed`/`pane_exited`, appends a `question` row to the orchestrator. Ships in v0 (Fred, 2026-10-29): a detached listener on Herdr `events.subscribe` (`pane.agent_status_changed`, `pane.exited`); on a Kiln seat `blocked` or pane exit it appends one `question` row to the orchestrator. No polling, no retries, no decisions.
- Seat states: acting (working) / waiting (one wait armed, turn ended) / idle. A seat is never `working` while it waits. **Wait contract** [S]: "armed" = a live wait process; its exit (result, timeout, or worker `blocked`) clears it and the manager handles each case: result → read the status file; timeout → decide (extend once, or question up); blocked → read the pane, resolve or escalate. Never re-arm a lifecycle wait when the status file is absent; use a bounded file wait instead.
- Team tool keeps: `send` (append + Codex nudge), `inbox`, `overdue`, ledger. Removed: held queues, admission/confirming, retries, steer-while-working, wake-watch, stuck scans, **and the request-count refusal** [R] (three strikes live in the build manager's card, see §5).

## 2b. Exchange formats and budgets (Fred, 2026-10-29: "tight, lean protocol for all communications and knowledge transfer")
One shape per exchange, fixed sections, a line budget; a seat that needs more splits the work, never the format. Readers open only what the row points at.
| Exchange | Shape | Budget |
|---|---|---|
| Ledger row | `kind`, headline (one line, what and why now), `path` to the file | headline ≤ 100 chars |
| Packet (manager → worker) | `## Goal` (outcome) · `## Context` (paths, interfaces, facts it cannot find alone) · `## Constraints` (writable scope, hard lines, each once) · `## Done when` (checks it runs, result file) | ≤ 60 lines; no transcript, no history |
| Result (worker → launcher) | answers first, then `verified` vs `inferred`, changes, checks run, skipped, open points, evidence paths | ≤ 40 lines; `status.txt` one line `HH:MM done:` / `question:`. Every round is its own request row with its own packet, result and status files (`fix<n>-packet.md`, `result-fix<n>.md`, `status-fix<n>.txt`), so a late `done` or status line from an earlier round can never close the current one |
| Question / answer | one question, the decision it blocks, the options with a recommendation first; the answer is the file section (write before act) + one row | question ≤ 10 lines; answer row points, never explains at length |
| Card (SessionStart) | role, root, inbox, parent, pending ids, open items, "this is enough; read rules, ledger and panes only where an item points you" | ≤ 40 lines; whole start read ≤ ~5K tokens (§7.4). The standing part of a card changes only at rotation; everything volatile travels in rows and files, never in the card text |
| Handoff (persistent seat) | objective · latest user intent · constraints with source · decisions · verified state (paths) · remaining work and blockers · next exact action · pending request ids · artifact paths and session ids | ≤ 60 lines; detail lives in linked files |
| Report up (manager → super, super → director) | what is done (evidence path), what is open, what needs a ruling, one line each | ≤ 15 lines; one `done` per milestone, not per chunk |
| Boss → Fred | one line plus the receipt path; questions one at a time, recommendation first | as short as the decision allows |

## 3. Hooks (three scripts, shared logic, one adapter per CLI; identity from `seat.json`)
Every hook **exits 0 at once unless the session has a Kiln `seat.json` matching its pane env** [R], so Fred's own sessions and the paused CT101 team never see them. **No leak into non-Kiln sessions** (Fred, 2026-10-29), by construction:
- Claude: hooks are never installed in `~/.claude/settings.json` or any project settings; the launcher passes them inline with `--settings` to the seat's own process only. A Claude session not started by the launcher has no Kiln hook at all.
- agy: no hooks, ever.
- Codex: the only shared surface is the user-level `~/.codex/hooks.json` (the sole unattended option, §3 probe). Each entry's command is a guard, not the hook: `sh -c '[ -n "$KILN_SEAT" ] && [ -f "$KILN_SEAT" ] || exit 0; exec <plugin>/hooks/<event>.sh'`. Without the `KILN_SEAT` variable, which only the launcher sets through Herdr `--env`, the hook is one `sh` test and exit 0: no file read, no output, no state, under 5 ms. The install merges into the existing file and never removes a non-Kiln entry; uninstall removes only entries whose command contains `KILN_SEAT`.
- Every hook script repeats the same guard as its first line (defence for a hand-copied config), then checks that `seat.json.pane` equals the pane env before doing anything else.
- Kernel test (§7.4) includes the negative: a plain `codex exec` and a plain `claude -p` outside Herdr, with the Kiln hooks installed, produce no Kiln output, no ledger row, no file; a marker written by the hook body must be absent.

## 5. Council tab and fix rounds
Standing manager on Sol med (collects, never judges; the asker owns the ruling [R]); fresh seats per question, none sees another's answer before the merge; the merge keeps each seat's disagreements and names any seat that failed to answer, and the asker's ruling says what it did with them; conceptual mode (Astra+Fable, Argon parallel) and operational mode (Sol+Opus). Automatic conceptual council at brainstorm close and plan approval; **milestone councils on demand in v0** [R]. Escalation (Fred, 2026-10-29): **three strikes, you are out** (three passes, blocking only, owner routes). A pass = one implementation or fix followed by one review. Pass 1 build→review; pass 2 fix→review; pass 3 fix→review: if the third review still carries a blocking finding, the chunk is escalated (three reviews, two fix rounds, the third verdict decides). A finding is *blocking* only if it cites: a requirement/Done-when of the chunk not met; a reproduction (failing command); a plan-pinned contract or interface violated; a security or data-loss risk. Anything else is minor → `backlog.md`, chunk accepted. **Backlog exits** (Fred, 2026-10-29): (1) the build manager reads `backlog.md` when writing each next brief and folds items touching the same files into that chunk; (2) a backlog chunk clears the rest at the end of each slice; verify accepts a slice only when `backlog.md` is empty or every remaining item is marked `deferred` with a reason; (3) deferred items are listed in `delivery.md` for Fred. The reviewer never escalates, it rejects with its blocking findings. The build+review manager owns the chunk, counts passes in `build.md`, and on the third rejection has Chunk Norris write the five-line note (asked / failed / suspected cause) and routes: brief at fault → re-cuts the chunk itself; plan at fault → `question` to the council (conceptual by default, operational if "it runs wrong"), the manager owns the ruling; council says the plan changes → plan manager writes one ADR in `decisions.md`, re-plans only the affected rows, finished work stands, the chunk returns with a fresh three-pass budget. One message up per step, no new seats.

## 5b. Build tab: Fred's implementing loop (verbatim, 2026-10-27, `bridge/fred-answers.md` §2) + the seats that run it
> A slice is cut into small chunks just in time; each chunk is built test-first, proven by the tests, reviewed by the other model family, and closed only when no checked finding is left open.
> Per chunk: 1 Brief: Chunk Norris writes one brief from the code as it is now; what must be true, never how. 2 Build: a fresh implementer writes a failing test, then the minimum code, until the test passes. 3 Gate: the full check set must pass before any model reads the diff. 4 Review: a reviewer from the other family, with Argon alongside, reports findings and gives no verdict. 5 Check findings: nothing fixed on a reviewer's word alone; a finding a test can show gets a test that fails first; one no test can show goes to the boss. 6 Fix: the same implementer fixes only accepted findings, gate reruns, the same reviewer rereads the fix; [three strikes, §5, supersedes "two fix rounds"]; then split or re-brief. 7 Close: gate passing, nothing open, commit.
> Per slice: first chunk = thin end-to-end path through every layer; later chunks deepen it. Then a simplify audit chunk, then the milestone review, boss decides. At the end: one fresh-user trial runs the real thing.

Seats, three levels (decided B, Fred 2026-10-29: "Chunk Master summons"; each level does as little as possible; as-run CT101 evidence in `/home/dev/.cache/kiln4-fable/codex-buildwiring-kF6AvX/build-wiring.md`, where the manager launched everything and the loop eroded under that load):

Flow:
1. **Milestone, just in time.** The build manager cuts milestone M from the plan and what is built (first milestone = thin end-to-end path through every layer), writes `slice/<M>/packet.md` (goal, Done-when, pinned plan rows/contracts, pointers to arch doc and ADRs, the `build.md` state line, backlog items touching M), opens the slice branch, launches Chunk Master. A packet that forces Chunk Master to rebuild context by reading the world is a defect of the packet.
2. **Chunks, rolling.** Chunk Master cuts the next chunk only after the previous closed, from the code as it is now: one `brief.md`, what must be true never how, sized for one fresh implementer well under an hour (a chunk that needs more is re-cut).
