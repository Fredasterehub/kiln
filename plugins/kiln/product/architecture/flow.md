# Architecture flow — how the blueprint and the Law actually run

Binds `product/charter.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Communication protocol", §"Verification doctrine", §"Operator contract") to the two phases the registry titles **the blueprint** (`architecture` — planning) and **the Law** (`plan_gate`), to the planning trio the product law states verbatim (read below), to the criteria register, and to the standing artifact law — the manifest digests the five content artifacts only, never manifest.json or gate.json themselves. Same class of artifact as `product/research/flow.md` and `product/brainstorm/flow.md` — Kiln's own operating knowledge for these two phase transitions, read by Kiln and by whichever architecture agents need to know their place in the sequence, never scraped for state: a script reads records, never prose.

The blueprint is `interactive: false`; the Law is `interactive: true` in `machine/phases-registry.json` — two separate registry phases for a reason the product law states directly: the blueprint "encodes the implementation approach, defines all remaining artifacts, guarantees restart-anytime" (no operator judgment required to *produce* a plan), the Law is "last interactivity if opted; else auto-proceed" (operator judgment only about whether to *accept* it). This flow treats that separation as load-bearing, not cosmetic — see "Sealing the gate," below, for exactly where the boundary between the two phases sits.

## Roster

`plan-author` (`agents/plan-author.md`, the single-author `plan_draft` seat — fable-5, fallback opus-5), `plan-author-sol` (`agents/plan-author-sol.md`, the Sol-authored Maximal-confrontation candidate's Sonnet-5 host, dispatching GPT-5.6-Sol via Codex CLI), `plan-coverage-checker` (`agents/plan-coverage-checker.md`, hosting BOTH of the product law's Sol-authored missions — Mission 1 lost-nothing, Mission 2 infeasibility/risk — via Codex CLI), `plan-breaker` (`agents/plan-breaker.md`, the fresh-Claude PURE-breaking seat, opus-5), and `plan-judge` (`agents/plan-judge.md`, the maximal-confrontation selection seat, same `plan_draft` routing entry as `plan-author` but always a fresh spawn, tools reduced to `Read` only). `agreement-pass` (`agents/agreement-pass.md`, already in Kiln's roster since brainstorm) is this phase's escalation seat — see "Agreement-pass triggers at architecture," below. All five architecture-phase workers are named in `product/charter.md`'s worker roster, and Kiln's own narrowly-scoped `Bash` (machine-layer CLIs only — sealing, judge-verdict relay, rejection reopen) is bounded by that same charter's Bash law — law the seat holds itself to, never a frontmatter lock.

## Protocol selection

Kiln reads `settings.json.planning` (`machine/settings-schema.json`'s `planning` knob: `standard` ▶ / `deep_scrutiny` / `maximal_confrontation`) once, at the blueprint's own entry — the same "read the dated/live config, never a memory of it" discipline `research-chief.md` holds for `research_width`. This selects which of the three sequences below runs; Kiln never re-derives the protocol from context, and every worker's brief in that protocol states which one is active rather than letting the worker infer it.

## The three protocols — the product law, verbatim, bound to the built roster

**Standard** (the product law: "strongest planner drafts alone; Sol runs the lost-nothing coverage check against brainstorm+research criteria; author repairs; ≤2 passes"):
1. `plan-author` drafts the five content artifacts once, from `vision/vision.md` + a `decisions.jsonl` projection + `research/summary.md`/`research/index.json` — never raw streams.
2. `plan-coverage-checker` runs Mission 1 (lost-nothing). Zero findings closes the protocol immediately.
3. If findings exist, `plan-author` is resumed (never respawned) to repair; `plan-coverage-checker` is resumed for pass 2 — a FULL re-run of the complete lost-nothing enumeration, highlighting the prior findings but not limited to them — a repair can fix a flagged item while silently breaking something that passed cleanly in round one, and a closing pass that only re-checks its own prior findings cannot catch that regression. Two passes is the hard cap `plan-coverage-checker.md` itself states — a third pass on the same plan escalates to `agreement-pass`, per the pipeline-wide default, never a third coverage dispatch.

**Deep scrutiny** (the product law: "still one draft, one author... Escalated attack: three adversarial passes with narrow missions — Sol on dropped items, Sol on infeasibility/risk, fresh Claude purely to break the plan — author repairs after each"). THREE distinct passes, each a separate dispatch, author repairs after EACH one — the product law's literal shape. Merging the second and third named missions into one Claude-only dispatch would remove both a pass and the required cross-family perspective:
1. `plan-author` drafts once, at this seat's own `high` effort — one author throughout; the escalation is entirely in the passes that follow, never a second draft.
2. **Pass 1 — Sol on dropped items.** `plan-coverage-checker`'s Mission 1, unchanged from Standard's own mission. `plan-author` repairs, resumed.
3. **Pass 2 — Sol on infeasibility/risk.** `plan-coverage-checker`'s Mission 2 — a SEPARATE dispatch on the same host agent (not a continuation of Mission 1's Codex session; `plan-coverage-checker.md`'s own "Mission 2" section documents this as its own dispatch shape), against the repaired draft. `plan-author` repairs again, resumed.
4. **Pass 3 — fresh Claude purely to break the plan.** `plan-breaker`, scope trimmed to hidden coupling and false sequencing only (infeasibility and resource claims moved to Mission 2, above — `plan-breaker.md`'s own "What counts as a break" section states this split explicitly). `plan-author` repairs a third time, resumed, closing the protocol.

This is three genuine agent-level passes covering the product law's three named missions, with a distinct cross-family perspective (Sol, twice, on two different questions; fresh Claude, once, on a third) at each step, and a full lost-nothing re-enumeration rather than a targeted re-check whenever Mission 1 closes a protocol.

**Maximal confrontation** (the product law: "dual anonymous drafts (Claude ∥ Sol) → each reviews the other's convergences/divergences → each may refine its own plan once → both refined plans face the adversarial passes → selection, not fusion: a fresh strongest-Claude judge picks the winning plan whole and hands the winner's author a list of specific items found only in the loser, woven in as targeted amendments... then the standard lost-nothing check closes"). Executable on the built roster: `agents/plan-author-sol.md` is the named owner of the Sol-authored candidate, so no draft is left without a seat that can dispatch it. Judge anonymity is structural rather than instruction-only — mechanical slot assignment and real content anonymization, both below:

1. **Dual drafts, family-neutral internal names.** `plan-author` and `plan-author-sol` are each spawned with a family-neutral internal draft directory — e.g. `architecture/drafts/candidate-1/` and `architecture/drafts/candidate-2/` — assigned by Kiln at spawn time, mechanically (alternating, or by spawn order; the exact rule doesn't matter because these names are NEVER exposed to `plan-judge` and carry no bearing on the eventual `plan-A`/`plan-B` labels). Neither author is told the other's directory name, model, or family.
2. **Anonymized mutual review.** Once both candidates have drafted, Kiln runs `anonymize.js`'s bundle command over each candidate's internal draft directory — the invocation form lives in `product/charter.md`'s Bash law point 1, which is where every runtime command this document names is written out (this file is plugin payload; a command stored here would reach Bash with its plugin-root prefix unresolved) — producing an anonymized copy (model names, session ids, tool-transcript markers stripped) at a path named only for the review step — never `plan-A`/`plan-B` yet. Each author is resumed with the path to the RIVAL's anonymized copy (never a Kiln-authored summary or projection — that would delegate an interpretive projection of one author's work to an unnamed third mind) and forms its own view of convergences/divergences directly from the rival's actual anonymized files.
3. **Refine once.** Each author may revise its own draft exactly once, on the same resumed session — never a second round.
4. **All three adversarial missions, per candidate.** `plan-coverage-checker`'s Mission 1 (lost-nothing), Mission 2 (infeasibility/risk), and `plan-breaker`'s pure-breaking pass each run once against each refined candidate, scoped to that candidate alone — six dispatches total. Each mission applies independently to each candidate before judgment, matching Deep scrutiny's own three-pass shape; a candidate that faced only coverage plus a consolidated Claude breaker would go to the judge under a weaker attack than the protocol claims.
5. **Mechanical slot assignment.** Only NOW, after both candidates have cleared all three missions, does Kiln compute each candidate's manifest digest (`manifest.js`'s build command over `CANONICAL_ARCHITECTURE_ARTIFACTS`) and hand both digests to `slot-assignment.js`'s assign command — both invocation forms in `product/charter.md`'s Bash law point 1, which is the seat that runs them. The parity of each digest's first hex byte decides which candidate is labeled `plan-A`, which is `plan-B`; a same-parity tie breaks on the lexicographically smaller digest. A pure function of the two candidates' own finished bytes: no wall-clock time, no random draw, fully replayable from the same two directories on a second run, and unknowable to either author or the judge ahead of time.
6. **Anonymized bundles to the judge.** Kiln runs the same anonymize command again (Bash law point 1) — this time producing the FINAL `plan-A`/`plan-B`-labeled copies the judge will see, plus anonymized copies of each candidate's Mission 1/Mission 2/breaker reports. `plan-judge` is spawned fresh (never resumed from either candidate's transcript, tools reduced to `Read` only) with exactly these ten anonymized paths as its brief's anchors — never the candidates' real internal directories, never their real reports.
7. **Selection.** `plan-judge` reads all ten inputs and selects one slot whole, never per-artifact, returning its complete verdict and named-steals list as its own response text (it has no `Write`, so it cannot persist this itself).
8. **Verdict relay.** Kiln pipes the judge's returned response verbatim into `judge-verdict.js`'s write command (`product/charter.md`'s Bash law point 2), writing the standalone `architecture/judge-verdict.md` — mechanical relay, never a summary. The judge never holds `Write` at all, and `judge-verdict.md` is never one of the five digested content artifacts, so no path exists by which the judge touches a winning content artifact. Right after this write, Kiln already knows which internal draft directory the winning slot traces back to (its own mechanical slot assignment, step 5, above) and therefore which author drafted it — `plan-author` (`"claude"`) or `plan-author-sol` (`"sol"`). Kiln then runs the telemetry `enabled`/`record` pair (`product/charter.md`'s Bash law point 10, which carries both invocation forms and the caller authority for them) and, when enabled, records the event `{kind: "planning_selection", payload: {protocol: "maximal_confrontation", winner: "claude"|"sol"}, correlation_id: null}` — read by planning-bet calibration, the declared-bet honesty the product law requires. Standard and Deep scrutiny never produce a `winner` (single-author protocols, no selection step) — this event fires only for Maximal confrontation.
9. **Named steals, woven by the winner.** Kiln resumes the winning candidate's author (`plan-author` or `plan-author-sol`, whichever drafted it — the SAME Codex session throughout, for a Sol-authored winner, per `plan-author-sol.md`'s own continuity requirement) with `judge-verdict.md`'s path. That author weaves the named steals in as targeted amendments, appends a closing entry to its own `protocol-record.md` naming the verdict and what was woven in from where, then promotes its five files from its internal draft directory to the canonical `architecture/` paths (`plan-author.md`/`plan-author-sol.md`'s own "Promotion" sections).
10. **Standard lost-nothing check closes.** `plan-coverage-checker`'s Mission 1 runs one final, full pass against the promoted, steal-amended plan — the same mission as Standard's own step 2, now serving as Maximal confrontation's closing gate per `plan-judge.md`'s own line: "then the standard lost-nothing check closes."

## Deriving the criteria register — architecture emits, phase 7 assembles

The product law, verbatim: "architecture emits vision-criterion→ID JSON; every ID gets exactly one journey; phase 7 assembles, never writes." `plan-author` is the sole author of `criteria-register.json`, minting every `id`/`journey_id` pair at blueprint time without the journey's own script existing yet — JIT, one milestone at a time. `machine/src/validators.js`'s `validateCriteriaRegister` is the machine-checkable STRUCTURAL floor: `{schema_version: 1, criteria:[{id, text, source_ref, journey_id}]}` — `schema_version` required, the `criteria` array rejected outright when empty, `id` and `journey_id` both unique across the register (a strict 1:1 mapping — "exactly one journey per criterion" enforced in code, not merely in prose). `validateMilestones(ms, criteriaRegister)` requires its own `schema_version` on the same terms, and its optional second argument closes the "lost-nothing" floor structurally: every `milestones.json` `criteria_ids` entry must resolve to a real register id, and every register id must be claimed by at least one milestone — a register entry no milestone claims is a defect `plan-author` catches in its own draft before `plan-coverage-checker` ever runs. `machine/src/plan-gate.js`'s `approveGate()` runs both validators (cross-checked) before ever sealing — see "Sealing the gate," below.

**Honest boundary**: this structural floor proves the register is well-formed and internally 1:1 over whatever entries it carries — it can NEVER prove the register is COMPLETE against `vision/vision.md`'s actual stated criteria, because "does this register cover everything the vision requires" is a semantic judgment, not a structural one. That completeness check is `plan-coverage-checker`'s Mission 1 (lost-nothing) responsibility, run against `vision/vision.md` and `research/summary.md` as ground truth. The machine checks shape; the Sol coverage seat checks truth. Neither substitutes for the other.

## Agreement-pass triggers at architecture

Three conditions each convene `agreement-pass` before any operator escalation — the pipeline-wide default the product law states ("at ANY point that would otherwise ask the operator... Fable 5 + Sol convene... no consensus within 2 passes → blocked → operator"), scoped here to the specific moments the blueprint's own machinery can detect:

1. **Protocol exhausts its passes without a viable plan** — Standard's ≤2 coverage passes, Deep scrutiny's three escalated passes, or Maximal confrontation's full sequence through promotion all complete and the resulting artifact set still fails `validateCriteriaRegister`/`validateMilestones`, or `plan-coverage-checker`'s final pass still reports findings `plan-author` cannot resolve without violating doctrine's no-plan-merging anti-goal.
2. **Any vision criterion is unmappable to a journey id** — `plan-author` cannot mint a `journey_id` for a criterion it has identified from `vision/vision.md` without inventing scope the vision pair never stated; this is a genuine gap in what the sketchbook and the field desk handed to the blueprint, not something a repair pass resolves.
3. **Milestone decomposition conflicts with a binding constraint** — `validateMilestones`'s cross-check, `plan-breaker`'s coupling/sequencing findings, `plan-coverage-checker`'s Mission 2 infeasibility findings, or a brownfield `scout/constraints.json` entry (when present) name a conflict `plan-author`'s own repair discretion cannot resolve without breaking a `preserve[]`/`protected_paths[]`/`compatibility[]` guarantee.

Each convenes `agreement-pass` with the blocker, the fix attempts already tried (the repair passes that failed to resolve it), and the project constraints bounding a remedy — exactly the brief shape `agreement-pass.md` already documents. Consensus applies automatically per its own protocol; no consensus after its two internal passes returns the S1/S2/S3 severity verdict `product/charter.md`'s own "Blocker ladder" section already governs.

## Sealing the gate

`machine/src/plan-gate.js`'s `approveGate(archDir, {decision, decision_source})` is, per its own header comment, "the ONE sanctioned producer of the manifest.json + gate.json pair" — it re-validates the five content artifacts SEMANTICALLY (`validateCriteriaRegister`, `validateMilestones` cross-checked, minimal artifact-map/protocol-record shape checks) before writing anything at all; any failure throws and leaves `archDir` byte-for-byte untouched. Only past that floor does it build a fresh `manifest.json` over the artifacts' current bytes (`machine/src/manifest.js`'s `CANONICAL_ARCHITECTURE_ARTIFACTS` — the five content artifacts, never manifest.json or gate.json themselves), write `gate.json` bound to that manifest's digest, and append a `plan-gate-decision` ledger record mirroring gate.json's own decision fields. That ledger record is the evidence trail `verifyGate()`'s single mechanism (`check-honesty.js`'s `checkArchitectureManifest`) cross-checks a claimed approval against: it validates `decision_source`/`schema_version`/`decided_at` and matches gate.json against the record, so a hand-flipped decision with no corresponding ledger entry fails. `verifyGate(archDir)` deliberately does not reimplement any of this — it delegates entirely to `check-honesty.js`'s `verifyArchitectureGateApproved`, the same mechanism `phases.js`'s `architecture-gate-approved` entry check on `implementation` already runs (one native mechanism per constraint — doctrine rule 6). `machine/src/scaffold.js`'s `scaffoldArchitecture` delegates to `approveGate` rather than re-implementing any of this.

**Protected-path law** (on top of the product law, covering agreement-pass trigger moments the law leaves open): a plan that touches a path in a brownfield scout's `protected_paths[]` IS a block, and this same semantic-sealing step is where it is caught — no new trigger, no new gate, no new module. When `<treeRoot>/scout/constraints.json` exists and its `protected_paths[]` is non-empty, `approveGate` requires `milestones.json` to carry a `touched_paths[]` footprint (`validateMilestones`'s own extended check — REQUIRED, fail-closed, only in this condition; optional otherwise, so a greenfield plan never needs to declare one) and refuses to seal — naming every conflicting path plus its `protected_paths` entry's own `anchor`/`note` — while the plan's touched-file set and scout's protected set intersect. No scout constraints, or an empty `protected_paths[]`, is a vacuous pass. Path matching is posix-normalized and directory-prefix-aware: a protected path guards both an exact match and everything nested under it. Resolution is the existing agreement pass ladder, never a new one: the seal refusal itself IS the block that convenes Kiln's blocker ladder, and the recorded outcome is either a revised plan (the milestone's `touched_paths[]` changes to route around the conflict) or a scout constraints REVISION — `scout.js`'s `writeConstraints`, the sole sanctioned writer, already accepts a bumped `revision` releasing the entry (it replaces the whole document, so no separate revision-bump machinery is needed).

`GATE_DECISIONS` (`approved`, `auto-approved`, `rejected`, `reopened`) and `DECISION_SOURCES` (`operator`, `configured-policy`) are the whole vocabulary — both owned by `check-honesty.js` (the verifier module) and imported into `plan-gate.js` (the producer), never redeclared independently, so producer and verifier can never silently disagree about what "valid" means.

**Kiln is the sole sealer** — never `plan-author` or `plan-author-sol` (both agent files state directly "you do not seal the manifest or the gate yourself... calling it is Kiln's job"). Kiln's own `Bash` grant is scoped narrowly to exactly this. Every call Kiln makes states `--decision`/`--source` explicitly — a bare `approve` with omitted flags is never a production-safe path here, since it silently defaults to `decision: "approved", decision_source: "operator"` without any real decision having been made.

Two calls, not one, because the blueprint (`interactive: false`) and the Law (`interactive: true`) are separate phases and only the second may actually decide:

- **At the blueprint's own close**, once whichever `plan-author`/`plan-author-sol` instance produced the final promoted/repaired artifact set reports done, Kiln seals with `plan-gate.js`'s approve command (`product/charter.md`'s Bash law point 1 — the invocation form and its flag-omission trap both live there), `--decision auto-approved` when `settings.plan_review` is `auto_proceed` and `--decision reopened` otherwise, `--source configured-policy` either way. This satisfies the blueprint's own `exit_emits`/`exit_checks` (both `manifest.json` and `gate.json` must exist and be non-empty — Registry conformance, below) without pre-empting an operator decision that has not happened yet. `reopened` is read here as "the gate is open, awaiting a decision" — a deliberate reuse of the existing four-value enum, never a fifth "pending" value invented, and never a claim that a prior approval is being reopened; the standing artifact law's own gloss ("a material amendment creates a new architecture revision + gate, never a silent patch") is consistent with this reading, since nothing about the artifacts changes between this call and the next.
- **At the Law's own close**: if `auto_proceed`, the gate is already sealed — Kiln runs `plan-gate.js`'s verify command (Bash law point 1) to confirm it still holds (drift since the blueprint's close would mean something rewrote an artifact out of band, itself a violation worth an `agreement-pass` trigger) and then delegates to a worker to call `phases.advance()` (Phase sequencing remains a worker's job — Kiln's own `Bash` scope does not include `phases.js advance`). If `review`, Kiln asks the operator exactly one `AskUserQuestion` (approve / reject) — the same top-level-only exception `product/onboarding/interview.md` already documents for its own settings interview, reading `architecture/plan.md` directly first (a small, bounded prose file, the same class of read Kiln's Do/route boundary already permits for `state.json`) — then, on **approved**, the Law locks: Kiln seals with the same approve command at `--decision approved --source operator` and delegates the `phases.advance()` call to a worker. The operator's word, pinned to a reproducible digest of exactly what was approved, before the anvil takes anything.

**Operator rejects at the Law.** On **rejected**, Kiln seals the rejection with the same approve command at `--decision rejected --source operator` (even a rejected decision is bound to a reproducible digest of what was rejected, per `plan-gate.js`'s own header comment), then IMMEDIATELY runs `phases.js`'s reopen command against `architecture`, carrying the operator's stated reason verbatim as its rationale (`product/charter.md`'s Bash law point 3 — both calls happen in the same turn, right after the operator answers) — the reverse transition `machine/src/phases.js`'s `reopenPhase()` provides, since forward advancement alone has no way to re-enter a phase, capture the operator's rejection rationale, or stop a rejected gate from staying authoritative during repair. `reopenPhase()` appends a `phase-reopen` ledger event carrying the rationale BEFORE rewriting `state.json`'s `phase` back to `architecture`, and un-completes BOTH `architecture` and `plan_gate` in `phase_status` — the un-completion is what stops the just-rejected gate from looking authoritative during repair (`canEnter`'s `architecture-gate-approved` check on `implementation` would otherwise still see the rejected-but-still-on-disk gate.json and have to reason about its decision value rather than the phase itself being honestly marked incomplete). Kiln then resumes the same `plan-author`/`plan-author-sol` transcript for a fresh repair round against whatever the operator's rejection named — a NEW manifest and gate get built (a new `revision`, via `approveGate`'s own `opts.revision`) once that repair closes and architecture is re-exited, never a silent patch to the rejected one.

## Registry conformance

`machine/phases-registry.json`'s `architecture` and `plan_gate` entries:

```json
{
  "id": "architecture",
  "exit_emits": ["architecture/plan.md", "architecture/criteria-register.json", "architecture/milestones.json", "architecture/artifact-map.json", "architecture/manifest.json", "architecture/gate.json", "architecture/protocol-record.md"],
  "exit_checks": [
    { "file": "architecture/plan.md", "check": "file-nonempty" },
    { "file": "architecture/criteria-register.json", "check": "file-nonempty" },
    { "file": "architecture/milestones.json", "check": "file-nonempty" },
    { "file": "architecture/artifact-map.json", "check": "file-nonempty" },
    { "file": "architecture/manifest.json", "check": "file-nonempty" },
    { "file": "architecture/gate.json", "check": "file-nonempty" },
    { "file": "architecture/protocol-record.md", "check": "file-nonempty" }
  ]
},
{
  "id": "plan_gate",
  "exit_emits": ["architecture/gate.json"],
  "exit_checks": [
    { "file": "architecture/gate.json", "check": "file-nonempty" }
  ]
}
```

**Honest limit, stated plainly**: `phases.js`'s `EXIT_CHECK_KINDS` vocabulary (`jsonl-sealed`, `jsonl-min-records`, `jsonl-has-kind`, `file-nonempty`) has no member that can express "this JSON parses to a shape `validateCriteriaRegister`/`validateMilestones` would accept" — that is a cross-field, schema-aware check, not a presence-of-content one, and adding it to `phases.js` would either duplicate `validators.js`'s logic inside the phase-registry module (the exact redundant-enforcement pattern doctrine rule 6 forbids) or require `phases.js` to import `validators.js` and grow a registry-specific per-file dispatch table `EXIT_CHECK_KINDS` was never designed to hold. `file-nonempty` on all seven architecture artifacts and on `gate.json` again at `plan_gate` is deliberately the same belt-to-suspenders relationship `research/summary.md`'s own `file-nonempty` check has to the research chief's own richer self-check: it proves the files exist and have content, never that their content is well-shaped — the semantic floor now lives exactly once, at `approveGate()`'s own sealing-time call into `validators.js` (Sealing the gate, above), not duplicated into the registry's exit checks.

**Why no new `EXIT_CHECK_KINDS` entry for "gate approved"**: `implementation`'s registry entry already carries `"entry_checks": ["architecture-gate-approved"]`, which runs `check-honesty.js`'s `verifyArchitectureGateApproved` — the full digest-chain-plus-ledger-cross-check, not a shallow field read — as an unconditional gate on entering `implementation` from `plan_gate`. Adding a second, lighter check of the same fact as a `plan_gate` *exit* check would be exactly the "one native mechanism per constraint" violation doctrine rule 6 names. No such check exists at `plan_gate`'s exit, and none belongs there.

## Failure paths

**`plan-author`/`plan-author-sol` dies mid-protocol.** Its five artifacts and `protocol-record.md`'s append-as-you-go pass history are the recoverable state — the same "artifacts survive, respawn" contract every architecture-phase worker follows. A fresh spawn reads the current artifact set plus `protocol-record.md`'s tail before continuing, resuming the protocol at whichever pass `protocol-record.md`'s last entry shows in flight, never restarting the draft from zero.

**`plan-judge` unavailable.** Its seat is the same `plan_draft` routing entry `plan-author` uses — `fable-5`, fallback `opus-5` (the routing config) — so a Fable 5 outage falls back to the declared Opus 5 substitute automatically, per the routing law, with the same fallback-substitution disclosure `plan-author.md`'s own "Identity & scope" section already states for its own seat.

**Codex/Sol dead.** `plan-coverage-checker` (both missions) and `plan-author-sol` all depend on Codex CLI. Per the degraded-mode disclosure law and the routing config's own `degraded_seats` block, a dead Codex CLI degrades `coverage_check` to a same-family Claude substitute (`sonnet-5` high) with an honest notice in the worker's envelope — never a silently skipped coverage pass. Maximal confrontation itself has NO same-family substitute: its own definition — "dual anonymous drafts, Claude ∥ Sol" — structurally requires a second family, and `plan-author-sol.md`'s own "Failure paths" section states this plainly. ## Scope, stated honestly
