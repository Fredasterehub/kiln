# The Sketchbook — how phase 2 actually runs

The sketchbook is where an idea gets talked into a shape it can be built from: one operator-interactive session, held in its own window so a long dialogue never touches Maestro's context, then crystallized into `vision/vision.md` and `vision/decisions.jsonl` by a worker that reads the transcript Maestro never does. Two artifacts leave this phase; the conversation itself stays sealed in its own stream.

Binds `agents/maestro.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Communication protocol", §"Verification doctrine") to this one phase transition. Maestro's own operating knowledge — the same class of artifact as maestro.md itself, read by Maestro and by whichever sketchbook agents need to know their place in the sequence, never scraped for state: markdown owns meaning, and no script ever reads prose to learn a fact.

Two named workers this flow spawns, both `agents/brainstorm-facilitator.md` and `agents/brainstorm-crystallizer.md` — Maestro's `tools:` frontmatter carries `Agent(kiln:brainstorm-facilitator)` and `Agent(kiln:brainstorm-crystallizer)` alongside its existing `Agent(kiln:agreement-pass)`, and the roster table below is appended to maestro.md's own roster table per that file's own stated convention ("this table... grows as later build phases land their own `agents/*.md` files — append the new name to this file's `tools:` Agent allowlist, scoped, when that happens"). A worker not on that allowlist cannot be spawned from here, by construction (maestro.md, "Own agents only"). That allowlist syntax governs *which agent types Maestro may spawn at all* — the documented restriction on which subagents may be spawned — it does not by itself decide whether a given spawn forms a subagent or a teammate; that distinction is made at spawn time, below, and it is the load-bearing fix this revision makes. A cross-family review caught the earlier draft here: it spawned the facilitator through this allowlist alone and called that a "separate team window," which the checked agent-teams contract does not support on its own.

**Which path runs is a fact, not a judgment call.** Onboarding's preflight already records it once, honestly, at `state.json.preflight.capabilities.agent_teams.present` (`product/onboarding/preflight.md` check 4 — session-introspection, not a subprocess). Maestro reads that boolean (small bounded field, within the Do/route boundary's read carve-out) and never re-probes the capability itself.

| Worker | Spawn when |
|---|---|
| `brainstorm-facilitator` | **PRIMARY** (`agent_teams.present === true`): `state.json.phase == "brainstorm"`. If a `brainstorm-facilitator` teammate is already live in this session's own roster, Maestro resumes it (`SendMessage` to its existing transcript — maestro.md's general "Resume, don't respawn" law) rather than spawning a second one — the same discipline F5's onboarding-runner double-spawn named, applied here so the operator is never handed two live facilitator windows for one session. That is the only case an actual process resume applies. When `vision/transcript.jsonl` already exists and no facilitator teammate is live, the transcript's seal state — not the phase pointer — decides what spawns next: Maestro first runs the same speculative, content-blind crystallizer probe (d, FALLBACK) already defines, and only a `blocked` ("not sealed yet") result reaches the facilitator spawn this row goes on to describe — a sealed transcript with the phase still `brainstorm` means crystallization, not conversation, was interrupted, and a facilitator spawned against it has no session left to facilitate — a live brownfield run in the dev record caught exactly that: a resumed Maestro spawned a fresh facilitator against an operator-sealed transcript because this row's spawn condition read only `state.json.phase`, which stays `brainstorm` until the *crystallizer* advances it, so a sealed-but-uncrystallized tree pattern-matched "first entry". Otherwise Maestro spawns fresh **as a teammate**, never a subagent it waits on — whether this is genuinely the first entry into the sketchbook (no facilitator transcript exists yet) or the probe came back `blocked` over a transcript whose session's teammates are gone (a fresh Maestro session never restores its prior in-process teammates — the documented remedy for a gone teammate is to spawn a new one, never a message to a process that no longer exists). Either way the fresh spawn's own `initialPrompt` recovers continuity by reading the transcript tail (`brainstorm-facilitator.md`), never by opening a second stream — and "Greet first, study later" (`brainstorm-facilitator.md`) is what keeps that recovery bounded rather than an unbounded re-ingestion (Failure paths below). **FALLBACK** (`agent_teams.present === false`): Maestro never spawns this worker at all — the operator launches it directly in a second terminal (step (b) below). |
| `brainstorm-crystallizer` | **PRIMARY**: the facilitator's session ends with a `sealed` transcript record and it `SendMessage`s Maestro the signal, idle-delivered — never before. **FALLBACK**: Maestro speculatively spawns it at each of its own bounded checkpoints (step (d) below) to test whether the transcript has sealed yet; a `blocked` result just means "not sealed yet," not an error, and costs one bounded read. **RESUME PROBE** (either capability mode): whenever Maestro resumes into `brainstorm` and `vision/transcript.jsonl` already exists with no facilitator teammate live, this same speculative spawn runs FIRST — before any facilitator spawn — so a sealed-but-uncrystallized tree resumes at crystallization instead of conversation (the same resume finding; it reuses the crystallizer's own fail-closed entry check, never new machinery). |

## The five steps

**(a) Verify phase.** Maestro's own Operating Loop step 1 ("read the bounded state you need... never a raw stream") applies literally here: it reads `state.json.phase` itself (Read tool, small bounded file — within the Do/route boundary's explicit carve-out) and confirms `"brainstorm"` via `phases.loadRegistry(machine/phases-registry.json)` + the registry's own shape (`machine/src/phases.js:181-202`, `currentPhase`). This is a read, not a judgment call — Maestro never infers phase from file presence or narrative context, only from the one resume pointer — `state.json` is THE resume pointer, and nothing else is consulted to answer the question. In the same read, Maestro checks `state.json.preflight.capabilities.agent_teams.present` to pick PRIMARY or FALLBACK below.

**(b) PRIMARY path — spawn the facilitator as a teammate.** (Only when no facilitator teammate is already live in this session's roster to resume instead — the roster-row condition above.) The sketchbook is operator-interactive and its dialogue runs long, so it gets a window of its own and never touches Maestro's context: Maestro spawns `kiln:brainstorm-facilitator` **explicitly as a teammate** — the natural-language spawn request itself carries that intent, and it names the plugin-scoped agent type, never the bare one (the documented teammate form: spawn a teammate using the `kiln:brainstorm-facilitator` agent type to run the operator's session — never a bare subagent call, since a bare `subagent_type` name does not resolve under plugin load while the scoped name does, execution-proven in the dev record). This is the mechanism the checked contract actually documents, and it is what makes the separate window true rather than aspirational: a teammate gets its own context window, fully independent, and its own mailbox — the structural property a plain `Agent(kiln:brainstorm-facilitator)` subagent call does not have, since a subagent's result returns to its caller. Once spawned, the operator converses directly *in the facilitator's own team window* — selecting its row in the agent panel (or its split pane, if enabled) and typing there — never routed through Maestro's own session at any point: plain text typed in that window goes to that teammate and nowhere else. The brief Maestro sends at spawn time is complete-but-referential (maestro.md §"Communication protocol"): outcome (crystallizable vision + decisions), scope (the operator's stated domain), anchors (`vision/transcript.jsonl` as its sole write target, `kind-registry.js append vision-transcript` — cited in full, with its resolved invocation form, at `agents/brainstorm-facilitator.md`'s own Session-log discipline — as its one sanctioned write path; this document is `product/**` payload, where a plugin-root prefix does not resolve, so the command text itself lives only on that substituting charter), acceptance (a terminal `sealed` record — reached only after the operator's own explicit confirmation, never the facilitator's convergence judgment alone; Closure ritual, `brainstorm-facilitator.md`), freshness requirement (always-on domain research — not deferred, not one-shot, and per-turn from this revision — `brainstorm-facilitator.md` §"Domain freshness"), tier/model from `.kiln/routing/active.json`, return format (idle-delivered `SendMessage` back to Maestro on seal), stop condition (**the operator's explicit confirmation that the session is done, full stop** — the facilitator's own sense that a line of thinking or the whole session has converged is a prompt to *ask* the operator, never authority to close on its own; see Ruling below and `brainstorm-facilitator.md`'s Closure ritual, which already enforces this). `SendMessage` is a deferred tool — Maestro loads it via `ToolSearch("select:SendMessage")` before its first call in a session if not already loaded (maestro.md §"Communication protocol").

**(b, FALLBACK) — the operator launches the facilitator directly.** When `agent_teams.present === false`, Maestro does not spawn `brainstorm-facilitator` at all — there is no teammate mechanism available in this session to spawn it into, and a bare subagent call would recreate exactly the blocking, single-turn, reports-back-to-caller shape this phase refuses. Instead, Maestro tells the operator plainly — in Kiln's own first person (`product/voice/kiln.md`, loaded at the prefixed path `agents/maestro.md`'s Narration section anchors), never raw prose — to open a second terminal at the project root and run:

```
claude --agent brainstorm-facilitator --effort high
```

`--effort high` is required, not decorative, for the identical reason the primary Maestro launch line names it: `brainstorm-facilitator.md`'s own `effort: high` frontmatter does not take effect on a host with any settings-scope `effortLevel` set, at either scope, so the CLI flag is the only reliable carrier of this seat's specified tier — execution-proven in the dev record. If Maestro's own session was itself launched with `--plugin-dir <path>` (a dev install, not a marketplace install), this second terminal needs the identical flag too: `claude --plugin-dir <path> --agent brainstorm-facilitator --effort high` — a marketplace install needs neither `--plugin-dir` nor its caveat, but always needs `--effort high`. This is the same launch-shape Maestro itself uses and for the same reason — a persona adopted via `--agent` survives `/compact`; one adopted mid-conversation via a slash command does not, execution-proven in the dev record — the facilitator needs to hold its identity and its stance choice across a long session exactly as durably as Maestro holds its own. Coordination between the two independent CLI processes is **file-mediated only**, through `.kiln/vision/transcript.jsonl` — the same append-only, single-writer-locked stream the primary path uses (`jsonl.js`'s lock already serializes concurrent writers regardless of how many processes exist; nothing here relies on there being exactly one). There is no live message channel between two separately-launched `claude` processes — `SendMessage` targets teammates and subagents *within one session*, and these are two unrelated sessions — so the facilitator cannot signal Maestro directly in this mode; step (d) below covers how Maestro learns the session sealed instead.

**(c) Go idle.** Immediately after spawning (primary) or naming the terminal command (fallback), Maestro's turn ends — it does not poll continuously, does not read the transcript, does not narrate progress mid-session — nothing to narrate from: no recorded event, no line (`product/voice/kiln.md`), and `vision/transcript.jsonl` is the facilitator's alone, never projected into Maestro and never a record Maestro is allowed to read. The operator's entire session happens directly with the facilitator — inside its own team window (primary) or its own terminal (fallback) — no dialogue reaches Maestro either way, by design, not by omission. In the primary path this is the literal measured mechanism — idle-only delivery, execution-proven in the dev record: a message to a busy agent (Maestro mid-turn) sits until the turn ends, so the *only* way Maestro can safely disengage from a long interactive session without either blocking on it or missing its completion is to end its own turn and let the completion signal (below) wake it — exactly what step (c) does. In the fallback path there is no live agent to wait on at all — Maestro's turn simply ends after naming the command, and the next thing it does is bounded, operator-triggered polling (step (d)), never a background loop.

**(d, PRIMARY) — wake on the sealed signal, spawn the crystallizer.** The facilitator appends a terminal `sealed`-kind record to `vision/transcript.jsonl` only after the operator has explicitly confirmed the session is done (Closure ritual, `brainstorm-facilitator.md` — the facilitator may *propose* that a line of thinking looks exhausted, per the standing anti-mediocrity framing this flow holds, but proposing is not sealing), then `SendMessage`s Maestro one line: "brainstorm sealed, transcript ready." Because that message targets an idle Maestro, idle delivery lands in seconds — measured, execution-proven in the dev record — so Maestro wakes promptly, never on the next unrelated poll. Maestro reads nothing from the transcript itself (still facilitator-only); the message *is* the bounded signal. Maestro then spawns `brainstorm-crystallizer` — a fresh, context-blind worker whose **sole input is `vision/transcript.jsonl`**, read in full by the crystallizer itself, never by Maestro. Subagent-mediated crystallization is the mechanism that makes "the dialogue never touches Maestro's context" implementable rather than aspirational.

**(d, FALLBACK) — bounded, documented polling instead of a message.** With no live channel to the facilitator's terminal, Maestro cannot be woken by it. Instead, at each of Maestro's own turns where the operator raises the brainstorm again (the operator says something like "I've finished the brainstorm" or "check on the brainstorm," or a fresh Maestro session resumes and `resumePoint()` reports the phase is still `brainstorm`) — **never on a timer, never more than once per such turn** — Maestro speculatively spawns `brainstorm-crystallizer` exactly as it would in the primary path. The crystallizer's own existing fail-closed entry check (`brainstorm-crystallizer.md` §"Fail closed") already does the one thing this needs: it reads `vision/transcript.jsonl`, inspects the last record, and either proceeds (sealed) or refuses cleanly with `state: blocked` and an envelope naming what it found instead — no transcript content in that envelope either way. A `blocked` result here is normal traffic ("not yet"), not a failure and not yet a blocker rung (maestro.md §"Blocker ladder" — that ladder is for a fix attempt failing twice, not for a session still being had); Maestro reports "still in progress" to the operator and waits for the next natural checkpoint. This reuses the crystallizer's own machinery rather than inventing a second worker or a raw Maestro read of the transcript, and it is exactly as content-blind as the primary path's wake — the only difference is who initiates the check.

**(e) Verify exit artifacts, advance, and report.** The crystallizer's closing step — not Maestro's own tool call, per maestro.md's Do/route boundary ("You do not run commands, edit files, or write files... anything that touches disk state, runs a check... is a worker's job") — runs three checks before calling `phases.advance()`:
1. `vision/vision.md` exists and is non-stub (the crystallizer's own write, self-verified).
2. `vision/decisions.jsonl` carries **at least one non-genesis record** — checked via `projection.projectFile` (bounded view, never a raw read) rather than trusting its own write silently landed.
3. `vision/transcript.jsonl`'s latest record has `kind: "sealed"` — proof the facilitator closed the session properly rather than the crystallizer being spawned prematurely against a session Maestro merely *thinks* ended (belt-and-suspenders against a stale or spoofed wake message — see Failure paths).

Only if all three pass does the crystallizer call `phases.advance(treeRoot, registry, statePath, ledgerPath)` (`machine/src/phases.js:251-328`), which independently re-checks the registry's own `exit_emits` (file existence, `vision/vision.md` and `vision/decisions.jsonl`) **and, from this revision, the registry's `entry_checks` for the phase being entered** — see "Registry conformance," below, for the machine-enforced semantic checks now backing these same three facts at the `phases.advance()` boundary itself, not only in the crystallizer's own script-side logic. It writes the ledger-first `phase-transition` event, then atomically rewrites `state.json`.

The crystallizer reports back to Maestro via the standard worker envelope (STATE/RESULT/EVIDENCE/RISKS/ARTIFACT/QUESTION); Maestro's Verification doctrine applies exactly as written — it "never report[s] a gate green from a worker's prose alone," it cites the `phase-transition` ledger event `phases.advance()` just wrote (`ledger.jsonl`, `kind: "phase-transition", correlation_id: "research"`) as the checkable evidence, then narrates the boundary — the sketchbook closing, the field desk opening — to the operator in Kiln's own first person (`product/voice/kiln.md`, loaded at the prefixed path `agents/maestro.md`'s Narration section anchors).

## Ruling: closure authority is the operator's, always

The facilitator may notice a line of thinking is exhausted and say so, may notice the operator sounds ready to wrap up and ask, and may reflect the session back for confirmation (Closure ritual, `brainstorm-facilitator.md`) — none of that is sealing. The seal (`kind: "sealed"` appended to `vision/transcript.jsonl`) happens only after the operator has explicitly confirmed the session is done, every time, no exception for "obvious" convergence. This binds identically in both paths: primary (the facilitator, in its own team window, gets that confirmation directly from the operator before sealing) and fallback (same facilitator identity, same ritual, running in the operator's second terminal instead of a team window — the ritual does not change with the launch shape). A prior draft of this document described the stop condition as "the operator ends the session, or the facilitator seals it on convergence" — that "or" was the defect: it let the facilitator's own convergence judgment stand in for operator confirmation, which is exactly the ambiguity the crystallizer's trust in a sealed transcript cannot tolerate (if sealing can happen without the operator's say-so, a sealed record no longer proves the operator considered the session complete). This document and `brainstorm-facilitator.md`'s Closure ritual now agree: operator confirmation is the only sealing authority, in both paths, without exception.

## Registry conformance

`machine/phases-registry.json`'s `brainstorm` entry's `exit_emits: ["vision/vision.md", "vision/decisions.jsonl"]` mirrors the restart-anytime boundary exactly: past this phase a resume needs those two files and nothing more — the transcript stays sealed in its own stream. That boundary deliberately excludes `vision/transcript.jsonl` from the minimal disk set a resume needs, and the registry's `exit_emits` (and `research`'s mirroring `entry_requires`) follow the exclusion precisely. `vision/transcript.jsonl` is absent from both lists as a *path* by design: it is never projected into Maestro, and its role in the exit gate is content-level (does the latest record say `sealed`, does `decisions.jsonl` carry real content), a property bare path-existence (`missingRelpaths`, `machine/src/phases.js`) cannot express on its own.

That content-level property is no longer crystallizer-only prose, from this revision: `machine/phases-registry.json`'s `brainstorm` phase now declares `exit_checks` — the same kind of registry-declared semantic vocabulary `implementation`'s `entry_checks: ["architecture-gate-approved"]` already established as a pattern (`machine/src/phases.js`'s `SEMANTIC_CHECKS`) — naming `jsonl-sealed` against `vision/transcript.jsonl`, `jsonl-min-records:1` against `vision/decisions.jsonl`, and `file-nonempty` against `vision/vision.md`. `phases.advance()` runs these after its existing path-existence checks and refuses, by name, if any fails (`machine/src/phases.js` §"exit_checks", below). This does not replace the crystallizer's own script-side checks in step (e) — a worker that already knows what it just wrote should still verify that directly, cheaply, before ever calling `advance()` — it means the machine layer itself now independently enforces the same three facts at the one call every phase transition must pass through, so a caller who skipped or mis-ran the crystallizer's own checks (a bug, a different future worker, a hand-rolled script) cannot advance past `brainstorm` on file-existence alone the way the prior design allowed.

## Failure paths

### Primary (agent teams)

**Facilitator dies mid-session.** `vision/transcript.jsonl` is the append-only record of everything that happened up to the crash — jsonl.js's single-writer, append-only law means the last successfully-appended record survives on disk regardless of what killed the agent process. Maestro's `resumePoint()` (or an operator-triggered "resume brainstorm") re-spawns `kiln:brainstorm-facilitator` fresh, as a teammate again — the documented remedy for a gone in-process teammate, never a defect to route around: there is no session resumption for in-process teammates, spawning a new one is the stated fix, and there is no live process left to `SendMessage`. Per maestro.md's "Resume, don't respawn" the *first* thing its brief does is read the existing transcript tail (a bounded `projection.projectFile` view, `lastN` records) to recover context before continuing — never starting a second, competing transcript — and "Greet first, study later" (`brainstorm-facilitator.md`) is what keeps that recovery bounded: two live spawns without it each ground 15–38 minutes before their first post — execution-proven in the dev record. If a same-named facilitator is still technically alive but merely unresponsive, Maestro's `SendMessage` to it queues per idle-only delivery and is processed at its next wake (a message to a busy or stuck agent sits until that worker's turn ends — 91 seconds in the measured case) — Maestro does not spawn a second facilitator while the first might still be alive, since two writers to one JSONL stream is exactly what jsonl.js's single-writer lock exists to prevent.

**Crystallizer refuses (unsealed transcript).** If the crystallizer is spawned against a transcript whose latest record is not `kind: "sealed"` — a stale wake message, a facilitator that died after sending "almost done" but before actually sealing, or an operator-side race — step (e)'s third check fails and the crystallizer refuses to write `vision.md`/`decisions.jsonl` or call `phases.advance()` at all (fails closed, no partial crystallization). It reports the refusal to Maestro via its envelope (RESULT: refused; EVIDENCE: transcript tail showing the unsealed last record). Maestro's response is *not* to retry the crystallizer or to treat this as ambiguous operator intent (doctrine "Never guess — ask" names the operator as the recipient only for intent-ambiguity, not for this kind of implementation-state mismatch): it `SendMessage`s the still-addressable `brainstorm-facilitator` to close the session properly (append the missing `sealed` record, or resume the operator's session to actual completion if it was truly still open), then re-spawns the crystallizer once sealed. This is the blocker ladder's first rung (maestro.md §"Blocker ladder") only if a second distinct attempt also fails — a single unsealed-transcript refusal is normal traffic, not yet a blocker.

### Fallback (second terminal)

**Facilitator's terminal session ends or crashes.** The operator simply relaunches `claude --agent brainstorm-facilitator --effort high` (plus `--plugin-dir <path>` too, under a `--plugin-dir` dev install — the same caveat step (b, FALLBACK) states in full) in the same terminal. Resume-don't-respawn is enforced by the facilitator's own first action on launch (its frontmatter's `initialPrompt`, `brainstorm-facilitator.md`): check for an existing, unsealed `vision/transcript.jsonl` and continue it — read the tail, greet the operator with where the session left off, never open a second stream. jsonl.js's single-writer lock (`withLock`, `machine/src/jsonl.js`) additionally prevents two facilitator *processes* from corrupting the stream even if the operator briefly ran two by mistake — the second writer blocks, then retries, rather than interleaving.

**Maestro's speculative crystallizer spawn refuses (unsealed transcript).** This is the expected, common case in fallback mode — it means the operator hasn't finished yet. Maestro reports "still in progress" plainly and takes no other action; this is never a blocker-ladder rung, since nothing failed — a still-open brainstorm session is not a defect.
