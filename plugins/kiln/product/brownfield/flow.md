# Brownfield — the detour inside the door

A project that already has code gets one extra leg at the door: a scout-and-inventory pass, then every artifact created, then re-entry wherever state says. Scout inventories what is there and makes no policy decision of its own — a target already touching a regulated domain gets the same provider-limit and scope disclaimers any other build gets, stated plainly, never quietly refused.

Binds `machine/src/detect.js`'s actual, already-built `detect(projectRoot)` API (the real five-way classification, never a paraphrase), `machine/src/validators.js`'s `TRUST_FLAGS`/`validateScoutConstraints`, and `machine/src/scout.js`/`agents/scout-agent.md` as actually built, never assumed from a file's name. Same class of artifact as `product/verification/flow.md` and `product/delivery/flow.md` — Maestro's own operating knowledge for one onboarding sub-flow, read by Maestro and by `scout-agent` to know its own place in the sequence.

This is not a ninth pipeline phase. It is a **detour inside the door** (phase 1, `interactive: true`) that fires on one of `detect()`'s five possible outcomes — `greenfield`, `resume`, and `broken-install` never touch anything in this document. `legacy` is the one outcome that reaches this document indirectly rather than not at all: an earlier Kiln tree is set aside and harvested by the door's own intake leg first (`product/legacy/flow.md`), and the run that continues afterwards takes this document's own scout leg whenever the project has code — legacy is brownfield-plus-an-intake-leg when there is code, greenfield-plus-an-intake-leg when there is not. The scout pass below is unchanged by that; what changes is that `scout-agent`'s brief names intake's own report as an additional input.

## Detection → scaffold → scout, in that exact order

**1. Detect, once.** `detect.js`'s own `detect <projectRoot>` CLI subcommand, run by Maestro — the invocation form lives in `agents/maestro.md`'s Bash law point 7, which is where every runtime command this document names is written out (this file is plugin payload, so a command stored here would reach Bash with its plugin-root prefix unresolved). Every caller reaches the same classification through that one form — root `SKILL.md`'s own pre-Maestro preflight step included — and `detect()` itself is unchanged underneath it. A deterministic filesystem read, no model judgment (`detect.js`'s own header comment: "this module makes no decisions beyond the five-way classification and its honest refusals"). `mode: "brownfield"` — no `.kiln/` tree, but `evidence.has_code` is true (a git repo with at least one commit, or any file outside dot-directories) — is the outcome this document's own sequence below fires on directly; a `legacy` classification reaches the same sequence only after the intake leg has finished, and only when the project has code.

**2. Scaffold the tree BEFORE scouting it — order matters, not a stylistic choice.** Onboarding's own scripted step runs `scaffold.js` against `<targetRoot>` with the plugin's current dated routing config — `onboarding-runner` is the seat that owns that call and its own charter (`agents/onboarding-runner.md`, Method step 1) carries the invocation form, including how the dated config path is resolved rather than hand-typed. It is the **identical** call a greenfield run already makes — brownfield and greenfield trees are shape-identical, and `scaffoldTree`'s own header comment says why `scout/` is "deliberately excluded" from the greenfield skeleton: it is "brownfield-only". This has to run **before** `scout-agent` is spawned, not after, for a concrete structural reason: `scaffoldTree(targetRoot, opts)` refuses (throws) if `<targetRoot>/.kiln` already exists unless `opts.force` is set, and `opts.force` does not merge — it `rmSync`s the **entire** `.kiln` directory and rebuilds it from nothing. If `scout-agent` ran first and its own `writeReuseMap`/`writeConstraints` calls had already materialized `.kiln/scout/` (their own `atomicJson.writeAtomic` auto-creates parent directories — `scout-agent.md`'s own text notes the tree "may not fully exist yet at this point," a hedge about tolerance, not a mandate for this ordering), a subsequent `scaffoldTree` call would either refuse outright (no `force`) or silently destroy the scout pass's own work (`force: true`) — the exact `.kiln` genesis idempotency risk `scaffoldTree`'s own refuse-unless-force design exists to prevent. Scaffolding first, once, means `scout-agent`'s own three writes land under an already-complete, already-safe tree with nothing left to accidentally overwrite.

**3. Spawn `scout-agent`, once.** `agents/maestro.md`'s roster table: spawned "once, at onboarding, only when `detect()` reported `mode: 'brownfield'`," brief naming the target project root directly. `scout-agent.md`'s own precondition, quoted directly: "Maestro already ran `machine/src/detect.js`'s `detect()`... you do not re-run `detect()` yourself and you do not second-guess the classification" (doctrine rule 6 — a second detection pass over the identical question is the redundant-enforcement pattern the product forbids by name). Its method, as actually built (`agents/scout-agent.md` is the complete statement of it and the place its invocation forms live; summarized here only to the depth Maestro itself needs to know, and never read from this document at a bare `agents/` path — that would resolve inside the operator's project):
   - **`inventoryTarget(projectRoot, opts)`** (`machine/src/scout.js`) — the sole writer of `scout/inventory.json`: a deterministic recursive walk (never following symlinks, skipping `node_modules`/every dot-directory including the target's own prior `.kiln/`), atomic-written, files sorted by path regardless of on-disk creation order, `by_lang`/`entry_points`/`test_dirs`/`has_git`(+`commit_count`) tallied.
   - A **bounded, targeted read** — entry points, configs, READMEs, a sample of each test directory — never the whole tree (`scout-agent.md`'s own "Read selectively" section), every claim carrying a `file:line` anchor.
   - **`writeReuseMap(treeRoot, entries)`** — the sole writer of `scout/reuse-map.json`: `{path, trust, note}` per inventoried item worth flagging, `trust` one of `validators.js`'s two `TRUST_FLAGS` — **existing vision/README prose → `inherited-unverified`** (brainstorm INPUTS); **existing tests → `inherited-advisory`** (verification seeds — cannot vote on "done" until re-reviewed, the same standing a JIT journey holds before its own review); **existing architecture/design docs → research cache entries, never directly into `architecture/`**, flagged per the same two-flag meaning. Every entry validated (non-empty `path`, `trust` in the two-flag set, non-empty `note`) before it ever reaches disk; the whole write refuses on any malformed entry, nothing partial lands.
   - **`writeConstraints(treeRoot, constraints)`** — the sole writer of `scout/constraints.json`: five typed fields — `preserve[]`, `protected_paths[]`, `compatibility[]`, `migrations[]`, `known_failures[]` — every array present (empty where nothing was found, never omitted), every entry carrying one of the same two `TRUST_FLAGS` plus (by `scout-agent.md`'s own house convention layered on top of that structural floor) an `anchor` and a `note`. Routed through `validators.validateScoutConstraints` — the sole gate, never re-implemented in `writeConstraints` itself — which refuses the whole document (writes nothing) on a missing field, a non-array field, or any entry carrying an unrecognized `trust_flag`.

**The binding law underneath all three**: inherited material never enters a decision artifact directly — it enters as a flagged input, and the pipeline re-derives. `scout-agent` never writes to `vision/`, `research/`, or `architecture/` itself (its own `tools:` frontmatter has no reach there) — a later phase that trusts a flagged pointer without re-deriving its own conclusion from it is that phase's own violation to answer for, not scout's.

## Then create all artifacts — the normal pipeline, informed

Once `scout-agent` reports `state: done` (all three `scout/` files on disk), the door continues exactly as any greenfield run does — the settings interview, then the standard eight-phase sequence — with two concrete, named differences this document is the canonical source for:

- **The sketchbook may be shortened by operator choice.** `scout/reuse-map.json`'s `inherited-unverified`-flagged prose entries (existing README or founding material) give `brainstorm-facilitator` a genuine head start, and the facilitator's freshness-research obligation is already conditional on what the operator brings. An operator whose project already carries real founding prose is offered the choice to shorten that dialogue accordingly — at the same "plan review or auto-proceed" style decision point the door already holds, never a new settings knob invented here.
- **Constraints feed the blueprint as binding inputs, never advisory color.** `scout/constraints.json`'s five typed fields are read directly by the architecture phase when it drafts `milestones.json`/`criteria-register.json` (`product/architecture/flow.md`) — a `protected_paths[]` entry constrains which files a milestone may propose touching, a `preserve[]` entry constrains what a criterion may propose changing, a `known_failures[]` entry is disclosed context a plan author must account for rather than silently rediscover later. "Binding" here means what it means everywhere else in this product: architecture may not silently contradict a flagged constraint without that contradiction becoming its own named decision event (`vision/decisions.jsonl`), the identical discipline any other cross-phase input already gets — never a new enforcement mechanism invented for this one input class (doctrine rule 6).
- **`protected_paths[]` specifically is machine-enforced, never merely disclosed**: a plan touching a path a `protected_paths[]` entry guards is a block, caught deterministically where the Law locks, by a set-intersection between `milestones.json`'s `touched_paths[]` footprint (required, fail-closed, exactly when a non-empty `protected_paths[]` exists) and scout's guarded set — never by model judgment, never a second gate. See `product/architecture/flow.md`'s "Sealing the gate" for the full mechanism; resolution runs through the same agreement pass ladder every other block does.

`scout/` is deliberately **not** a registry-declared phase boundary — no phase's `entry_requires`/`exit_checks` in `machine/phases-registry.json` names anything under it. Brownfield changes the *content* later phases receive, never the *structural* shape of the pipeline; a registry gate here would be machinery built ahead of an actual need, which this product does not build. No phase is currently blocked without it — the sketchbook and the blueprint simply read richer inputs when it exists, and correctly read nothing extra when it does not.

## Re-enter where state says

Nothing brownfield-specific is needed here beyond the restart-anytime discipline that already holds at every phase boundary: `scout/` is part of the tree the moment it's written, travels with it, and a resumed session picks it back up exactly the way it picks up `vision/` or `architecture/` — `resumePoint()` and every `canEnter()` check already treat it as ordinary tree content, because it is. The one operational rule worth stating plainly: **`scout-agent` is spawned once per onboarding run, fresh, with no mid-scout state to resume** (`scout-agent.md`'s own "Roster" line) — a session that dies mid-scout re-spawns it from scratch rather than trying to resume a partial inventory; `inventoryTarget`'s own atomic-write discipline means a half-finished run never leaves a corrupt `scout/inventory.json` behind for the fresh spawn to trip over.

## Failure paths

**`broken-install`, not brownfield.** A `.kiln/` tree that exists but fails `detect()`'s own validity check (missing `state.json`, a directory in its place, malformed JSON, or a genesis stub missing `phase`/`next_action`) is a **different** outcome this document does not own — `detect.js`'s own header comment: "an explicit, fail-closed outcome rather than being silently reported as greenfield or resume." Routed straight to the operator (`maestro.md`'s "Operator contract": ambiguity about what the operator wants is asked directly, one precise question, ending the turn there) — never scaffolded over, never guessed into either a fresh brownfield scout or a resume.

**Oversized repos — truncation honesty, never a silent drop.** `inventoryTarget`'s own `opts.maxEntries` (default 5000) caps the file list at a **sorted prefix** — deterministic, never an arbitrary subset — and sets `truncated: true` rather than silently omitting the excess. `scout-agent.md`'s own text is explicit about the consequence: a truncated inventory means the agent's own subsequent targeted-read pass (entry points, configs, READMEs, test-dir samples) is working from an incomplete file list, and it "says so plainly in your envelope's `risks`" — never presenting `reuse-map.json`/`constraints.json` as exhaustive when the inventory beneath them wasn't. A monorepo genuinely large enough to need a higher ceiling is an onboarding-time brief decision (`opts.maxEntries` passed explicitly in `scout-agent`'s own dispatch), stated to the operator as a cost/time tradeoff before it happens — never silently raised.

**A `scout-agent` envelope reports `blocked`.** Per its own contract: the precondition failure above (a named path that doesn't exist, or looks empty enough that brownfield seems wrong — `scout-agent.md`'s own text: "that is a `blocked` envelope naming what you actually found, not a silent re-classification"), an `inventoryTarget` throw, or a target genuinely too sparse for a meaningful reuse-map/constraints pass (no README, no configs, no tests). This is not an onboarding failure to route to the agreement pass — that ladder is reserved for a genuine implementation-judgment deadlock after two distinct attempts; a `blocked` scout envelope over what a target repo actually contains is a fact for the operator to see and decide on directly (Maestro's own "Operator contract"), the same class of decision a `broken-install` result already routes there.

## Where the rest of the door lives

`product/onboarding/flow.md` carries the FULL scripted door sequence this detour lives inside of (settings interview, mode routing, the rest of phase 1), and is the canonical source for exactly where within that pass the scout spawn sits: **after** the settings interview and `settings.js write`, never before — nothing before the sketchbook consumes `scout/reuse-map.json`/`scout/constraints.json`, and the interview's own panels do not vary by onboarding mode. This document's own detect → scaffold → scout ordering and its concrete reason (the `scaffoldTree` force/overwrite risk, above) bind regardless of where in the door that last leg falls.
