# The Handover — how phase 8 actually runs

The handover produces **two artifacts**, and neither one is optional or a substitute for the other: the styled final presentation, and the last-mile report — what remains, prioritized, honestly. Delivered scope is never silently incomplete; fix-loop-cap items still open when this phase runs route through the agreement pass, never a silent drop. The voice law binds hardest here: fact first, one breath of style at most, no recorded event means no line, and red is red — never softened.

Binds `machine/src/{delivery,phases,quarantine}.js`'s actual, already-built APIs, `machine/phases-registry.json`'s `delivery` entry, and `product/voice/kiln.md`'s own handover sample line ("It stands. Everything on the list runs green — proven, never promised. One honest page waits for you on what is left for later, and why" — traced to the delivery gate, all criteria green plus the last-mile report generated). This phase only *reads* the verification tree, never writes it. Same class of artifact as `product/verification/flow.md` and `product/implementation/flow.md` — Maestro's own operating knowledge for one phase, read by Maestro and by whichever handover agents need to know their place in the sequence, never scraped for state.

The handover (phase 8, `machine/phases-registry.json`'s `delivery` entry) is `interactive: false` — no operator judgment gates this phase's own mechanics; the presentation IS the operator-facing moment, but nothing about producing it asks the operator anything mid-pass. It is also the registry's **terminal phase** — the highest `order` value in the eight-phase sequence — a structural fact this document's own closing step (below) is built around, never worked around.

## The tree, as actually built

Four files live under `delivery/`: the two prose artifacts the handover is named for, and the two machine-checkable projections (`machine/src/delivery.js`) those artifacts are grounded in. `machine/phases-registry.json`'s `delivery` entry names all four in its `exit_emits`/`exit_checks`:

```
delivery/
  last-mile.json         JSON   machine/src/delivery.js's           {schema_version, generated_from_run,
                                 assembleLastMile (sole writer)      items:[{source:{file, seq|path},
                                                                      id, summary, severity,
                                                                      owner_phase?}], counts:{total,
                                                                      last_mile_parks, quarantine_entries,
                                                                      fix_attempts_at_cap,
                                                                      verification_reports,
                                                                      milestones_not_green}}
  facts.json              JSON   machine/src/delivery.js's           {schema_version, facts:[{kind,
                                 renderFacts (sole writer)           ts, ...statement fields}]} —
                                                                      phase-transition / suite-state /
                                                                      milestone / last-mile-counts kinds
  last-mile-report.md     MD    delivery-presenter (prose,           honest remainder, prioritized —
                                 "Roster," below)                     every claim traces to
                                                                      a `last-mile.json` item
  presentation.md          MD    delivery-presenter (Kiln's            styled final; no event, no line —
                                 own first person)                    every claim traces
                                                                      to a `facts.json` entry
```

`last-mile.json` and `facts.json` are **machine-generated, deterministic projections over already-recorded truth** — never a place new facts get invented — the same "assembles, never writes" division the hundred eyes' own `assembleSuite` draws, applied here to this phase's two read-only assemblers. `last-mile-report.md` and `presentation.md` are the only two artifacts in this phase that need model judgment — turning recorded facts into honest, prioritized, styled prose — and they are the two the handover is actually named for.

## Roster

- `delivery-presenter` (`agents/delivery-presenter.md` — a runtime reader of this document does not read that file, and would not resolve a bare `agents/` path from the operator's project if it tried; Maestro's outbound brief carries the plugin-root-prefixed anchor when a seat needs one) — spawned once, after `assembleLastMile`/`renderFacts`/`checkDeliveryReady` have all run in that order and the last one reports `{ok:true}`, brief anchors naming `delivery/facts.json` and `delivery/last-mile.json` as the two projections it renders from, plus the one voice file it composes in (`product/voice/kiln.md`, anchored at the prefixed path `agents/maestro.md`'s outbound-brief law requires for every plugin-internal anchor) — three reads, named as three, never understated to two. Its own `tools:` frontmatter is `Read, Write` only — no `Bash`, no `Grep`, no `Glob` — a structural guarantee, not a stated intention, that it cannot reach for `ledger.jsonl` or any raw stream even if it wanted to — a raw unbounded stream never reaches a model here, enforced at the tool-permission layer rather than by instruction alone. Its own precondition re-verifies both inputs exist and parse, AND independently re-checks `facts.json`'s own `suite-state` fact reports `status: "green"` before writing a word — belt-and-suspenders on top of Maestro's own `checkDeliveryReady`, never a substitute for it (a `blocked` envelope here means an upstream sequencing error, not something this seat papers over). It renders `delivery/last-mile-report.md` covering **every** `last-mile.json` item (severity-ordered: `blocking` first, then free-text severities alphabetically, then `quarantined`, `pending`, `unclassified`, `unspecified` last) with its own internal self-check that its rendered count equals `last-mile.json.counts.total` exactly, and `delivery/presentation.md` in Kiln's own first person, one beat per `facts.json` entry, each fact-bearing line carrying an inline citation — `[<kind> @ <ts>]` when the fact carries a recorded `ts`, else `[<kind> @ <source.file>[:<seq|path>]]` naming the fact's own source locator instead. A timestamp a fact does not carry is never synthesized to stand in for one. Its envelope `result` field states the item count it rendered — the number Maestro's own "counts match" check (step (d), below) cross-references against `last-mile.json`'s own `counts.total`.
- `agreement-pass` — reused, unchanged, if `assembleLastMile`'s own `fix_attempts_at_cap` items are still open at this phase (a fix-loop cap reached during verification and never resolved by a repair before delivery ran) — the same blocker-ladder default every earlier phase already routes through (`maestro.md`'s "Blocker ladder → agreement pass").
- `discovery-agent` / `security-scanner` — not spawned again here; their post-green verification-phase findings (`product/verification/flow.md` step (e)) already reached `last-mile.json` through the ordinary channels `assembleLastMile` reads (a queued fix-task or a `verification/*.md` report file), never a second delivery-phase spawn of the same seats.

## Machine layer (as actually built)

- `machine/src/delivery.js`:
  - `checkDeliveryReady(treeRoot)` — `{ok, missing[]}`. Composes `phases.js`'s own exported `runExitChecks` over three named facts: `verification/suite-state.json` must pass the identical `suite-state-green` check (green **and current** — the same `runs-index.json` cross-check `product/verification/flow.md`'s own exit check performs) verification's own exit already ran, plus `delivery/last-mile.json` and `delivery/facts.json` must each pass `run-bound` — its own `generated_from_run` field, stamped by `assembleLastMile`/`renderFacts` when they wrote the file, must equal the SAME current-run identity `suite-state-green` just confirmed; missing, unparseable, empty, or stale (a run older than the live suite) all fail closed. Reusing `runExitChecks` rather than re-deriving either judgment a second way is doctrine rule 6 (one native mechanism per constraint) — the reason this re-check exists at all is temporal, not redundant: delivery can be entered long after verification's own exit check last ran (a resumed session; a later quarantine mutation marking `suite-state.json` stale; a newer run going green after these two projections were last rendered), so "is the suite still honestly green right now, AND do these two projections still reflect it" is a distinct question asked at a distinct moment. `run-bound` subsumes what a bare `file-nonempty` check on these two files would do and goes further: a present-but-stale file fails here too, so readiness never accepts delivery projections rendered against an older run.
  - `assembleLastMile(treeRoot)` — the sole writer of `delivery/last-mile.json`. A deterministic projection, never a place new facts get invented, over five sources, every item carrying a `source` pointer naming the file (plus a `seq` or `path` locating it within that file) it was derived from: `last-mile.jsonl`'s own `"park"` records (Maestro's sole-writer parking stream, via `delivery.js`'s `park` command — the invocation form lives in `agents/maestro.md`'s "Blocker ladder → agreement pass" section, as every runtime command this document names lives in its executing seat's charter: this file is plugin payload, so a command stored here would reach Bash with its plugin-root prefix unresolved. A worker requests parking through its envelope, never appends directly); `verification/quarantine.json`'s entries, both PENDING (mid-incident) and DECIDED (a real quarantine verdict); `verification/fix-attempts.jsonl` problem-keys that reached the fix-loop cap (`FIX_LOOP_CAP`, imported from `quarantine.js` rather than re-declared, so this can never drift from the actual enforcement threshold); `verification/*.md` report files, presence-referenced only (never parsed — markdown carries prose meaning and is never scraped for state, here as everywhere); and `milestones/index.json` entries whose status is not `"green"`. `counts` totals every category so `last-mile-report.md`'s own coverage is machine-checkable (step (d), below).
  - `renderFacts(treeRoot)` — the sole writer of `delivery/facts.json`. The narrating seat's own bounded input projection — never the raw stream, and DATA only, every element `{kind, ts, ...}`, never a prose sentence: ledger `phase-transition` records (`projection.project`, `lastN: 100`, never the raw `ledger.jsonl`), the current `verification/suite-state.json` snapshot (run id, status, pass/fail/quarantine counts), one fact per `milestones/index.json` entry, and `last-mile.json`'s own `counts` — cited, never recomputed a second way. Requires `delivery/last-mile.json` to already exist (throws otherwise) — `assembleLastMile` runs first in this phase's own sequence, always.
  - CLI: `delivery.js {check-delivery-ready|assemble-last-mile|render-facts} <treeRoot>` — the same flat, one-command-per-call convention `verification.js`/`quarantine.js`/`milestones.js` already establish. Maestro is the sole caller of all three; the prefixed invocation forms are in `agents/maestro.md`'s Bash law point 6.
- `machine/src/phases.js`'s `closeTerminal(treeRoot, registry, statePath, ledgerPath)` — the terminal-phase counterpart to `advance()`. `advance()` always throws `"is the terminal phase... nothing to advance to"` against delivery, by construction — the registry's own highest-`order` phase has no `order+1` to enter. Without a terminal closer, delivery's own `exit_emits`/`exit_checks` would never be marked verified and its `phase_status` entry never flipped to `"complete"`, leaving a fully delivered build with no machine-checkable "done" fact for `resumePoint()` to report. `closeTerminal` runs the SAME `exit_emits`/`exit_checks` validation `advance()` already runs on the phase it closes (never a second implementation of "is this phase's own exit satisfied" — doctrine rule 6) and the same ledger-first write-ahead ordering, but writes a `"phase-terminal"` ledger record (there is no `"to"` phase) and sets `next_action` to the literal sentinel `"done"` rather than leaving it pointed at a phase that has, in fact, already finished. Throws if called on any phase other than the registry's own terminal one. CLI: `phases.js close-terminal <treeRoot>`, Maestro's own call per Bash law point 6.

## The engine

The executable order is law, and it runs in this exact sequence every time delivery is entered — a fresh entry from verification's exit, or a resume where an earlier attempt left stale projections behind: `assemble-last-mile`, then `render-facts`, then `check-delivery-ready` as the final pre-presentation gate. No step in this document, and no other document that describes this phase, instructs calling `check-delivery-ready` before the two projections it checks exist — that order is unsatisfiable by construction (`checkDeliveryReady` requires both files present and current; `renderFacts` itself requires `last-mile.json` to already exist).

### (a) Assemble the facts, unconditionally — `assembleLastMile`, then `renderFacts`

Delivery is only entered once verification's own exit has already gated the suite (`entry_requires`, above) — that gate is not re-asked here first. Instead Maestro runs both projections unconditionally, every entry (Bash law point 6 carries both invocation forms): `assemble-last-mile <treeRoot>` first — `renderFacts` cites `last-mile.json`'s own `counts` rather than recomputing them a second way, and throws if that file does not yet exist — then `render-facts <treeRoot>`. Both are pure, deterministic, judgment-free — determinism through workflows, never guardrails — which is why Maestro's own narrowly-scoped Bash runs them directly (`maestro.md`'s "Bash, narrowly" point 6) rather than delegating them to a worker: there is no judgment here to delegate. Running both unconditionally, before any readiness question, is what makes the first-delivery path executable at all: on a first entry neither `delivery/last-mile.json` nor `delivery/facts.json` exists yet, so any order that asks readiness first can never reach a state where it can say yes.

### (b) Verify readiness — `checkDeliveryReady`, the final pre-presentation gate

Maestro calls `delivery.js`'s `check-delivery-ready <treeRoot>` (Bash law point 6). Two distinct `{ok: false}` shapes route to two distinct responses, never conflated:

- **A `suite-state-green` failure naming `verification/suite-state.json`** — the suite itself has gone stale or red since verification's own exit. This is **not** a delivery-phase failure to fix here: it means the acceptance suite itself needs another failing-first pass, and Maestro routes back to `product/verification/flow.md`'s own engine (step (b), its failing-first dance) rather than inventing a delivery-phase repair mechanism of its own (doctrine rule 6 — one native mechanism per constraint, verification owns "make the suite green," delivery only ever re-asks whether it currently is).
- **A `run-bound` failure naming `delivery/last-mile.json` or `delivery/facts.json`** — the suite itself is green and current, but a newer run went green after these two projections were last written (a resumed session; a quarantine mutation between renders). This is not a suite problem: Maestro re-runs step (a) — `assemble-last-mile` then `render-facts` — against the now-current run, and calls `check-delivery-ready` again. Never patch either JSON file in place; the projections are always regenerated whole, per their own "assembles, never writes" contract (above).

Only once `check-delivery-ready` reports `{ok: true}` does step (c) run.

### (c) Spawn `delivery-presenter` — facts + last-mile only

Maestro's brief names exactly `delivery/facts.json` and `delivery/last-mile.json` as this worker's anchors (never the raw ledger, never raw quarantine.json — see the Roster's own paragraph, above, for the full contract this seat is written against). It writes `delivery/presentation.md` (Kiln's own first person, styled — no recorded event, no line) and `delivery/last-mile-report.md` (honest, prioritized remainder) and reports back through the standard six-field envelope, its `result` field stating the exact count of `last-mile.json` items it wove into the report.

### (d) Verify the two `.md` artifacts land, and that nothing was silently dropped

Two checks, both small and bounded (Maestro's own Do/route boundary — reading a worker's envelope and a small JSON file, the same class of read a routing config already gets):

1. **The artifacts land** — `machine/phases-registry.json`'s `delivery` `exit_checks` (below) cover this structurally the moment `closeTerminal` runs; Maestro does not need a separate ad hoc check here, per the same anti-redundant-enforcement reasoning `product/verification/flow.md`'s own exit-check discussion already draws.
2. **Counts match** — two layers, not one. `delivery-presenter.md`'s own contract requires it to self-check its rendered `last-mile-report.md` item count against `last-mile.json.counts.total` BEFORE it ever reports `state: done` (its own "Writing `delivery/last-mile-report.md`" section: "an easy self-check: count your own rendered entries before finishing"). Maestro's own layer on top of that self-attestation: read `delivery/last-mile.json`'s own `counts.total` (already on disk from step (a)) and compare it against the count the presenter's envelope `result` field states — a small, bounded read, the same Do/route-boundary class as a routing config or any other worker's envelope. A mismatch — the presenter's own self-check missed something, or its envelope misreports what it actually did — is **not** waved through: delivered scope is never silently incomplete, and that is the law this check exists to enforce, and a mismatch climbs the blocker ladder exactly like any other failed verification (`maestro.md`'s "Blocker ladder → agreement pass": one retry with a provably distinct approach, e.g. re-spawning the presenter with an explicit reminder of the missed item; a second distinct mismatch escalates). This remains a Maestro-side comparison rather than a dedicated machine function, because the fact it checks (a worker's own prose coverage of a JSON list) has no deterministic shape to assemble ahead of the prose itself — the same boundary `product/verification/flow.md`'s own "Roster" section draws when it names a gap plainly rather than inventing machinery to paper over it.

Once the counts match — never on a mismatch, and never before this check has actually passed — Maestro runs the telemetry `enabled`/`record` pair (`agents/maestro.md`'s Bash law point 10, which carries both invocation forms and the caller authority for them) and, when enabled, records `{kind: "delivery_summary", payload: {last_mile_count: <the same `last-mile.json.counts.total` this check just cross-referenced>}, correlation_id: null}` — read by last-mile calibration, in service of the same delivered-scope honesty.

### (e) Present — the closing moment

Once both artifacts are verified, Maestro renders the operator-facing closing narration in Kiln's own first person (`product/voice/kiln.md`, loaded at the prefixed path `agents/maestro.md`'s "Narration" section anchors, never composed by Maestro itself), citing `delivery/presentation.md` and pointing the operator at `delivery/last-mile-report.md` for the honest remainder — the handover sample line ("It stands. Everything on the list runs green — proven, never promised. One honest page waits for you on what is left for later, and why") is written against exactly this moment, traced to the delivery gate, all criteria green plus the last-mile report generated. **Red is red, never softened** — if `checkDeliveryReady` was ever `{ok: false}` on the path here, that fact is not narrated away; the presentation renders only once the gate is honestly green.

### (f) Close — the terminal phase, not a ninth phase

`machine/phases-registry.json`'s `delivery` entry, as actually built:

```json
{
  "id": "delivery",
  "exit_emits": [
    "delivery/last-mile-report.md",
    "delivery/presentation.md",
    "delivery/last-mile.json",
    "delivery/facts.json"
  ],
  "exit_checks": [
    { "file": "delivery/last-mile-report.md", "check": "file-nonempty" },
    { "file": "delivery/presentation.md", "check": "file-nonempty" },
    { "file": "verification/suite-state.json", "check": "suite-state-green" },
    { "file": "delivery/last-mile.json", "check": "run-bound" },
    { "file": "delivery/facts.json", "check": "run-bound" }
  ]
}
```

The handover is the registry's own last phase — the spine names exactly eight, no ninth "done" phase exists, and this document does not invent one. `phases.js close-terminal <treeRoot>` (`maestro.md`'s "Bash, narrowly" point 6, where its invocation form lives) is the closing step this phase's own version of "the worker whose brief closes a phase's `exit_emits` runs its own closing call" (`product/verification/flow.md`'s "Phase sequencing" precedent) takes — `advance()` itself is never called here, it structurally cannot be. `closeTerminal` fails closed exactly like `advance()` does on a missing `exit_emits` file or a failed `exit_checks` entry — and because the registry's own `exit_checks` above include `suite-state-green` and `run-bound` on both projections — so a not-ready or red delivery can never be marked done — `closeTerminal` natively enforces the identical readiness `checkDeliveryReady` computes, at the registry-declared layer, without `phases.js` importing `delivery.js` (doctrine rule 6 — one native mechanism per constraint, exercised through the same registry data both `checkDeliveryReady` and `closeTerminal` read). `closeTerminal` is also exactly-once: it refuses a second call once `next_action` already reads `"done"` or the phase's own `phase_status` entry already reads `"complete"`, checked before any ledger append or state write — a build that has already closed produces exactly one `"phase-terminal"` ledger record, never two. Once it succeeds, `state.json`'s `phase` stays `"delivery"` (there is nowhere else to point it) and `next_action` reads the literal sentinel `"done"` — the fact `resumePoint()` now has to report a fully delivered build with, where none existed before. The forge cools; the work remains.

## Failure paths

**`checkDeliveryReady` reports not-ok.** Per step (b): a `suite-state-green` failure routes back to verification's own failing-first dance; a `run-bound` failure routes back to step (a) to re-render against the current run. Neither is patched around here.

**A `delivery-presenter` mismatch on the "counts match" check.** Per step (d): blocker ladder, capped at two attempts, then agreement pass — the same ladder every other phase's own failed verification already climbs.

**`closeTerminal` refuses.** Either `exit_emits` are still missing (the presenter has not yet produced one or both `.md` files — this is not a distinct failure mode, it means step (c)/(d) has not actually completed yet, and Maestro does not call `close-terminal` before it has), an `exit_checks` entry fails on a file that exists but is empty/whitespace-only (a presenter that reported `done` without actually writing real content — an honesty violation for the presenter's own envelope contract, not something this phase silently accepts), a `suite-state-green`/`run-bound` entry fails (the suite or one of the two projections went stale between step (b)'s own `checkDeliveryReady` call and this one — re-run steps (a)–(b) rather than retrying `close-terminal` bare), or the phase is already closed (`next_action` already `"done"` — this is not an error to recover from, it means closure already happened and nothing further is required).

## Known, disclosed scope limits

- The "counts match" check (step (d).2) is a Maestro-side comparison against the presenter's own envelope, never a dedicated machine function — the same honesty convention `product/verification/flow.md`'s own "Roster" section holds for `verification/affected-map.json`'s maintenance gap. `delivery-presenter.md`'s own internal self-check (Roster, above) is a real, load-bearing second layer, but nothing machine-enforces that its envelope `result` field honestly reports what it actually rendered — the same trust boundary every worker envelope in this product carries.
