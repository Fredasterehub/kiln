# Implementation flow — how the anvil runs, milestone by milestone

Binds `agents/maestro.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Blocker ladder → agreement pass", §"Communication protocol", §"Verification doctrine") to the product law's implementation rule ("Implementation, per milestone/vertical slice — JIT, TDD"), to its verification architecture (JIT journey authoring, the anti-brittleness checklist), to its kept-warm milestone designer (verbatim anchors, facts by reference, judgment by consultation), to the standing tree law (the `milestones/<id>/` shape and its restart-anytime boundary), to the adopted toolchain design, and to the proven git flow every git command below is drawn from verbatim rather than reinvented — execution-proven in the dev record. Same class of artifact as `product/architecture/flow.md` — Maestro's own operating knowledge for one phase, read by Maestro and by whichever implementation-phase agents need to know their place in the sequence, never scraped for state: a script reads records, never prose.

The anvil (phase 6, `machine/phases-registry.json`'s `implementation` entry) is `interactive: false` — no operator judgment is required to run it; every escalation this flow names routes through the blocker ladder (`maestro.md`'s own section, unchanged here) and, beyond that, the pipeline-wide agreement pass default, never a hosted operator conversation mid-milestone.

## Roster (built as of this revision)

`milestone-designer` (`agents/milestone-designer.md`, opus-5 high, kept-warm — the ONE Claude seat every milestone gets regardless of `designer_family`), `implementer-sol` (`agents/implementer-sol.md`, sonnet-5 high, dispatches GPT-5.6-Sol via Codex CLI — routing's `implementer` seat, the default), `implementer-opus` (`agents/implementer-opus.md`, opus-5 high, native — routing's `implementer_ui_creative` seat, UI/creative milestones only), `chunk-reviewer-sonnet` (`agents/chunk-reviewer-sonnet.md`, sonnet-5 high — routing's `chunk_review_of_gpt_work` seat, reviews every `implementer-sol` diff), `chunk-reviewer-sol` (`agents/chunk-reviewer-sol.md`, sonnet-5 medium scoped, dispatches Sol via Codex CLI — routing's `chunk_review_of_claude_work` seat, reviews every `implementer-opus` diff), `milestone-reviewer` (`agents/milestone-reviewer.md`, sonnet-5 high — routing's `milestone_review: "cross-family"` seat, reviews each milestone's CUMULATIVE diff once every chunk is green, family-routing itself to a native read or a Sol-hosted dispatch depending on which family dominated the milestone's own chunk implementations — the law's own "Milestone review closes each slice," distinct from per-chunk review). `agreement-pass` (already in Maestro's roster) is this phase's escalation seat, unchanged.

Machine layer: `machine/src/milestones.js` (`createMilestone`/`recordChunk`/`closeMilestone` — the milestone-lifecycle bookkeeping this flow drives, `closeMilestone` now requiring and verifying real git evidence, below), `machine/src/toolchain.js` (`loadProfiles`/`validateProfiles`/`detectPackageManager`/`probeSatisfied`/`composeInstall`/`scaffoldProfile` — the R3 toolchain design, `detectPackageManager` now falling back to a PATH probe and `scaffoldProfile` materializing each profile's own scaffold inputs), `machine/src/check-honesty.js`'s `runGate` (the one sanctioned command-execution-plus-ledger-evidence mechanism, reused here rather than duplicated — doctrine rule 6), `machine/src/phases.js` (phase sequencing, plus this revision's `milestones-all-green` exit check).

All six agent files above are wired into `agents/maestro.md`'s own `tools:` frontmatter, roster table, and its widened "Bash, narrowly" law (the machine-layer CLIs plus the enumerated git commands this flow names below) — the roster/wiring gap and the missing milestone-review seat a prior revision disclosed here are both closed as of this revision.

## The engine — for each `architecture/milestones.json` entry, in order

Milestones run sequentially in v1 (the law: "Chunks sequential in v1"; the same discipline applies one level up — one milestone open at a time, in the `order` `validateMilestones` already enforces contiguous). For each entry:

### (a) Maestro creates the milestone

Two calls, both narrowly-scoped Bash per `maestro.md`'s "Bash, narrowly" law (machine-layer CLIs and named git commands only — never an ad-hoc script):

1. `milestones.js`'s `create` command (`agents/maestro.md`'s Bash law point 4 — the invocation form lives there, as it does for every runtime command this document names: this file is plugin payload, so a command stored here would reach Bash with its plugin-root prefix unresolved), taking `<treeRoot>` plus a JSON entry `{"id", "title", "designer_family", "toolchain_profile"}`. `<treeRoot>` is the `.kiln` directory itself, NEVER `<treeRoot>/milestones` (`createMilestone` appends that segment internally; passing it pre-appended was a documented-but-broken shape a prior revision of this flow named and this revision corrects). The values come straight from the `architecture/milestones.json` entry this loop is on (`id`, `title`, `designer_family`, and `toolchain_profile` if the architecture phase set one; `null` otherwise, per R3's "nothing needed" value). This materializes `milestones/<id>/{mailbox/, chunks.jsonl}` and appends the tracking row to `milestones/index.json` — `machine/src/milestones.js`'s `createMilestone`, refusing (throwing) on a duplicate id, so a resumed session re-running this step for an already-created milestone fails loud rather than silently re-genesis-ing it.
2. `git checkout -b milestone/<id>` — off whatever branch the previous milestone's merge landed on (`main` for the first milestone), per the proven git flow's Step 2 ("Create milestone branch") — execution-proven in the dev record. Every milestone gets its own branch; agents never commit to a shared branch.

### (b) Toolchain preflight — zero new artifacts, one closed enum, one gate

**Actor: `milestone-designer`, as its own opening action.** Maestro does not run these calls — its own Bash law reserves `toolchain.js` for a worker's brief by name — so this step executes inside the designer's dispatch, before it decomposes the slice: step (a)'s two Maestro calls happen, then the designer is spawned (step (c)), and this preflight is the first thing that seat does with the `toolchain_profile` its brief carries. The invocation forms for all four calls below live in `agents/milestone-designer.md`'s own "Toolchain preflight" section, which is where every runtime command this step names is written out — this file is plugin payload, so a command stored here would reach Bash with its plugin-root prefix unresolved.

Skipped entirely when the milestone's `toolchain_profile` is `null` ("this milestone needs nothing beyond what's already installed"). Otherwise:

1. `toolchain.js`'s `probe-satisfied` — a presence probe over the target project (`targetRoot`), never the `.kiln` tree. `node-cli` is always satisfied (Node ships `node:test`); `node-web`/`python-pytest` check for `node_modules/@playwright/test` / `.venv/bin/pytest` respectively.
2. If unsatisfied: `scaffold-profile` materializes the profile's own scaffold inputs FIRST — a generated `playwright.config.ts` plus an example `tests/example.spec.ts` for `node-web` (each individually skipped, never overwritten, if it already exists on disk), the `requirements-dev.txt` entry (created with its venv-convention note, or appended if the file already exists without a `pytest` line) for `python-pytest`; `node-cli` is a no-op. THEN `compose-install` composes the exact install command — lockfile-first package-manager detection for `node-web` (per the adopted toolchain design, now falling back to a PATH probe of npm/yarn/pnpm/bun, in that order, when neither a lockfile nor a `packageManager` field names one, so a fresh Node target with only a global npm install can still preflight), with the browser-install half now composed through that SAME resolved manager (`npx`/`yarn dlx`/`pnpm dlx`/`bunx playwright install --with-deps`, never a hard-coded `npx` regardless of manager); a fixed venv+pip command for `python-pytest`; `node-cli` never reaches either step.
3. The composed command runs through `check-honesty.js`'s `run-gate` at `gateId: "toolchain-<id>"`, the one sanctioned command-execution-plus-evidence mechanism (doctrine rule 6: one native mechanism per constraint — never a second install-and-hope path bolted onto this flow). The resulting ledger `gate` record (`{gate_id, cmd, exit_code}`) is the evidence `check-honesty.js`'s existing gate-evidence law already knows how to cross-check; no new mechanism is added here.
4. `exit_code !== 0` — a real toolchain install failure — climbs the blocker ladder exactly as any other worker fix-attempt failure does (`maestro.md`'s "Blocker ladder → agreement pass": one retry with a provably distinct approach is normal, a second distinct failure escalates to `agreement-pass`). No special-cased toolchain-failure path exists; this is the same ladder every other implementation-phase failure in this document climbs.

### (c) Spawn the kept-warm milestone designer

`milestone-designer` is spawned once per milestone (never respawned while one is alive for it — `agents/milestone-designer.md`'s own frontmatter: "Spawn once per milestone at implementation-phase entry... never a second designer while one is still alive for it"), with the milestone's slice (`slice_goal`, `criteria_ids`, `toolchain_profile`, `designer_family`) from `architecture/milestones.json`, plus `architecture/plan.md`, `architecture/criteria-register.json`, and the relevant `research/summary.md` sections as anchors.

**This spawn precedes step (b)'s execution**: the toolchain preflight is this seat's own opening action, run before it decomposes anything, because a chunk whose implementer cannot run the target project's suite is a chunk that cannot go green. Step (b) is written above rather than below only because it belongs to milestone setup rather than to decomposition; the designer's own charter states the ordering as the seat actually holds it.

**Confirmed against the actual built agent**: the designer's own frontmatter always stays Opus 5 high regardless of `designer_family` — what changes is who authors `spec.md`'s CONTENT. `designer_family: "claude"` milestones get `spec.md` authored directly by the designer's own judgment. `designer_family: "gpt"` milestones (the default — the law: "Sol implements most") get `spec.md`'s chunk decomposition DRAFTED by the designer itself dispatching Sol via the `codex-cli` skill (the same one-agent-hosts-two-seats pattern `plan-author-sol.md`/`plan-coverage-checker.md` already use elsewhere in this pipeline) — never via a separate `implementer-sol` spawn, which is reserved for chunk implementation, not milestone design. The designer verifies Sol's draft (every chunk states WHAT, never HOW — `milestone-designer.md`'s own "Verify before adopting" line) before writing `spec.md` and taking over execution ownership (mailbox, consult verdicts, `chunks.jsonl` writes) either way.

`spec.md`'s per-chunk shape (WHAT-to-build / WHAT-to-test, criteria_ids closed, an 8-field chunk brief validated against `machine/src/validators.js`'s `validateBrief`) is the "anchor source" the law means by "verbatim anchors" — every consult verdict the designer gives from here on quotes it exactly, by section, never a paraphrase.

### (d) Chunks — sequential v1

For each chunk `spec.md` names, in build order:

1. **Designer records `chunk-spec`.** The designer's brief-issuance is logged via `machine/src/milestones.js`'s `recordChunk(treeRoot, milestoneId, {kind: "chunk-spec", chunk_id, brief_ref})` — `brief_ref` pointing into `spec.md`'s own section for this chunk, never a copy of the brief's text into the stream — a script reads records, never prose.
2. **Implementer seat per routing, NEVER Fable.** `implementer-sol` (routing's `implementer` seat, the default) for every chunk except UI/creative ones, which route to `implementer-opus` (`implementer_ui_creative`) — the law verbatim: "Sol implements most; Opus 5 takes UI/creative; Fable 5 never implements," the design-smell rule `milestone-designer.md`'s own "Identity & scope" section names directly ("the same one that keeps Fable out of implementation entirely"). `recordChunk(..., {kind: "chunk-start", chunk_id, implementer_seat, implementer_family})` logs which seat took the chunk AND its family (`"gpt"` for `implementer-sol`, `"claude"` for `implementer-opus`) — the fact this chunk's eventual `chunk-green` record is cross-checked against later (below), so it must name the real implementer, never a placeholder.
3. **TDD + JIT journeys.** The implementer writes the failing test(s) first, confirms the right failure, then the minimum green implementation (`implementer-sol.md`/`implementer-opus.md`'s own "TDD dispatch" sections) — running the target project's suite via the milestone's `toolchain_profile` reporter flags (`node --test`'s TAP output for `node-cli`, `npx playwright test --reporter=json` for `node-web` — **`npx playwright` only, never the Playwright MCP tool** — a standing product law, never a per-phase preference — `pytest --junitxml=...` for `python-pytest`). If the designer nominated this chunk for a criterion's journey (`criteria-register.json`'s pre-minted `journey_id`), the implementer authors that journey script now, JIT, against the anti-brittleness checklist verbatim (no hard-coded waits, stable element identity, mandatory outcome assertions) — reviewed in the SAME chunk review that follows, zero new review events (the law: "reviewed like code in the existing chunk/milestone reviews"). The milestone designer logs `recordChunk(..., {kind: "chunk-journeys", chunk_id, journey_ids})` once the implementer's envelope reports the script's `journey_id`(s) authored, and — the ONE addendum `product/verification/flow.md`'s "journeys.json provenance" section already specifies as canonical but this step never named directly (a dogfood finding, execution-proven in the dev record: `journeys.json` had to be reconstructed by hand at verification entry because no chunk brief ever said to write it) — the SAME step also appends one entry per authored `journey_id` directly to `verification/journeys.json` — read-current-array-append-write, creating the file fresh with `{schema_version:1, journeys:[]}` if this is the build's first journey, in the exact `{journey_id, criterion_id, script_path, harness, added_in_milestone}` shape `assembleSuite` expects. **Disclosed residual**: this is the one stream-shaped write in the whole pipeline with no closed-contract CLI writer behind it — the designer lands it with its own `Write` tool (`agents/milestone-designer.md`'s "JIT journey nomination"), so nothing machine-enforces the shape at the write boundary the way `kind-registry.js` does for every JSONL stream. `assembleSuite`'s own fail-closed validation at verification entry is what catches a malformed entry, one phase later than a writer-side refusal would. One JIT-authoring action, two records — the audit trail and the assemblable catalog entry — never a second disconnected writer reconstructing the catalog later.
4. **Cross-family chunk review.** `implementer-sol` (GPT-family) diffs go to `chunk-reviewer-sonnet` (Claude); `implementer-opus` (Claude-family) diffs go to `chunk-reviewer-sol` (GPT, dispatched via Codex CLI) — the routing law's seat ladder verbatim: "chunk reviews: GPT work→Sonnet 5, Claude work→Sol medium scoped." Diff-scoped correctness against `git diff HEAD` plus any untracked new file, contract adherence against the chunk's 8-field brief, the anti-brittleness checklist against any journey script added, report-everything discipline (every finding surfaces, tagged, no pre-filtering). Verdict is `approve` or `revise` — the CLOSED two-value vocabulary `machine/src/milestones.js` itself enforces (`"green"` is not a valid verdict; it never was a value either reviewer contract produced) — findings enumerated either way. `recordChunk(..., {kind: "chunk-review", chunk_id, review: {family, verdict, ref}})` logs the verdict, `family` the reviewer's own family (`"claude"` for `chunk-reviewer-sonnet`, `"gpt"` for `chunk-reviewer-sol`), `ref` pointing at the reviewer's own envelope/evidence artifact. Once this chunk's own latest `chunk-review` record carries `verdict: "approve"` — whether reached here on the first pass or only after the revise loop (step 5, below) runs its course — the reviewing seat runs the telemetry `enabled`/`record` pair (`agents/maestro.md`'s Bash law point 10 — Maestro pastes the resolved invocation forms into this seat's own brief, since a worker file is not a substituted surface for text it never carried) and, when enabled, records `{kind: "review_pass", payload: {scope: "chunk", pass_count: <this chunk's own total `chunk-review` record count>, agreement_pass: <true iff this chunk's revise loop escalated to `agreement-pass` before reaching approve, else false>}, correlation_id: null}` — read by the maintenance workflow's own review-reinforcement calibration.
5. **Revise loop, capped at 2, then the blocker ladder.** A `revise` verdict resumes the SAME implementer session (never a fresh dispatch — `implementer-sol.md`/`implementer-opus.md`'s own "Fix passes" sections) for a fix round, then the SAME reviewer session for a re-review — each re-review is its own new `chunk-review` record; `machine/src/milestones.js` allows any number of sequential `chunk-review` records for one chunk, but a `chunk-green` may only ever follow the chunk's OWN most recent one. Two revise rounds on the same chunk without reaching `approve` is a blocker — `maestro.md`'s "Blocker ladder → agreement pass" runs unchanged (one retry with a provably distinct approach is normal work; a second distinct failure escalates); no separate implementation-phase escalation mechanism is invented here.
6. **Green: Maestro commits.** The chunk seals here — evidence-bound, never sacred; a later red check reopens it. Only after `approve` — never the implementer, per both implementer agents' own "What you never do" sections ("a real, gate-named commit happens only after an approve verdict, made by the flow orchestrator, never by you") and per both chunk reviewers' own explicit prohibition on running `git commit`/`merge`/`tag` themselves. Maestro's Bash runs `git add -A && git commit -m "chunk: <chunk_id> green [gate <chunk_id>-unit]"` — the message naming the chunk and the gate id whose evidence backs it, per the proven git flow's own commit-message shape ("chunk: parser green [gate unit-parser]"), corrected here to name the specific chunk's own gate id rather than a project-wide one — then `git rev-parse HEAD` to read the real commit sha just made. `recordChunk(..., {kind: "chunk-green", chunk_id, commit, review: {family, verdict: "approve", ref}, verification: {gate_id, cmd, exit_code: 0}})` — `commit` is that real `git rev-parse HEAD` output (`machine/src/milestones.js` refuses anything that does not look like a git SHA), `review` must be copied EXACTLY (same `family`/`ref`) from the chunk's own latest `chunk-review` record — `recordChunk` refuses a `chunk-green` whose `review` diverges even slightly, so a caller cannot invent a family or ref no real review record ever carried — and `verification` is the exact suite run (`runGate`'s own record) that proved green. `machine/src/milestones.js`'s `recordChunk` REFUSES a `chunk-green` record carrying no `verification` object, a non-zero `exit_code`, a commit that is not a git SHA, a `review` that does not match the latest `chunk-review` record, or a `review.family` equal to the chunk's own recorded `implementer_family` (the cross-family review law, enforced structurally — the load-bearing rejection of the whole step) — a chunk cannot report green on an implementer's, reviewer's, or forger's say-so alone, mirroring `check-honesty.js`'s own "a gate passes only with ledger evidence" law at the chunk level, not merely the phase level.
7. **Next chunk.** Repeat from step 1 for `spec.md`'s next chunk, sequential — no parallel or speculative chunk ordering (`milestone-designer.md`'s own Sol-dispatch constraint states this explicitly, and it holds for the loop generally, not only the drafting dispatch).

### (e) Milestone close

Four steps, in THIS EXACT ORDER — review, then the regression floor, then merge+tag, then `closeMilestone` LAST. This ordering is load-bearing, not stylistic: a prior revision of this flow ran `closeMilestone` before the merge/tag existed, leaving a milestone marked "green" with no durable rollback point behind it if a crash or git failure struck between the two. `closeMilestone` itself now refuses to run at all unless the merge/tag it is told about are real, so this ordering is also the only one that can succeed. A milestone seals only once all four have landed — cross-family inspection, then the regression floor, then a durable rollback point, then the record:

1. **Cross-family milestone review.** `milestone-reviewer` (`agents/milestone-reviewer.md`, routing's `milestone_review: "cross-family"` seat) reviews the milestone's CUMULATIVE diff (`git diff <base-tag>...HEAD`, `<base-tag>` the previous milestone's own green tag, or this project's initial commit for the first milestone) for slice-level coherence a chunk-scoped review cannot see — do the chunks compose into the `slice_goal` `architecture/milestones.json` actually named, not merely each chunk's own local correctness. It family-routes itself: a native read when Sol dominated this milestone's chunk implementations, a Sol-hosted dispatch (mirroring `chunk-reviewer-sol.md`'s pattern) when Opus dominated — so the review stays genuinely cross-family either way. A light security paragraph rides along here too (the law: "security paragraph in milestone reviews"). An `approve` verdict's envelope path becomes step 4's `review_evidence`; a `revise` verdict climbs the blocker ladder like any other implementation-phase failure, before anything below it runs. Once `milestone-reviewer` reaches `approve` — whether on its first pass or after a blocker-ladder-driven fix and re-review — it runs the same telemetry `enabled`/`record` pair (Bash law point 10, relayed into its brief the same way) and, when enabled, records `{kind: "review_pass", payload: {scope: "milestone", pass_count: <this milestone's own total `milestone-reviewer` invocation count>, agreement_pass: <true iff this milestone's review escalated to `agreement-pass` before reaching approve, else false>}, correlation_id: null}` — read by the maintenance workflow's own review-reinforcement calibration.
2. **Accumulated journey suite re-run — the regression floor.** The law: "accumulated journey suite re-run as the floor" at milestone close. The full verification apparatus (failing-first dance, TIA-lite affected mapping, flake quarantine) belongs to the hundred eyes, not to this phase — this flow does not reach for that apparatus early. What it DOES run today, with primitives that already exist: every closed milestone's own `toolchain_profile` reporter command (accumulated across every milestone closed so far, not just this one) through `check-honesty.js`'s `run-gate` at `gateId: "milestone-<id>-regression"` — the same one sanctioned command-execution-plus-evidence mechanism step (b) already uses, never a second one, and run by the same seat: the kept-warm `milestone-designer`, still alive for this milestone and holding the Bash grant, per `agents/milestone-designer.md`'s "Toolchain preflight" section where that invocation form is written out. Maestro does not run it — `check-honesty.js`'s gate runner called directly is a worker's job by its own Bash law. A non-zero exit here means a later milestone's chunks broke an earlier milestone's own green suite; it climbs the SAME blocker ladder chunk-review failures climb, before any merge happens. The hundred eyes' own module supersedes this minimal floor with its richer failing-first/TIA-lite/quarantine apparatus — named here as a forward pointer, never something this flow claims to already provide.
3. **Merge + tag.** Only once both checks above are clean: `git checkout main && git merge --no-ff milestone/<id> -m "merge: milestone/<id> into main"` — a real, non-fast-forward merge commit, preserving the milestone branch's own shape in history (the proven git flow's Step 4). Then `git tag -a milestone/<id>-green -m "milestone/<id> green: all chunk gates passed"` — an annotated tag on the merge commit, named as the proof's own Step 5 names it, and the rollback point every later milestone's own rollback law (below) resets to. Then `git rev-parse HEAD` to read the real `merge_sha` step 4 requires.
4. **`closeMilestone`.** `milestones.js`'s `close` command (Bash law point 4), taking `<treeRoot> <id>` plus a JSON close-info object `{"tag": "milestone/<id>-green", "merge_sha": "<the real sha from step 3>", "review_evidence": "<milestone-reviewer's envelope path from step 1>"}` — `closeMilestone` refuses (throws) unless (a) every chunk this milestone ever recorded currently sits at `chunk-green` as its MOST RECENT lifecycle record (latest-by-seq among the four ordered lifecycle kinds, mirroring `check-honesty.js`'s own "only the latest record counts" discipline), (b) `tag`, `merge_sha`, and `review_evidence` are all present and non-empty, and (c) `tag` and `merge_sha` both independently verify against the real git repository via read-only `git rev-parse --verify` (`opts.repoRoot` defaulting to the project root the `.kiln` tree sits inside — a fabricated or stale merge_sha/tag refuses the close outright rather than trusting the caller's say-so). This is the machine-checkable floor `phases.js`'s new `milestones-all-green` exit check (below) reads at the implementation→verification phase boundary — a structural fact about `chunks.jsonl` AND the real git history behind it, never merely a claim about whether the milestone review/regression steps above genuinely happened in isolation (the review's own truth stays the reviewer's envelope evidence, the same "machine checks shape and evidence-linkage, the review seat checks truth" division `architecture/flow.md`'s own criteria-register section already draws).

### (f) Rollback law

Any post-merge regression discovered later — a subsequent milestone's chunks break something this milestone's own merge had proven green — resets to the LAST green tag, per the two proven rollback paths — execution-proven in the dev record — scoped exactly as that proof states:

- **Unmerged milestone branch, abandon it.** `git checkout main && git branch -D milestone/<id>` — `main` is provably untouched (`git diff --exit-code <last-green-tag>` returns 0), since an unmerged branch never touched `main`'s own tracked files.
- **Already-merged bad milestone, roll `main` back.** `git checkout main && git reset --hard <last-green-tag>` — restores `main`'s tracked files to exactly the tag (`git diff --exit-code <last-green-tag>` returns 0 after), discarding every commit after that tag, not merely the offending one. This is why the check in step (e.2) above runs BEFORE the merge, not after: catching a regression pre-merge needs no reset at all, only a blocker-ladder escalation on an unmerged branch.
- **Immediate-window recovery only — never a standing guarantee.** The proof's own final verdict states this precisely: a discarded commit stays reachable via `git reflog`/`git show`/`git cat-file` only until `gc.reflogExpireUnreachable` (default 30 days for the unreachable case, not the general 90-day `gc.reflogExpire`) or a manual `git gc` prunes it. This flow's rollback law inherits that scope exactly — a rollback executed promptly is safe; treating `git reflog` as permanent archival is not something this document, or the proof it is drawn from, ever claims.

## Registry conformance

`machine/phases-registry.json`'s `implementation` entry, as of this revision:

```json
{
  "id": "implementation",
  "entry_checks": ["architecture-gate-approved"],
  "exit_emits": ["milestones/index.json"],
  "exit_checks": [
    { "file": "milestones/index.json", "check": "file-nonempty" },
    { "file": "milestones/index.json", "check": "milestones-all-green" }
  ]
}
```

`milestones-all-green` (new `machine/src/phases.js` `EXIT_CHECK_KINDS` entry, this revision) reads `milestones/index.json`, requires a non-empty `milestones` array, and requires every entry's `status` field to read `"green"` — the only writer of that field is `machine/src/milestones.js`'s `closeMilestone`, so this check is really asking "has every milestone this run created been through the close sequence in §(e) above," structurally, at the one phase boundary that matters (implementation → verification). `file-nonempty` stays alongside it as the same belt-to-suspenders pairing `research/summary.md`'s own exit checks already establish elsewhere in the registry — proving the file exists and has content is a distinct, cheaper fact than proving its content means "done," and both are worth checking independently.

**Why no schema-aware check beyond presence-of-"green"**: the same honest limit `product/architecture/flow.md`'s own "Registry conformance" section names for `criteria-register.json`/`milestones.json` applies here — `phases.js`'s `EXIT_CHECK_KINDS` vocabulary is deliberately shallow (file-existence and JSONL-shape facts), and teaching it `milestones/index.json`'s full entry shape (id/title/designer_family/toolchain_profile/status) would either duplicate `machine/src/milestones.js`'s own bookkeeping logic inside `phases.js` or force a registry-specific per-file dispatch table `EXIT_CHECK_KINDS` was never designed to hold — the exact redundant-enforcement pattern doctrine rule 6 forbids. The check added is the narrowest one that closes the real gap (a milestone left silently "open" must block the phase from claiming done), nothing broader.

## Consult protocol (unchanged; stated here for completeness)

Every chunk-lifecycle step above that needs the designer's judgment — not "what does the brief say" (a direct read) but "what did the brief MEAN" — goes through `milestones/<id>/mailbox/<consult-id>.q` → `<consult-id>.a`, the proven file-mailbox channel — execution-proven in the dev record — never a mid-task `SendMessage` a worker inside a deterministic chunk-loop step cannot wait on. Every answer is a verdict PLUS a verbatim anchor — the exact `spec.md`/`architecture/plan.md`/criteria-register quote plus its file:line — never a paraphrase. No separate librarian agent exists or is needed; this is the same channel `maestro.md`'s own "Communication protocol" section already names as one of its two consult channels.

## Failure paths

**Milestone designer dies mid-milestone.** `spec.md` and `chunks.jsonl`'s own append-as-you-go history are the recoverable state (`milestone-designer.md`'s own frontmatter: "spawned fresh only at milestone start" otherwise resumed) — a fresh designer spawn for the SAME milestone id reads both before continuing, never restarting the decomposition from zero. This mirrors `plan-author.md`'s own crash-recovery contract for architecture.

**Implementer or reviewer session dies mid-chunk.** The chunk's own `chunks.jsonl` tail (`chunk-spec`/`chunk-start`/`chunk-review` — whichever is the latest record) tells a fresh spawn exactly which step to resume from; nothing about this flow assumes a chunk completes in one uninterrupted session.

**Codex/Sol dead.** `implementer-sol` (routing's `implementer` seat) and `chunk-reviewer-sol` (`chunk_review_of_claude_work`) both depend on Codex CLI. Per `routing-2026-07-27-2.json`'s own `degraded_seats` block: `implementer` degrades to `opus-5` (Opus becomes "the sole degraded-mode implementer for every chunk, not just UI/creative ones" — the config's own note), and `chunk_review_of_claude_work` degrades to a same-family Claude substitute — both with an honest notice in the affected worker's envelope, per the degraded-mode disclosure law. The Fable-never-implements ban holds unconditionally even in degraded mode (the config's own note states this explicitly) — degradation substitutes Sol, never Fable.

**Toolchain install gate fails.** See step (b) above — climbs the same blocker ladder as any other implementation-phase failure; no special-cased path.

**Post-merge regression.** See §(f), Rollback law, above.
