# The Door — how phase 1 actually runs

Phase 1's charter, and the whole of it: plumbing preflight; the settings interview; greenfield / brownfield / legacy / resume / broken-install detection — brownfield adding a scout-and-inventory pass, legacy adding an intake leg that sets an earlier Kiln tree aside whole before anything is scaffolded, then every artifact created, then re-entry wherever state says. The door also puts two standing questions to the operator: plan review or auto-proceed, and blocking preference — auto-remedy or advise-me. It is a scripted flow writing straight to state, never a conversation: an advise-me moment is one compact question and one answer, and this phase hosts no multi-turn operator dialogue.

Binds `product/onboarding/preflight.md` (LAW for the five checks' exact semantics, order, and never-buried report rules) and `product/onboarding/interview.md` (LAW for the settings interview's own execution constraint and step sequence), `product/brownfield/flow.md` (the detect→scaffold→scout law this document's own mode-routing step below places precisely, closing that document's own disclosed "does not exist on disk" gap note), `product/legacy/flow.md` (LAW for what happens to an earlier Kiln tree — the archive-then-harvest transaction, what may be carried and what may never be, and the line the operator hears; this document places its two legs at (a0) and (d) and states nothing about the transaction's own contents), `machine/phases-registry.json`'s `onboarding` entry (five `exit_emits`, this document's own "The tree" section names where each one actually comes from), and `machine/src/{scaffold,detect,preflight,settings,routing,phases}.js`'s actual, already-built APIs — read in full before citing, never assumed from a module's name. Same class of artifact as `product/verification/flow.md` and `product/delivery/flow.md` — Maestro's own operating knowledge for one phase, read by Maestro and by `onboarding-runner`/`scout-agent` to know their own place in the sequence, never scraped for state.

Onboarding (phase 1, `machine/phases-registry.json`'s `onboarding` entry) is `interactive: true` — the settings interview is a real operator conversation, hosted entirely inside Maestro's own turn (`AskUserQuestion` exists only in the top-level session, `interview.md`'s own "Execution constraint"). It is also the pipeline's **entry** phase — `entry_requires: []`, the only phase with nothing upstream of it — and its own registry entry carries no `exit_checks` at all, a disclosed gap this document's own "Known, disclosed scope limits" section names rather than silently working around (a finding proven in the dev record against an earlier four-file `exit_emits` list, before `handoff.md` joined it: `scaffoldTree`'s genesis step alone writes every `exit_emits` file's path into existence immediately, so file-existence-only checking would call the door complete the instant scaffold finishes — true of all five files today, not fewer). What actually enforces correct sequencing here is this document's own scripted order, held by construction: `onboarding-runner`'s closing `phases.js advance` call, below, never fires until the interview, `settings.js write`, and any mode-specific detour have all genuinely completed — not because a registry check demands it, but because nothing in this document's own sequence calls `advance()` any earlier.

## The tree, as actually built — where each `exit_emit` comes from

## Roster

- `onboarding-runner` (`agents/onboarding-runner.md` — this document's own claims about that seat were checked against it at authoring time; a runtime reader of this document does not read that file, and a bare `agents/` path would resolve inside the operator's project rather than the installed plugin if it tried. Maestro's outbound brief carries the plugin-root-prefixed anchor when a seat needs one) — spawned once, at entry, kept warm and resumed (never respawned) for its own closing dispatch later in the same pass. Owns exactly four mechanical actions: `scaffold.js` (only when Maestro's own `detect()` call found the tree absent), `intake.js`'s two legs (only on `legacy` — the archive leg at (a0), which subsumes the scaffold call, and the harvest leg at (d)), `preflight.js run` (always, with the two capability flags Maestro's brief supplies), and — resumed — generating `handoff.md` plus running its own `phases.js advance` closing call. Never runs the interview, never invents prose, never re-derives a classification Maestro already made.
- `scout-agent` (`agents/scout-agent.md`) — spawned once, only on a `brownfield` classification, at the exact point this document's own mode-routing step (below) places it — never earlier, per `product/brownfield/flow.md`'s own precondition ("Maestro already ran `detect()`... you do not re-run `detect()` yourself").

## Entry — Maestro's own toolset facts, then classification

Two things happen in Maestro's own turn before anything is delegated:

1. **Read its own session facts — two separate probes, named sources, and an honest `unknown`.** `product/onboarding/preflight.md`'s checks 3 and 4 (the Workflow tool, agent teams) are session-introspection facts, not subprocess-checkable ones — "there is no shell command that answers 'is `Workflow` in this session's tool list,' it is a fact the running session reads about itself" (`preflight.md` §3). For every other check in this product, that read happens inside a worker's own turn, about the worker's own toolset. Here it cannot: `onboarding-runner`'s toolset (`Bash, Read, Write`) says nothing about whether *Maestro's* session has `Workflow` or agent teams available, and those are exactly the two facts the report needs. This is the one deliberate exception to "anything that touches disk state, runs a check... is a worker's job" (`maestro.md`'s Do/route boundary) — carved out for the same structural reason `interview.md`'s own `AskUserQuestion` exception is: only the main session knows its own toolset.

   **The Workflow tool's source is the session's own resolved tool-schema block** — the tool definitions actually supplied to this running session, not the static `tools:` frontmatter line, and not `ToolSearch`, which searches *deferred* tools while `Workflow` is a built-in. A `Workflow` definition present in that block is `present`; the block exposed without one is `absent`; a host that does not expose that registry to the session at all is `unknown` — never an inferred absence.

   **Agent-team availability is its own separate probe, never derived from the Workflow result.** `SendMessage` being available does not prove a team window exists, and the two capabilities have no implication in either direction — so Maestro checks the team-enablement flag and the team-spawn surface as their own fact and reports it as its own token. Reading one capability off the other is the specific error this step forbids by name.

   **Each capability travels as a PAIR of tokens**, and `preflight.js run` takes both: the routing token (`--workflow-tool` / `--agent-teams`, strictly `present` or `absent` — the binary every downstream consumer already handles) and the observation token (`--workflow-tool-observed` / `--agent-teams-observed`, `present` / `absent` / `unknown` — what Maestro actually saw). **The `unknown` rule, in full**: an `unknown` observation maps to `absent` for routing, is recorded as `unknown` in `state.json.preflight.capabilities.<cap>.observed` and in the matching `preflight` ledger record via the `--*-observed` flag, and **carries a mandatory operator sentence naming the uncertainty** in step (b)'s report — that this session could not determine the capability, that the build is proceeding as if it were absent, and what that costs. Recording only `present: false` would make a host that refused to answer indistinguishable from one that answered no; routing on a third token would hand every downstream consumer a state it has no branch for. Fail degraded, and say so — a silence I could not break is never rendered as an answer I received.
2. **Classify.** `detect.js`'s `detect <projectRoot>` command — `maestro.md`'s Bash law point 7 carries the invocation form, as it does for every runtime command this document names (this file is plugin payload, so a command stored here would reach Bash with its plugin-root prefix unresolved). One call, once, per onboarding run. Returns `{mode, evidence}`; `mode` is exactly one of `greenfield` / `brownfield` / `legacy` / `resume` / `broken-install` (`detect.js`'s own five-way classification), and `evidence.has_tree` is what tells Maestro whether `onboarding-runner`'s first brief should include a scaffold step or skip it — except on `legacy`, where the brief names the intake leg instead and never a scaffold step of its own ((a0), below, and the reason it cannot be both).

**`broken-install`** routes straight to the operator here, before anything else runs (`product/brownfield/flow.md`'s own "Failure paths" section: "Routed straight to the operator... never scaffolded over, never guessed into either a fresh brownfield scout or a resume") — this document's remaining steps do not apply.

**`legacy`** takes the intake leg at (a0) below, before anything else in this document runs — an earlier Kiln tree is in the exact place this version's tree wants, so nothing can be scaffolded until it has been set aside whole (`product/legacy/flow.md`, which owns what the transaction does; this document owns only where its two legs sit). It is never routed to the operator as a failure and never refused for being old: a shape this version does not speak is a fact about the shape, not a fault of the operator's project.

**`resume`** with `state.json.phase` already past `"onboarding"` never enters this document at all — Maestro's own `resumePoint()` continues from wherever the tree actually is. A `resume` classification with `phase: "onboarding"` still (an interrupted prior onboarding pass) continues through this document's own steps from wherever they left off — every step below is safe to re-enter: `preflight.js run` always writes the LATEST honest result regardless of prior runs, and `interview.md`'s own Step 0 skips the interview entirely once `settings.json` is non-empty and carries a `facilitator` key. No separate resume-path logic exists here beyond that idempotency, by design — the restart-anytime discipline every other flow document in this product holds too.

## The engine

### (a0) The intake leg — `legacy` only, before anything is scaffolded

Skipped entirely on every other mode. On `legacy`, Maestro's first `onboarding-runner` brief names the intake leg instead of a scaffold step: that seat runs intake's own archive command (`agents/onboarding-runner.md`'s Method carries the invocation form, as it does for every runtime command this document names), which sets the earlier tree aside whole inside the new one and scaffolds in its place — one transaction, `product/legacy/flow.md`'s own subject.

**Why it precedes (a) rather than living inside it.** `scaffoldTree` refuses an existing `.kiln/` unless `force` is set, and `force` deletes the whole directory before rebuilding — the same refuse-or-destroy semantics `product/brownfield/flow.md` gives as the structural reason scaffold precedes scout. An earlier Kiln tree occupies exactly the path the new tree wants, so the set-aside has to happen first or not at all. **The scaffold is a step inside that transaction**, not a separate call afterwards: `onboarding-runner`'s usual scaffold step is subsumed here, never run twice, and `force` is never passed by this leg or any other — it would destroy precisely what intake exists to preserve.

`onboarding-runner`'s envelope reports the transaction's own result — the archive path, the tier, and the marker it retired. A throw here is a `blocked` envelope naming the exact refusal and the paths involved; it is never retried with `force`, and nothing further in this document runs until the operator has ruled.

### (a) Scaffold + preflight — one `onboarding-runner` dispatch

Maestro spawns `onboarding-runner`, brief naming `<projectRoot>` directly, stating whether to scaffold (per `evidence.has_tree` from Entry step 2's `detect()` call, above — on `legacy` the brief names (a0)'s intake leg in its place, and the scaffold happens inside that transaction) and carrying the two literal capability tokens from Entry step 1. `onboarding-runner` runs `scaffold.js` (only if told to) then unconditionally `preflight.js run <projectRoot> --workflow-tool <present|absent> --agent-teams <present|absent> --workflow-tool-observed <present|absent|unknown> --agent-teams-observed <present|absent|unknown>` — the flag forms and their prefixed invocations live in `agents/onboarding-runner.md`'s own Method section; the four token values come straight from Entry step 1's pairs, passed through, never re-derived by that seat. The five checks, in `preflight.md`'s exact order, real subprocess exit codes via `check-honesty.js`'s `runGate` for the three gate checks (node/codex/git), `kind: "preflight"` ledger records for the two session-fact checks (Workflow tool, agent teams) — writing `state.json.gates[]` and `state.json.preflight` atomically, alongside the matching `ledger.jsonl` records, and printing the resulting `{mode, gates, capabilities, repo}` JSON. `onboarding-runner`'s own envelope reports back; Maestro reads `state.json.preflight` (a small, bounded JSON read — the same Do/route-boundary class as a routing config) rather than re-parsing the worker's own stdout capture.

### (b) Deliver the report — verbatim, never-buried

Every preflight result reaches the operator plainly, one line each, nothing buried and nothing assumed — `preflight.md`'s own "Report to the operator" section, restated here as this document's own binding order:
1. **The degraded-mode sentence, first, if `state.json.preflight.mode === "degraded-claude-only"`** — the exact sentence `preflight.md` check 2 specifies, verbatim, never paraphrased, said before anything else in onboarding proceeds (never buried after the interview has already started).
2. Node, git, and (if not already covered by 1) Codex results, one line each.
3. **The agent-teams enablement instruction, whenever `state.json.preflight.capabilities.agent_teams.present === false`** — the exact instruction `preflight.md` check 4 specifies verbatim (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, restart may be needed) — a ruled operator-facing trap: preflight must name the flag and the restart caveat, because agent teams ship off by default and a silent absence would read as a missing feature rather than an unset switch. Delivered in this same report, same never-buried rule as the degraded-mode sentence.
4. The Workflow-tool result, one line, noting the plain-Node-scripts-via-Bash fallback when absent.
5. **The intake line, whenever (a0) ran** — what was found, where it was set aside, that nothing in it was deleted, and what is not being carried forward, composed per `product/legacy/flow.md`'s own operator moment. Same never-buried rule as the two above, and for the same reason `preflight.md` gives it: being asked settings questions while unaware that a prior run has just been set aside is a form of burial. The operator hears it here, before the interview, never after. The clauses about what was *kept* are not said here — the harvest that establishes them has not run yet at (b), and `product/legacy/flow.md`'s own line omits any clause whose field is not on disk rather than softening or guessing it; they land at (d), where the record they trace to is written.

This is plain factual reporting, not narration (`maestro.md`'s "Narration" section governs operator-facing *progress* lines grounded in ledger events during the build proper, composed in the one voice `product/voice/kiln.md` fixes; this report is preflight's own contract, quoted, never composed).

### (c) The settings interview — Maestro's own turn, per `interview.md`

Maestro runs every step of `product/onboarding/interview.md` directly, in its own turn (its own "Execution constraint": "No step here is delegated"), Steps 0 through 7 — the re-run skip check, the preset question, the Custom knob panels if chosen, the always-asked telemetry/blocking/plan-review/floor-lock panel (four questions since the operator's own ruling on that panel), and the recap/ledger-event closing steps. **Step 5's persistence — the six-step manual validation dance `interview.md` describes inline (load schema, build picks, read-merge-clamp, write atomically)** — runs as this product's own pinned CLI, never re-implemented a second way (doctrine rule 6):
```
settings.js write <treeRoot> '<json>' --source interview        (form: agents/maestro.md, Bash law point 8)
```
Maestro's sole-caller call, the same pattern `maestro.md`'s Bash law already holds for the delivery engine's own machine-layer calls (point 6) — a small, bounded, judgment-free call, its literal JSON-string argument built the same way point 5's verification calls build theirs: Maestro assembles the picks object plus the `preset` bookkeeping key from the operator's own panel answers (in its own turn, not a worker's — constructing a JSON literal from answers already in hand is not itself a disk-touching or multi-tool-call operation) and passes it as this call's argument. The `--source interview` flag is this exact call's own provenance marker (`machine/src/settings.js`'s `parseArgv`/`write`) — the one thing in this whole product entitled to let a `floor_lock: false` pick land rather than being clamped back to `true`; every other caller of `settings.js write` (or a plain hand-edit of `settings.json` read back later) gets the fail-closed `hand-edit` default instead, per interview.md's own Floor lock question and Step 5 point 4. `settings.js write` validates and floor-clamps through its own existing functions — never a second validation path — atomic-writes `<treeRoot>/settings.json`, and prints the clamped document back; Maestro reads that printed document rather than trusting its own assembled JSON as the final word, since clamping can change values. `settings.js read <treeRoot>` is the same module's read-side counterpart, used by Step 0's own re-run check.

### (d) Mode routing — the scout detour, placed here explicitly

Once the settings interview has closed (`settings.json` real content on disk, the interview's own Step 7 ledger record appended), Maestro routes on the same `mode` step 2 of Entry already classified:

- **`greenfield`** → proceed directly to (e).
- **`brownfield`** → spawn `scout-agent` now, per `product/brownfield/flow.md`'s own "Detection → scaffold → scout, in that exact order" law — detection already happened (Entry, step 2), scaffold already happened ((a), above, via `onboarding-runner`), so this is the one remaining leg. This is the explicit placement `product/brownfield/flow.md` itself named as parked, disclaiming full sequencing authority over it: "This document names the exact detect → scaffold → scout ordering... it does not attempt to author the rest of onboarding's sequencing." **This placement — after the interview, not before it — differs from that document's own provisional sketch** ("onboarding continues exactly as any greenfield run does — the settings interview, then the standard eight-phase sequence," which reads as scout-then-interview): nothing before phase 2 (brainstorm) actually consumes `scout/reuse-map.json`/`scout/constraints.json` (brainstorm is the first and only consumer named in `product/brownfield/flow.md`'s own "Then create all artifacts" section), and the interview's own knob panels are asked identically regardless of onboarding mode — so there is no correctness reason to front-load scout ahead of the interview, and running the mode-invariant steps (preflight, interview) first keeps operator momentum before the bounded-but-real-cost scout pass runs. Maestro waits for `scout-agent`'s envelope (`state: done`, all three `scout/` files on disk, per `scout-agent.md`'s own envelope contract) before proceeding to (e). A `blocked` scout envelope routes to the operator directly (`product/brownfield/flow.md`'s own "Failure paths" section — a fact for the operator to see and decide on, not an agreement pass deadlock).
- **`legacy`** → the harvest leg first: Maestro resumes `onboarding-runner` to run intake's own harvest command against the archive (a0) recorded (again, the invocation form lives in `agents/onboarding-runner.md`'s Method), which copies out what can be carried honestly into `intake/`, writes `intake/report.json` and `intake/report.md`, and appends the one `intake` ledger record — the whole of it `product/legacy/flow.md`'s subject, not this document's. Maestro then says the rest of the intake line (step (b) point 5's deferred half) from the report now on disk, and routes on the same fact any other project routes on: **whenever the project has code, `scout-agent` spawns exactly as the `brownfield` bullet above specifies**, its brief additionally naming `intake/report.json` and `intake/documents/` as inputs to re-derive from, never to trust; when it has none, the run continues to (e) as a greenfield one does. Legacy is brownfield-plus-an-intake-leg when there is code and greenfield-plus-an-intake-leg when there is not — no new phase, no new pipeline shape, and no second scout contract.
- **`resume`** (mid-onboarding re-entry) → proceed to whichever of (a0)–(d) hasn't yet completed, per Entry's own re-entry note. A re-entry always routes back through Entry's own `detect()` call, never by calling a leg of the intake transaction directly: intake's archive leg is a no-op once the tree is already set aside, and the harvest leg completes from wherever it stopped.

### (e) Close — `onboarding-runner`'s resumed dispatch

Maestro resumes `onboarding-runner` (`SendMessage` to its existing transcript, never a fresh spawn — the "Resume, don't respawn" law, `maestro.md`'s "Communication protocol") to run `handoff.js render-onboarding <treeRoot>` (`agents/onboarding-runner.md`'s Method step 3) — the sole other writer of `handoff.md` alongside `handoff-recorder`'s own `write-stop` (a cross-family review finding: a direct `Write`-tool overwrite here, alongside the stop writer's own contained write elsewhere, meant a late door close and a stop could race through two formats and two write mechanisms, only one of which participated in the shared state/ledger lock). The command re-reads `state.json`/`settings.json`/`scout/inventory.json`/`intake/report.json` fresh off disk itself and renders `<treeRoot>/handoff.md` as a mechanical view of whatever it finds there — the phase and settings facts now fully on disk, including scout's own completion fact for a brownfield build and, for a legacy one, an intake section naming the tier, the archive path, and how many files were carried, under the same omit-when-absent rule the scout line already holds: no report on disk, no section. Once it succeeds, `onboarding-runner` runs `phases.js advance <treeRoot> onboarding` as its own closing step. This is the single point in this whole document that actually transitions the project out of onboarding: `advance()` fails closed (throws) on any missing `exit_emits` file, and — because nothing earlier in this sequence calls it — it is never reached with a stale or half-written tree. `onboarding-runner`'s own closing envelope reports the transition; Maestro cites `handoff.md` to the operator, never the envelope's own prose, per its own Operating Loop ("If [a worker's envelope] names an artifact, that artifact is what you cite... not the envelope's own prose").

## Failure paths

**`broken-install`.** Routed to the operator at Entry, before any of (a)–(e) runs. Per `product/brownfield/flow.md`'s own "Failure paths" section: never scaffolded over, never guessed into a resume.

**`onboarding-runner` reports `blocked` at (a0) or at (d)'s harvest leg.** Intake refuses rather than guesses on exactly two classes of fact: a filesystem hazard (a symlinked tree or marker, a path resolving outside the project root, an unreadable directory) and a transaction state it cannot honestly complete (a target archive slot already taken, a destination that would be written through a link). Both name the paths involved and both leave the tree byte-identical — `product/legacy/flow.md`'s own refusal contract. Routed to the operator as a fact to rule on, never retried with `force` and never worked around by scaffolding over the older tree: the whole point of the leg is that nothing in it is lost.

**`onboarding-runner` reports `blocked` at (a).** A scaffold throw (most commonly a stale "tree absent" brief) or a `preflight.js` invocation error is named plainly in its envelope; Maestro does not retry with `--force` or a guessed flag value on its own initiative — this is a Maestro-side brief error to fix, not a worker-side judgment call.

**`scout-agent` reports `blocked` at (d).** Per `product/brownfield/flow.md`'s own "Failure paths" section: a precondition failure, an `inventoryTarget` throw, or a target too sparse for a meaningful pass — routed to the operator directly, the same class of decision a `broken-install` result already routes there, never an agreement pass deadlock (no implementation-judgment disagreement exists here to arbitrate).

**`onboarding-runner` reports `blocked` at (e) — `advance()` throws.** Names exactly which `exit_emits` file `phases.js` considers missing. Given this document's own sequencing, the only realistic cause is a Maestro-side skip earlier in the sequence (e.g., (c) or (d) not actually having completed before (e) was dispatched) — never patched around by fabricating the missing file; re-run the skipped step.

## Known, disclosed scope limits

- **`machine/phases-registry.json`'s `onboarding` entry carries no `exit_checks`.** `scaffoldTree`'s own genesis step writes all five `exit_emits` files' *paths* into existence immediately (`state.json`, `settings.json` as `{}`, `handoff.md` as a stub, `ledger.jsonl`, `routing/active.json`), so a bare file-existence check would call the door complete the instant scaffold finishes — a pre-walk finding from the dev record, still open. This document's own scripted order is what actually prevents a premature `advance()` (step (e) is the only place `advance()` is ever called, and nothing before it in this sequence reaches that step early) — a real guarantee, but an enforced-by-sequencing one, never a machine-checkable one the way `suite-state-green`/`run-bound` checks are for delivery. A semantic `exit_checks` entry for this phase (a `settings-non-empty` check, a `handoff-non-stub` check) would close it properly; `machine/phases-registry.json` is not a file this layer touches, so the gap is named here rather than silently assumed closed — the same honesty convention `product/verification/flow.md`'s and `product/delivery/flow.md`'s own "Known, disclosed scope limits" sections already hold for their own gaps.
- **CLOSED: `machine/` path resolution inside a scaffolded target project.** Two separate findings in the dev record named this as a packaging gap: Maestro (and, by extension, `onboarding-runner`) launches with `cwd` = the target project, but a `node machine/src/<module>.js` call assuming `cwd` = the kiln dev repo would resolve nothing there. The resolution — execution-proven in the dev record: `machine/` ships as plugin payload, addressed by a plugin-root placeholder Claude Code substitutes **by content, in skill and agent component prose only**, into an absolute path before the model ever reads the text — not a shell environment variable a subprocess could fail to inherit, and **not something that resolves in `product/**` payload like this document**. That is why every runtime command this document once stored inline now lives in its executing seat's charter and is cited from here by name: the charters substitute, so their commands resolve correctly regardless of the target project's own `cwd`, and this file carries no executable text that could silently expand to nothing.
- This document cites `preflight.js`'s and `settings.js`'s contracted CLI behavior — the interfaces they were pinned to — never an independent read of their final source. A contract read, not a code review; said here rather than left to look like one.
