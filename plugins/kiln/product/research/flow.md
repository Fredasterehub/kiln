# The Field Desk — how phase 3 actually runs

The field desk is a bounded feasibility and freshness pass over whatever the sketchbook decided: a cache-first sweep that lands `research/index.json` entries, dated topic files, and one chief-authored `research/summary.md` the blueprint reads next. It answers what is known, at its official sources, before anyone plans on top of it.

Binds `agents/maestro.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Communication protocol", §"Verification doctrine") to this one phase transition. Maestro's own operating knowledge — the same class of artifact as maestro.md itself and as `product/brainstorm/flow.md`, read by Maestro and by whichever field desk agents need to know their place in the sequence, never scraped for state: markdown owns meaning, and no script ever reads prose to learn a fact.

The field desk is `interactive: false` in `machine/phases-registry.json` — unlike the sketchbook, no operator dialogue happens inside this phase, so no separate team window buys anything here. Its shape problem is a different one: one long-lived chief holding a scratchpad and dynamically steering a fan-out of workers, width a settings knob (2/3/5) rather than a judgment call in the moment.

## Roster

This flow names two workers: `research-chief` (the phase's sole Maestro-spawned agent, `agents/research-chief.md`) and `research-worker` (the chief's own worker fleet, width N, `agents/research-worker.md`). Routing config `routing/active.json` names their seats `research_chief` and `researcher` respectively — a different key than the spawnable agent's own frontmatter `name:`, the same two-namespace shape `research-chief.md` itself already bridges ("`tier` is `sonnet-5` at `high` effort, per `.kiln/routing/active.json`'s `researcher` seat"): the routing config names the seat, the agent file names the spawn target, and one worker's own prompt is the place that maps between them.

Maestro's own `tools:` frontmatter carries `Agent(kiln:research-chief)` and its roster table carries the matching row (`agents/maestro.md:6`, `agents/maestro.md:70`). `research-worker` never appears there at all, since Maestro never spawns it directly in the primary path (only the fallback path below routes a worker spawn through Maestro).

| Worker | Spawn when |
|---|---|
| `research-chief` | `state.json.phase == "research"` and no chief transcript is already open for this run (fresh spawn) or is open but the chief agent itself is gone (respawn, resume-don't-respawn against the surviving `research/scratchpad.jsonl` — Failure paths below). Maestro spawns it as a plain subagent (never a teammate — no operator dialogue lives in this phase, so agent-teams' isolation machinery buys nothing brainstorm-shaped brings). |
| `research-worker` | Spawned by `research-chief` itself, width N at a time (`settings.json.research_width`, enum `2`/`3`/`5`, default `3` — `machine/settings-schema.json:10-15`), per topic the chief is actively steering — each spawn individually named (`research-chief.md` §"Width & spawning": "give each spawn a distinct, topic-scoped name at spawn time"). **Never spawned by Maestro directly** except in the fallback path below. |

## The five steps

**(a) Verify phase.** Same read as `product/brainstorm/flow.md` step (a): Maestro reads `state.json.phase` itself (Read tool, small bounded file — within the Do/route boundary's explicit carve-out) and confirms `"research"` via `phases.loadRegistry(machine/phases-registry.json)` + the registry's own shape (`machine/src/phases.js`, `currentPhase`). A read, not a judgment call — Maestro never infers phase from file presence or narrative context, only from `state.json`, which is THE resume pointer and the only thing consulted to answer that question.

**(b) Spawn the chief with a mission envelope anchored to the vision pair.** Maestro spawns `research-chief` as a subagent with a complete-but-referential brief — the eight fields `machine/src/validators.js` enforces (maestro.md §"Communication protocol"):
- **outcome**: a cache-first research pass covering the open questions the crystallized vision raises, landed as `research/index.json` entries plus dated topic files plus a chief-authored `research/summary.md` that the blueprint reads next.
- **scope**: whatever the vision pair actually decided — the chief derives its own topic list from vision content; Maestro never hands it a topic list, since deciding what needs researching is research judgment, not orchestration.
- **anchors**: `vision/vision.md` and `vision/decisions.jsonl` — **the vision pair** research's own `entry_requires` names (`machine/phases-registry.json`'s `research` entry). Paths only, never pasted content (maestro.md §"Communication protocol": "anchors (file paths, never pasted content)"). The chief reads `vision/vision.md` directly — markdown owns meaning — and `vision/decisions.jsonl` only through a bounded `projection.projectFile` view (`kinds:["decision"]`), never the raw stream: the same context-hygiene rule that keeps Maestro itself off raw JSONL (maestro.md §"Context hygiene").
- **acceptance**: the registry's own `research` exit_checks, mirrored as the chief's own self-check before it ever reports done (see step (e)) — `research/index.json` non-empty with at least one real entry, `research/scratchpad.jsonl` carrying at least 3 non-genesis records including at least one `"freshness_gate"` record (the cache-first gate's own audit trail), `research/summary.md` written and non-stub.
- **freshness**: cache-first, always — the cache is read before any re-research, and re-verification fires on staleness or on a load-bearing decision, never as reflex token-burning. Before citing or re-deriving anything, the chief calls `research-cache.js`'s `requireFreshOrExplain(index, topic, nowIso, opts)` against the loaded `research/index.json`, passing `opts.loadBearing: true` whenever the architecture decision resting on this subtopic is expensive to get wrong even if the cache looks recent. **The single rule**: the chief consumes the cache directly only when the call reports `fresh:true` AND the subtopic is not load-bearing — `requireFreshOrExplain` itself makes this unambiguous by returning `fresh:false` unconditionally whenever `opts.loadBearing` is `true`, so a load-bearing subtopic always dispatches a re-verification worker regardless of the cached entry's age, and there is never a branch where "fresh" and "load-bearing" both point at consuming the cache. Every call gets a matching `research-cache.js` `recordGateCheck(scratchpadPath, {topic, fresh, reason, load_bearing})` against `research/scratchpad.jsonl` — one gate-check record per brief decision, so the gate's own outcome is auditable on disk rather than only ever asserted in the chief's prose (see "Registry conformance," below).
- **tier**: `routing/active.json`'s `research_chief` seat for the chief itself (`opus-5`, `high` in the current dated config) — read from the dated config, never from memory of a prior one (maestro.md §"Non-negotiable invariants": "Model routing"). The chief tiers its own worker briefs from the same config's `researcher` seat (`sonnet-5`, `high`).
- **return_format**: the standard worker envelope (STATE/RESULT/EVIDENCE/RISKS/ARTIFACT/QUESTION) — ARTIFACT names `research/summary.md` once written, so Maestro cites that file to the operator rather than the envelope's own prose (maestro.md §"Verification doctrine": "If it names an artifact, that artifact is what you cite... not the envelope's own prose").
- **stop_condition**: the chief reports `done` only once its own three acceptance checks (above) all pass and it has called `phases.advance()` itself as its closing action — the same "the worker that closes out a phase's `exit_emits` artifacts is the one whose brief includes running `phases.js`'s `advance()` as its closing step" rule maestro.md's own §"Phase sequencing" already states for whichever worker closes a phase.

**(c) The chief runs the width-N worker fleet.** The shape — one chief owning a scratchpad, dynamically steering workers, width a settings knob — is a nesting relationship, never a Maestro-mediated fan-out, by design: Maestro never touches research content (below), so it cannot be the one deciding what each worker researches or when the chief redirects one mid-task.

*PRIMARY — the chief spawns its own workers.* By default, a Claude Code subagent can spawn subagents of its own up to three layers below the main conversation — the documented default depth, 3, since v2.1.219. Maestro (main, depth 0) → `research-chief` (depth 1) → `research-worker` (depth 2) fits comfortably inside it, so on any install at that version or later this is the path that runs. `research-chief.md`'s own `tools:` frontmatter carries `Agent(kiln:research-worker)` unconditionally, confirming it: the chief reads `settings.json.research_width` itself at the start of each dispatch round — never a value Maestro forwarded, since every knob lives as a key in the persisted settings file and the interview is a curated front door, never a cage — and holds that many `research-worker` subagents active at once, each individually named and with its own complete-but-referential brief (one topic, one freshness requirement, one acceptance check — the same eight-field shape the chief's own brief used, scaled down to a single topic). A worker's result returns to the chief directly (subagents report to whoever spawned them — the plain "Agent tool" mechanism, not agent-teams' mailbox), and the chief folds each result into its own `research/scratchpad.jsonl` steering log and, when the topic is settled, a `research-cache.js` `upsertEntry` call against `research/index.json`.

*FALLBACK — nested spawning unavailable to the chief.* This is a version/config-dependent platform constraint, not a hypothetical: nested spawning requires both that the chief's own `tools:` frontmatter carries `Agent` and that the effective spawn-depth limit (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`) leaves room at depth 1. Versions v2.1.217–v2.1.218 defaulted that limit to 1, raised to 3 only from v2.1.219 — on such an install, or one where an operator or packaged config has explicitly lowered the env var, Claude Code withholds the `Agent` tool from every subagent at the depth limit, so a depth-1 chief has no `Agent` tool to spawn `research-worker` with at all, no matter what its frontmatter declares. **The specified fallback is chief-authored briefs executed via Maestro-mediated spawns — briefs unchanged.** The chief would still decide width, topics, and each worker's full brief exactly as in the primary path (nothing about brief content changes); it would hand each brief to Maestro via `SendMessage` instead of calling `Agent` itself. Maestro would spawn the `research-worker` subagent with that brief verbatim — a mechanical pass-through, not authorship (maestro.md §"Do/route boundary" still applies: Maestro reads/relays bounded material, it does not write research content). Because Maestro would be the one holding a live `Agent` tool at depth 0, the worker's result would return to *Maestro*, not the chief (the same "subagent... reports results back" mechanism from the primary path — the caller changes, not the mechanism); Maestro would relay that envelope back to the chief via `SendMessage`, unread and unacted-on beyond an optional structural `validators.validateEnvelope` shape check, never interpreting RESULT/EVIDENCE content — a pure bounced relay, preserving "Maestro stays out of research content" (below) even though it pressed the `Agent` button. **This branch is specified, not wired**: `research-chief.md` grants `Agent(kiln:research-worker)` unconditionally and its "Width & spawning" section assumes the primary path throughout, with no fallback logic — so on an install whose depth limit withholds `Agent` from a depth-1 subagent, the chief has no branch to take and the phase stalls at its first dispatch rather than degrading into the relay above. This section is the contract that branch would implement. The primary path is unaffected, and it is the path a current Claude Code version takes.

**(d) Maestro stays out of research content.** In both paths, Maestro's own turn after step (b) is short: spawn (primary) or relay (fallback), then go idle — it never reads `research/scratchpad.jsonl`, `research/index.json`, or any dated topic file itself, and it never narrates research progress mid-phase (nothing to narrate from that traces to a record it's allowed to read — maestro.md §"Narration": "if you don't have that record, you don't have a line yet"). Every research artifact this phase produces is chief-owned and chief-consumed; Maestro consumes only the chief's own envelopes, exactly as it consumes the crystallizer's in `product/brainstorm/flow.md` step (e) — an outcome, an artifact pointer, nothing about the content in between.

**(e) Verify exit artifacts, advance, and report.** The chief's own closing step (not Maestro's tool call, per maestro.md's Do/route boundary) runs its four acceptance checks (step (b), above) before calling `phases.advance()`:
1. `research/index.json` carries at least one real entry (`research-cache.js`'s `loadIndex` + a non-empty `entries` array) — the chief's own write, self-verified before it ever relies on the registry's own weaker `file-nonempty` check to catch a regression.
2. `research/scratchpad.jsonl`'s tail (a bounded `projection.projectFile` view, never a raw read even by the chief writing it) shows at least 3 non-genesis records — real steering, not a rubber-stamped empty phase.
3. `research/scratchpad.jsonl` carries at least one `"freshness_gate"` record — the cache-first gate ran and its outcome was logged for at least one brief decision, not merely claimed in prose.
4. `research/summary.md` exists and is non-stub — the chief's own recap, the artifact its envelope names and architecture's `entry_requires` now lists alongside `research/index.json` and `research/scratchpad.jsonl`.

Only if all four pass does the chief call `phases.advance(treeRoot, registry, statePath, ledgerPath)` (`machine/src/phases.js`), which independently re-checks the registry's own `exit_emits` (`research/index.json`, `research/scratchpad.jsonl`, `research/summary.md` — all three must exist) **and** the registry's `exit_checks` — `file-nonempty` on `research/index.json`, `jsonl-min-records:3` on `research/scratchpad.jsonl`, `jsonl-has-kind:freshness_gate` on `research/scratchpad.jsonl`, and `file-nonempty` on `research/summary.md` (see "Registry conformance," below). This does not replace the chief's own script-side checks above — a worker that already knows what it just wrote should still verify that directly, cheaply, before ever calling `advance()` — it means the machine layer itself now independently enforces the same facts at the one call every phase transition must pass through, so a caller who skipped or mis-ran the chief's own checks (a bug, a different future worker, a hand-rolled script) cannot advance past `research` on file-existence alone. Both new machine-layer checks are deliberately presence-of-evidence, not truth-of-evidence: `jsonl-has-kind:freshness_gate` proves a gate record exists, never that its `fresh`/`reason` decision was itself correct, and `file-nonempty` on `research/summary.md` proves the file has content, never that the content clears the chief's own stricter "non-stub" bar (step 4, above) — the machine boundary stays honest about exactly what it can and cannot verify, the same way `jsonl-min-records` never claimed to judge the quality of what was recorded.

The chief reports back to Maestro via the standard worker envelope; Maestro's Verification doctrine applies exactly as written — it "never report[s] a gate green from a worker's prose alone," it cites the `phase-transition` ledger event `phases.advance()` just wrote (`ledger.jsonl`, `kind: "phase-transition", correlation_id: "architecture"`) as the checkable evidence, then narrates the boundary — the field desk closing, the blueprint opening — to the operator in Kiln's own first person (`product/voice/kiln.md`, loaded at the prefixed path `agents/maestro.md`'s Narration section anchors, never composed by Maestro itself), citing `research/summary.md` as the artifact (per the chief's ARTIFACT field, step (b)) — never the envelope's own RESULT prose.

## Registry conformance

`machine/phases-registry.json`'s `research` entry, as actually built:

```json
"exit_emits": ["research/index.json", "research/scratchpad.jsonl", "research/summary.md"],
"exit_checks": [
  { "file": "research/index.json", "check": "file-nonempty" },
  { "file": "research/scratchpad.jsonl", "check": "jsonl-min-records:3" },
  { "file": "research/scratchpad.jsonl", "check": "jsonl-has-kind:freshness_gate" },
  { "file": "research/summary.md", "check": "file-nonempty" }
]
```

`research/summary.md` is a **deliberate extension beyond the bare `research/` cache tree** of `index.json`, `scratchpad.jsonl`, and dated `<topic>-<date>.md` files. It exists by the same logic the sketchbook applies to `vision/vision.md`: the blueprint needs one chief-authored recap to read, never a raw cache index plus a steering log it would have to interpret itself — the same "crystallize the work into one artifact the next phase reads" shape, scoped to the field desk. `research/index.json`'s **actual** "at least one real entry" bar is enforced by the chief's own step-(e) self-check, not by a machine-layer check kind — `file-nonempty` is a weaker, cheaper belt to `phases.advance()`'s suspenders, exactly the same relationship `jsonl-min-records:1` on `vision/decisions.jsonl` has to the crystallizer's own richer self-check in `product/brainstorm/flow.md` step (e). `research/summary.md`'s `file-nonempty` check is the same belt-to-suspenders relationship one level further: it proves the file exists and has content, never that the content clears the chief's own stricter "non-stub" bar (step (e), point 4, above) — substance beyond non-emptiness stays the chief's own attested responsibility, not something the machine layer can or claims to verify (the machine boundary is honest about presence-of-evidence, never truth-of-evidence).

`jsonl-has-kind:<kind>` is a `phases.js` `EXIT_CHECK_KINDS` entry: at least one record whose `kind` matches `<kind>` exists in the named JSONL file (genesis records never match, since a real gate kind like `"freshness_gate"` is never the scaffold-time seed's own kind). Used here as `jsonl-has-kind:freshness_gate` on `research/scratchpad.jsonl` to prove the cache-first gate (`research-cache.js`'s `requireFreshOrExplain` + `recordGateCheck`, step (b) "freshness," above) actually ran and logged at least one decision before the phase closed. Without it, cache-first and the load-bearing exception would be prompt law only, with no machine-checkable trace that either ever fired. Like every other `exit_checks` kind, this is presence-of-evidence, not truth-of-evidence: it proves a gate record exists, never that its `fresh`/`reason` decision was itself correct — that remains the chief's own attested call, the same boundary `jsonl-min-records` and `file-nonempty` already draw.

Because `research/summary.md` is now a `research`-phase exit artifact, every downstream phase's `entry_requires` that already listed `research/index.json` + `research/scratchpad.jsonl` (`architecture`, `plan_gate`, `implementation`, `verification`, `delivery`) now lists `research/summary.md` alongside them too — the same accumulate-forward shape every other phase's `entry_requires` already follows (each phase requires everything every earlier phase emitted).

**Why `research/summary.md` is undated.** A phase-level crystallization is a single, overwritten-in-place artifact, not an accumulating dated cache entry, so it does not take the `<topic>-<date>.md` naming its cache siblings use — the same shape `vision/vision.md` holds.

**One writer for the index.** `research/index.json` is written through `research-cache.js`'s `upsertEntry` and nowhere else, in that module's own shape (`{schema_version:1, entries:[]}`, entries `{topic, path, date, sources}` — `machine/src/research-cache.js`). A parallel hand-rolled `atomic-json.js` `writeAtomic` read-modify-write against any other shape would produce a file `research-cache.js`'s own `loadIndex` rejects on the very next read — a resumed chief included (doctrine rule 6, no redundant enforcement over one file).

## Failure paths

**Worker dies mid-topic.** A `research-worker` never writes `research/scratchpad.jsonl` or `research/index.json` itself — only the chief does: the scratchpad is the chief researcher's alone, never shared-written by workers (`research-worker.md` itself: "never touch `research/index.json`... or `research/scratchpad.jsonl`... those are research-chief's alone"). A worker therefore holds no state the chief doesn't already have: its brief (one topic, one freshness requirement, one acceptance check) is the complete recoverable spec, and briefs are re-issuable by design. The chief simply re-dispatches the same brief to a fresh `research-worker` — primary path via its own `Agent` call, fallback path (once implemented) via another `SendMessage` to Maestro — never treating a dead worker as lost research, since nothing about that worker's assignment lived anywhere but the brief itself.

**Chief dies mid-phase.** `research/scratchpad.jsonl` is the chief's durable memory — `jsonl.js`'s single-writer, append-only law means the last successfully-appended record survives on disk regardless of what killed the chief's process. Maestro's `resumePoint()` (or an operator-triggered "resume research") re-spawns `research-chief` fresh, but per maestro.md's "Resume, don't respawn" the *first* thing its brief does is read the existing `research/scratchpad.jsonl` tail (a bounded `projection.projectFile` view, `lastN` records) and the current `research/index.json` before dispatching anything new — cache-first applies reflexively to the chief's own prior work, not only to future re-research: a topic `research/index.json` already carries a fresh entry for is treated as closed, and the chief resumes only what the scratchpad shows as still open. This never starts a second, competing scratchpad — `jsonl.js`'s single-writer lock additionally prevents two chief *processes* from corrupting the stream even if a resume briefly overlaps a still-alive chief.

**Width change mid-phase (allowed, logged).** `settings.json.research_width` is not read once and cached — the chief re-reads it at the start of every dispatch round (step (c)), so an operator or agreement-pass-mediated change to the knob mid-phase (e.g., cost ceiling pressure, or a line of research not converging) takes effect on the *next* round without restarting the phase. `research-chief.md`'s existing `"steer"` scratchpad-record kind (`kind: "steer"`, payload `{decision, topic, reason}`) already covers a width reallocation between subtopics with a topic-scoped reason; a change to the knob's own value itself — as opposed to how existing width is allocated — is the same idea one level up: the chief appends a scratchpad record naming the change (old/new width, and why if known) before acting on it — logged, always — so a later reader of the scratchpad tail (a resumed chief, an operator asking what happened) sees the width knob's own history as part of the steering log, not as a silent behavior change. No machine-layer change is needed for this — `settings.json` is already a live-editable file any reader may re-read at any time, and `stream.appendRecord`'s `kind` field is a free-form string per stream (`machine/src/stream.js`), so no registry or validator change is required to log it.
