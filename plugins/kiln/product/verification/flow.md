# Verification flow — how the hundred eyes runs

Binds `agents/maestro.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Bash, narrowly" point 5, §"Communication protocol", §"Verification doctrine", §"Blocker ladder → agreement pass") to the product law's verification architecture (read verbatim: two test families, criteria register, the suite decides "done", model judgment never gates, flake quarantine re-run-once, the failing-first dance, the post-green discovery agent, the light security lane, verification-floor-never-scales-down) and its fix-loop cap (2 passes per same/similar problem → agreement pass), to the standing tree law (the `verification/` shape — corrected against the actual build below), to the adopted verification mechanics this phase's own machinery implements, and to `machine/src/{verification,quarantine,check-honesty,phases}.js`'s actual, already-built APIs. Same class of artifact as `product/architecture/flow.md` and `product/implementation/flow.md` — Maestro's own operating knowledge for one phase, read by Maestro and by whichever verification-phase agents need to know their place in the sequence, never scraped for state: a script reads records, never prose.

The hundred eyes (phase 7, `machine/phases-registry.json`'s `verification` entry) is `interactive: false` — no operator judgment is required to run it; every escalation this flow names routes through the blocker ladder (`maestro.md`'s own section, unchanged here) and, beyond that, the pipeline-wide agreement pass default, never a hosted operator conversation mid-pass.

## Fix-pass revision (post-independent-review)

An independent cross-family review of this phase's first build — verdict **REVISE-BLOCKING**, soundness tag `CURRENT-RUN-COMPLETENESS-UNBOUND`, execution-proven in the dev record — found the suite-state verdict was not actually bound to a complete, current, evidenced run: a nonexistent run, a partial run, and a stale (superseded) run could all compute green. This revision closes every one of those gaps at the machine layer and updates this document to match. The corrected, actual tree — including the removal of the never-live `flakes.jsonl` legacy artifact the prior tree sketch carried — is below.

## The corrected tree

The standing tree law originally sketched quarantine state as a `flakes.jsonl` event-history stream. The actual built machinery (`machine/src/quarantine.js`) instead keeps it as `verification/quarantine.json` — an atomically-rewritten JSON *document* (`{schema_version, entries:[{journey_id, since_run, reason, history}]}`), not an append-only stream — because the flake protocol's own question ("is this journey CURRENTLY tracked, and what's its live decision?") is a snapshot question, not a history-of-events one. `flakes.jsonl` itself is **retired as of this revision**: `machine/src/scaffold.js` no longer seeds it, `machine/phases-registry.json`'s `verification` `exit_emits` and `delivery` `entry_requires` no longer name it, and every scenario fixture that embedded the old registry shape has been updated to match — a prior build carried it forward as a disclosed-but-inert legacy artifact; this one removes the artifact rather than continuing to disclose around it. The corrected, actual tree this phase owns:

- `discovery-agent` (`agents/discovery-agent.md`, sonnet-5 high) and `security-scanner` (`agents/security-scanner.md`, sonnet-5 medium) — the post-green parallel lane, step (e). Both are now in `maestro.md`'s `tools:` Agent allowlist and roster table (this revision closes the prior build's disclosed gap on exactly this point — the two agents existed but Maestro could not spawn them).

**Disclosed gap, named plainly**: nothing in this build charters a dedicated "run the already-authored suite" worker seat. `machine/src/verification.js`'s core functions (`assembleSuite`, `orderRun`, `startRun`, `recordRun`, `computeSuiteState`, `recordAffected`) are pure/self-contained over their own arguments — none of them reads `architecture/criteria-register.json`, `verification/journeys.json`, or `verification/affected-map.json` from disk on its own; every one of those is a caller-supplied argument (or, for `recordAffected`, a caller-supplied `entries` list the function itself validates and writes). `runJourney` closes the *execution* half of the gap by wiring `check-honesty.js`'s `runGate` (the one sanctioned command-execution-plus-ledger-evidence mechanism, never a second one) directly into a single per-journey execute-and-record call. This is enough for **Maestro's own narrowly-scoped Bash** (`maestro.md` point 5) to drive the whole failing-first loop directly, the identical way it already drives `milestones.js`'s create/record-chunk/close. `recordAffected` (this revision's own addition) closes the remaining writer gap the prior build left open: `verification/affected-map.json` no longer depends on an unnamed worker's own generic `atomicJson.writeAtomic` call — `verification.js` is now its sole, validating, sanctioned writer, and the milestone-designer/implementer flow's chunk-green step is where each chunk's own affected journeys are fed into it (`product/implementation/flow.md`'s chunk lifecycle; each `chunk-green` for a chunk that touches journey scripts or their underlying code calls `record-affected` for the journeys that chunk's own diff affects).

## Machine layer (as actually built, this fix-pass revision)

- `machine/src/verification.js`:
  - `assembleSuite(treeRoot, criteriaRegister, journeysIndex)` — pure; `{ok, errors, journeys}`. Fails closed on a malformed criteria register itself (`validators.validateCriteriaRegister` — a duplicate criterion id, a missing required field), the criterion↔journey 1:1 mapping (missing/duplicate/orphan), and — **this revision's own addition** — an unsafe `script_path`: only a relative, contained path (no absolute paths, no `..`/`.` segments) drawn from an allowlisted charset (letters, digits, `.`, `_`, `-`, `/`; no shell metacharacters of any kind) is accepted. A `script_path` is later interpolated into a shell command by this document's own harness-to-cmd derivation (below), so this validation runs BEFORE that derivation ever happens, closing the class of attack structurally rather than only at execution time.
  - `orderRun(previousResults, affectedMap, allJourneys)` — pure; returns `allJourneys` reordered: previously-failed first, then affected, then the rest. **This revision's own addition**: only an affected-map entry whose `status` is exactly `"pending"` (never `"green"` or `"quarantined"`) is treated as affected — a journey the map itself already marks resolved no longer re-prioritizes. A non-null `affectedMap` is validated via `validators.validateAffectedMap` and rejected (thrown) if malformed, rather than silently degrading to "no affected entries"; a `null`/`undefined` `affectedMap` (the very first pass, before the file exists) is still tolerated as empty.
  - `startRun(treeRoot, runId, suite)` — **new this revision**. The sole writer of a run's own leading `"run-start"` record and of `verification/runs-index.json`'s append-only ordering. Binds `runId` to `digestSuite(suite)` — a deterministic, order-independent digest of the assembled suite's own journey identities — and enforces monotonic run identity: a `runId` already present in `runs-index.json`, or one whose own `runs/<run-id>.jsonl` already carries records, refuses to start again. This is the machine-owned "current run" identity the "suite-state-green" exit check (below) cross-verifies against.
  - `recordRun(treeRoot, runId, results, ledgerPath, opts)` — the sole writer of `runs/<run-id>.jsonl`'s per-journey records. Every result MUST carry a non-empty `gate_id` AND — **this revision's own tightening, closing a BLOCKING finding** — a matching ledger record (`kind: "gate"`, this exact `gate_id`, a present `exit_code`) proving that gate actually ran; a caller-attested "pass" with no execution behind it is refused outright, not merely logged as such. `opts.unverifiedImport` (default `false`) is a documented escape hatch for scenario/mock use ONLY: it skips the ledger check and stamps the record `unverified: true`, which `computeSuiteState` (below) then treats as a failure unless its OWN caller opts into the symmetric `opts.allowUnverified`. Production callers — `runJourney`, and therefore Maestro's own `record-journey-run` loop — never set either flag; both exist for the deterministic replay fixtures in the dev record and nothing else.
  - `computeSuiteState(treeRoot, runId, quarantine, suite, opts)` — the sole writer of `suite-state.json`. **`suite` — the assembled journey universe from step (a) — is now a REQUIRED argument**, closing the prior build's central defect: green is no longer whatever the run's own records happen to contain, it is EVERY journey in `suite` either decided-quarantined or backed by exactly one verified, current-run passing record. A missing record (`"no-result"`), an ambiguous duplicate (`"duplicate-result"`), an unverified one (`"unverified-result"`, unless `opts.allowUnverified`), a malformed run stream — parse errors or header violations anywhere in it (`"malformed-run-stream"`, applied to every non-quarantined journey at once, fail-closed) — or a run whose own `"run-start"` record names a different suite digest than the `suite` this call was given (`"suite-digest-mismatch"`) are all red, with the reason recorded per-journey in the returned/persisted `reasons` map. Computing for a `runId` never registered via `startRun` throws (a caller defect, not a legitimate verdict — "was this run ever actually started" is a yes/no protocol question, not a shade of red). `run_seq` and `suite_digest` are recorded into `suite-state.json` alongside `status`/`passing`/`failing`/`reasons`/`quarantined` — the same facts the "suite-state-green" exit check (below) needs to verify currency without duplicating this module's own run-lookup logic there.
  - `recordAffected(treeRoot, entries)` — **new this revision**. The sole sanctioned writer of `verification/affected-map.json`; validates the assembled document via `validators.validateAffectedMap` before it ever reaches disk, and stamps `generated_at` itself (never caller-supplied).
  - `runJourney(treeRoot, runId, journeyId, cmd, ledgerPath)` — runs one journey's reporter-flagged command through `runGate`, derives `status` from the real exit code, and calls `recordRun` with the one-element result, passing the SAME `ledgerPath` through so `recordRun`'s own evidence-binding check always finds the record `runGate` just wrote. `gate_id` is deterministic as `journey-<journeyId>-<runId>`, so the flake protocol's re-run-under-a-new-runId never collides with the original attempt's ledger record.
  - CLI: `verification.js {assemble-suite <treeRoot> <criteriaRegisterJson> <journeysIndexJson> | order-run <previousResultsJson> <affectedMapJson> <allJourneysJson> | start-run <treeRoot> <runId> <suiteJson> | record-run <treeRoot> <runId> <resultsJson> <ledgerPath> [--unverified-import] | compute-suite-state <treeRoot> <runId> <quarantineJson> <suiteJson> [--allow-unverified] | record-affected <treeRoot> <entriesJson> | record-journey-run <treeRoot> <runId> <journeyId> <cmd> <ledgerPath>}` — every JSON-shaped argument a literal JSON string, the same convention `milestones.js record-chunk <milestoneId> <jsonRecord>` already uses.
- `machine/src/quarantine.js`:
  - `decideFlake(history)` — pure; **this revision's own tightening**: requires an array of EXACTLY 2 `{outcome, run_id}` objects — never a bare outcome string, never an open-ended trailing window — and the two `run_id`s MUST be distinct (a verdict decided over the same run counted twice is not a re-run at all, and throws). All-fail → `"fix-task"`; all-pass → `"clear"`; mixed → `"quarantine"`.
  - `recordOutcome(quarantinePath, journeyId, outcome, opts)` — `opts.runId` is now REQUIRED (throws otherwise); a re-run under the SAME `runId` as the tracked entry's first outcome is refused. A journey already carrying a DECIDED entry (`history.length === 2`, a `"quarantine"` verdict already persisted) refuses a THIRD `recordOutcome` call outright — `release()` (the repaired path) is now the ONLY sanctioned way to reopen tracking for it; the prior build's "clears organically after two more consecutive passes" narrative is superseded by this machine-enforced refusal and is no longer how quarantine clearing works. Any call that actually mutates `quarantine.json` marks a persisted `suite-state.json` `status: "stale"` (a non-destructive rewrite, not a delete — it fails the exact same "status !== green" branch the exit check already had) so a green snapshot computed before the mutation can never be consumed as if it still reflected current quarantine membership.
  - `release(quarantinePath, journeyId)` — explicit administrative removal (the "repaired, right after a fix's `chunk-green` lands" path), and the sanctioned way to reopen a DECIDED entry for further tracking. Also marks a persisted `suite-state.json` stale when it actually removes an entry.
  - `capTracker(treeRoot)` — `{recordAttempt(problemKey), countFor(problemKey), atCap(problemKey), checkAndRecord(problemKey)}`, backed by `verification/fix-attempts.jsonl`; `FIX_LOOP_CAP = 2`. **`checkAndRecord` is new this revision** — the atomic combined operation: it checks the cap BEFORE recording, refusing (`{allowed: false, agreement_pass_required: true}`) rather than letting a caller record a third attempt in the window between a separate `atCap` check and its own `recordAttempt` call. Prefer it over the separate two-call sequence. Note, honestly: `problemKey` identity ("is this the same/similar problem as a prior attempt") remains caller judgment — a semantic boundary the machine cannot itself draw. Two failures the caller judges to share a root cause must be given the SAME `problemKey` for the cap to bind them together; nothing here can verify that judgment was made honestly, and a caller that mints a fresh key per attempt resets the count. This is a disclosed, load-bearing limit of the mechanism, not an oversight.
  - CLI: `quarantine.js {decide-flake <historyJson> | record-outcome <quarantinePath> <journeyId> <outcome> --run-id X [--reason Y] | release <quarantinePath> <journeyId> | cap-record-attempt <treeRoot> <problemKey> | cap-at-cap <treeRoot> <problemKey> | cap-check-and-record <treeRoot> <problemKey>}` — the cap commands curry `capTracker`'s factory shape into flat commands, since a factory has no direct CLI shape of its own.
- `machine/src/check-honesty.js`'s `runGate({gateId, cmd, ledgerPath})` — unchanged, the execution-evidence law this whole phase (via `runJourney`, above) and `security-scanner.md`'s own scan step both route every real command execution through, never a second one.
- `machine/src/phases.js`'s `EXIT_CHECK_KINDS['suite-state-green']` — reads `verification/suite-state.json`, requires a non-empty `run_id` string and `status === "green"` (a `"stale"` status — quarantine.js's own post-mutation marker — fails this the same way any other non-`"green"` status does), then — **this revision's own addition, closing the "old-green vs current-red" BLOCKING finding** — reads the sibling `verification/runs-index.json` and requires the persisted `run_id` to equal that index's own LATEST entry. A run that computed green honestly, but has since been superseded by a newer `startRun` call, is rejected here as stale — currency is verified structurally, never assumed from a bare `status === "green"` read.

## journeys.json provenance — the one addendum to implementation's own flow

`assembleSuite`'s `journeysIndex` argument (`{schema_version:1, journeys:[{journey_id, criterion_id, script_path, harness, added_in_milestone}]}`) has to come from *somewhere* before the hundred eyes ever runs `assemble-suite` — and nothing in `machine/src/*.js` derives it automatically from milestone metadata (a milestone's own `chunks.jsonl` `chunk-journeys` record, per `product/implementation/flow.md` step (d).3, carries only `{chunk_id, journey_ids}` — no `script_path`/`harness`/`criterion_id`). This flow document is the canonical source for the missing link: **the same JIT-authoring step that logs a chunk's `chunk-journeys` bookkeeping record also appends one entry per authored `journey_id` directly to `verification/journeys.json`** (`atomicJson.writeAtomic`, read-current-array-append-write — the file may not exist yet on the very first journey authored in the build; the writer creates it fresh with `{schema_version:1, journeys:[]}` as its own starting point), in the exact shape `assembleSuite` expects and in a `script_path` that already satisfies `assembleSuite`'s own containment/charset floor (a relative, repo-contained path — the authoring step never has reason to produce anything else). One JIT-authoring action produces both records — the audit trail (`chunks.jsonl`) and the assemblable catalog entry (`journeys.json`) — never two disconnected writers of the same fact. By the time the hundred eyes is entered (`milestones-all-green` having already closed the anvil), `journeys.json` already reflects every milestone's own authored journeys; this phase only ever cross-checks it against `architecture/criteria-register.json`, per the law's "phase 7 assembles, never writes."

Each chunk's own `chunk-green` step (`product/implementation/flow.md`) is also this build's named producer for `verification/affected-map.json`'s entries: for every journey a chunk's diff touches (its own authored journeys, or an existing journey whose underlying code the chunk modified), the chunk-green step calls `verification.js`'s `record-affected <treeRoot> '<entriesJson>'` (Maestro's own call, invocation form in `agents/maestro.md`'s Bash law point 5) with that journey's own `{journey_id, affected_by: [<chunk_id or milestone_id>], status: "pending"}` entry — `recordAffected` reads nothing itself, so the calling step is responsible for merging against whatever `affected-map.json` already holds (read-current, append/update-by-`journey_id`, write) before calling it, the same read-then-write discipline `journeys.json`'s own writer already follows above.

## The engine

Every `verification.js` and `quarantine.js` call named below is Maestro's own, and the runtime invocation form for all of them — the full `node "<plugin root>/machine/src/<module>.js" ...` shape — lives in `agents/maestro.md`'s Bash law point 5, not here. This file is plugin payload: the plugin-root placeholder does not substitute in it, so a command stored here would reach Bash with that prefix expanded to nothing — a cross-family review finding, execution-proven in the dev record. What this document owns is the protocol — which call runs when, against what, and what its result means — with subcommands and arguments named exactly as the CLI takes them.

### (a) Entry — `assembleSuite`, fail-closed

Maestro reads `architecture/criteria-register.json` and `verification/journeys.json` directly (small, bounded JSON — within its Do/route boundary, the same class of read a routing config already gets), then calls `verification.js`'s `assemble-suite <treeRoot> '<criteriaRegisterJson>' '<journeysIndexJson>'`. `assembleSuite` fails closed (`ok: false`) on:

- a malformed criteria register itself — `validators.validateCriteriaRegister` runs first: duplicate criterion ids, missing required fields, an empty register.
- **missing** — a register criterion with zero matching journey entries (an ACR the architecture phase promised but implementation never actually authored a journey for).
- **duplicate** — a criterion with two-or-more journey entries, or two journeys sharing one `journey_id`.
- **orphan** — a journey entry naming a `criterion_id` the register doesn't have (a journey authored against a criterion architecture never defined, or one whose id drifted).
- a malformed journey entry (empty `script_path`, an unsafe/uncontained `script_path`, an unrecognized `harness`).

Every one of these means the architecture-time promise (`criteria-register.json`, digest-frozen at the plan gate) and the real, shipped implementation have structurally drifted apart — **this climbs the blocker ladder exactly like any other implementation-phase failure** (`maestro.md`'s "Blocker ladder → agreement pass": one retry with a provably distinct approach — e.g. re-deriving `journeys.json` if a genuinely missing entry was simply never appended — is normal; a second distinct failure escalates to `agreement-pass`, never a silent skip or an invented placeholder journey). A clean `{ok: true, journeys}` result is this pass's fixed universe — the SAME array is now threaded through every remaining step below (`orderRun`'s `allJourneys`, `startRun`/`computeSuiteState`'s `suite`) as the one authoritative suite this pass is bound to.

### (b) The failing-first dance — `startRun` + `orderRun` + `runJourney` + `computeSuiteState`

Maestro reads `verification/suite-state.json` (absent on this phase's very first pass — treated as no prior failures) for its own `failing` array, and `verification/affected-map.json` (absent on the very first pass too — treated as `{entries: []}`) for its `"pending"`-status entries, then calls `order-run '<previousResultsJson>' '<affectedMapJson>' '<allJourneysJson>'` — `previousResultsJson` is a minimal array Maestro constructs itself, one `{journey_id, status: "fail", duration_ms: 0, gate_id: "prior"}` entry per id in the prior `failing` list. `orderRun` returns the assembled `journeys` from step (a), reordered: previously-failing first, then `"pending"`-status affected, then the rest — stably, deterministically. **This IS, by construction, "one full green pass"**: `orderRun` always returns the *complete* journey set, never a subset.

Before running anything, Maestro calls `start-run <treeRoot> <runId> '<suiteJson>'` — `runId` a fresh, never-before-used identifier (e.g. a timestamp or monotonic counter Maestro's own brief tracks) and `suiteJson` the exact `journeys` array from step (a). This binds the run to the suite's own digest and registers it in `verification/runs-index.json` BEFORE any journey executes — the machine-owned "current run" fact `compute-suite-state`'s own currency check (below) and the phase-exit `suite-state-green` check both key off.

For each journey in the ordered list, in sequence, Maestro derives the reporter-flagged `cmd` from the journey's `harness` field (`node --test <script_path>` for `node-test`; `npx playwright test <script_path> --reporter=json` for `playwright` — **`npx playwright` only, never the Playwright MCP tool**; `pytest <script_path> --junitxml=<path>` for `pytest`; the toolchain profile's own CLI/API runner invocation for `cli`), then calls `record-journey-run <treeRoot> <runId> <journey_id> '<cmd>' <ledgerPath>` — one call per journey, runs it via `runGate` (execution evidence law), derives `status` from the real exit code, times it, and appends the `journey-result` record to `runs/<runId>.jsonl` itself. Once every journey in the ordered list has run under this `runId`, Maestro reads `verification/quarantine.json` (or `{schema_version:1, entries:[]}` if absent) and calls `compute-suite-state <treeRoot> <runId> '<quarantineJson>' '<suiteJson>'` — the suite's own verdict, written to `suite-state.json`: `status: "green"` **iff every journey in the suite is either decided-quarantined or backed by exactly one verified, current-run passing record**, `"red"` otherwise (with a per-journey reason). **The suite decides; model judgment never gates** — the law's own words, and nothing about this step involves an agent's opinion of whether the product "looks done."

For every journey in `suite-state.json`'s own `passing[]` list — one that never entered the flake protocol at all because it never failed this run — its outcome is final right here: Maestro runs the telemetry `enabled`/`record` pair (`agents/maestro.md`'s Bash law point 10, which carries both invocation forms and the caller authority for them) and, when enabled, records `{kind: "journey_result", payload: {outcome: "pass", retry_count: 0}, correlation_id: null}` for it. This and the two flake-protocol branches in (d), below, are the only three points at which a journey's outcome becomes final for a run.

`status === "red"` routes to (c). `status === "green"` proceeds to (e)/(f).

### (c) Failures — fix loop, capped, reusing the chunk protocol

Every `journey_id` in `suite-state.json`'s own `failing[]` is a **fix task**, dispatched through the *identical* cross-family chunk protocol `product/implementation/flow.md` §(d) already defines — never a parallel, verification-specific review mechanism (doctrine rule 6's anti-redundant-enforcement law): the routed implementer (`implementer-sol` default, `implementer-opus` for UI/creative per the same routing seats) fixes the underlying code or the journey script itself, `milestones.js recordChunk`'s own `chunk-spec → chunk-start → chunk-review → chunk-green` lifecycle runs unchanged, and the cross-family reviewer (`chunk-reviewer-sonnet`/`chunk-reviewer-sol`, mirroring which family implemented) reviews the diff exactly as any other chunk. Only after `chunk-green` does the affected journey re-run — a fresh `record-journey-run` call under a **new** `runId` (via a fresh `start-run` call first) — before the next full `compute-suite-state` pass.

**Fix-loop cap**: before dispatching a fix attempt, Maestro calls `quarantine.js`'s `cap-check-and-record <treeRoot> <problemKey>` (`problemKey` — the failing `journey_id`, or a shared bug-signature string when several journeys trace to one root cause, the caller's own choice) — the atomic combined op: `{allowed: false, agreement_pass_required: true}` means the loop is exhausted (2 recorded attempts, `FIX_LOOP_CAP`) and convenes `agreement-pass` (`agents/agreement-pass.md`) with the blocker, every fix attempt already tried, and the project constraints bounding a remedy — the same brief shape `product/architecture/flow.md`'s own agreement pass triggers already document; `{allowed: true}` both checks AND records the attempt in the same call, so a third dispatch can never slip in between a separate check-then-record pair the way the prior build's `cap-at-cap`+`cap-record-attempt` sequence allowed.

### (d) Flake protocol — `decideFlake` + `recordOutcome`, one re-run only, machine-enforced

A journey that fails in a run gets **exactly one** re-run before anything routes to (c) as a confirmed bug: a second `start-run`+`record-journey-run` sequence, under a **new** `runId` (never the same one — both `runJourney`'s own deterministic `gate_id` shape and `recordOutcome`'s own distinct-run-id requirement depend on this), immediately after the original failure. Maestro calls `quarantine.js`'s `record-outcome <quarantinePath> <journeyId> fail --run-id <the original runId>` for the original failure, then `record-outcome <quarantinePath> <journeyId> <re-run-outcome> --run-id <the re-run's runId>` for the re-run — `recordOutcome` refuses a re-run call carrying the SAME `runId` as the original failure, and refuses a third call outright once a verdict is DECIDED (2 outcomes persisted):

- **consistent fail-fail, across two distinct runs → `"fix-task"`**: a real bug, not flake noise — no `quarantine.json` entry persists (or an existing one is removed); it stays in `suite-state.json`'s own `failing[]` and routes to (c) exactly like any other confirmed failure. This journey's outcome is final for this run right here: Maestro runs the same telemetry pair (Bash law point 10) and, when enabled, records `{kind: "journey_result", payload: {outcome: "fail", retry_count: 1}, correlation_id: null}`.
- **fail-then-pass (or pass-then-fail) → `"quarantine"`, DECIDED**: the flakiness the re-run-once protocol exists to catch — an entry persists in `quarantine.json` (`since_run`/`reason` stamped from the call's own `opts` when supplied), and `compute-suite-state`'s own `quarantine` argument (read from this same file) strips that journey's vote from every subsequent pass, **provided the entry is DECIDED** (2 outcomes) — a PENDING entry (1 outcome, the original failure alone, awaiting its one re-run) still votes normally, exactly like any other journey, so a journey mid-incident can never accidentally turn a genuinely-failing pass green before its re-run has actually happened. It is never silently forgotten — the law: "repaired or honestly listed in the last-mile report" — `delivery`'s own last-mile report is where an unresolved quarantine entry surfaces if it is still open at that phase. This journey's outcome is also final for this run right here: Maestro runs the same telemetry pair (Bash law point 10) and, when enabled, records `{kind: "journey_result", payload: {outcome: "quarantined", retry_count: 1}, correlation_id: null}`.
- **A DECIDED quarantined journey clears exactly one way**: `quarantine.js`'s `release <quarantinePath> <journeyId>`, right after its own fix's `chunk-green` lands. **This is the ONLY sanctioned reopen path** — `recordOutcome` refuses a third outcome for a decided entry outright, so there is no "clears organically after two more consecutive passes" anymore; a prior build's flow document described that path, and it is superseded by this revision's machine-enforced re-run-once discipline.

### (e) Post-green parallel lane — discovery + security, neither gates

Once `compute-suite-state` reports `status: "green"`, Maestro spawns `discovery-agent` (time-boxed exploration — dead paths, unwired UI, edge inputs the JIT suite's happy-path assertions never exercised) and `security-scanner` (one scripted dependency-audit scan per applicable toolchain ecosystem, via `runGate`, never a second execution mechanism) **in parallel** — both are in `maestro.md`'s `tools:` Agent allowlist and roster table as of this revision. Both re-verify the precondition themselves before doing any work (`discovery-agent.md`'s own "Precondition — verify green before you roam" section) rather than trusting the spawn brief's say-so. **Neither gates**: discovery-agent's findings queue as a proposed journey (a genuine criterion gap — never self-authored into the digest-frozen register) or a fix-task record; security-scanner's findings queue as a severity-tagged scan report. Both feed `delivery`'s own last-mile report via their envelopes; neither has write access to `suite-state.json`, `architecture/criteria-register.json`, `verification/quarantine.json`, or `.kiln/last-mile.jsonl` — every one of those stays its own sanctioned writer's alone.

### (f) Exit — registry conformance

`machine/phases-registry.json`'s `verification` entry, as actually built (this revision retires `flakes.jsonl` from both `exit_emits` here and `delivery`'s own `entry_requires`):

```json
{
  "id": "verification",
  "exit_emits": [
    "verification/suite-state.json",
    "verification/affected-map.json"
  ],
  "exit_checks": [
    { "file": "verification/suite-state.json", "check": "suite-state-green" },
    { "file": "verification/affected-map.json", "check": "file-nonempty" }
  ]
}
```

`suite-state-green` requires a non-empty `run_id` string, `status === "green"` (a `"stale"` status — quarantine.js's own post-mutation marker — and any other non-`"green"` value both fail here identically), AND — this revision's own addition — that `run_id` to equal the LATEST entry in the sibling `verification/runs-index.json`: a genuinely-green-when-computed run that has since been superseded by a newer `start-run` call is rejected as stale, not silently accepted on its own historical say-so. **"Runs recorded" is not a separately re-checked fact beyond that** — `phases.js`'s `EXIT_CHECK_KINDS` vocabulary has no per-dynamic-filename check (`runs/<run-id>.jsonl` is named per-run, never a fixed path an `exit_checks` entry could name), and adding one would duplicate `computeSuiteState`'s own logic inside `phases.js` — exactly the redundant-enforcement pattern doctrine rule 6 forbids.

`verification/quarantine.json`, `verification/journeys.json`, and `verification/runs-index.json` are internal working artifacts, never registry-declared exit facts (the law's phase-boundary "load-bearing subset" framing, the same distinction `architecture/flow.md` draws between its seven emitted artifacts and `judge-verdict.md`, which is never one of the five digested content artifacts either).

Once both `exit_checks` pass, a worker's own `phases.advance()` call (per "Phase sequencing" — the worker whose brief closes a phase's `exit_emits` runs `advance()` as its closing step, never Maestro's own Bash directly) carries the project into `delivery` — the handover.

## Failure paths

**Harness crash.** A journey's own toolchain command crashing the harness process outright (a missing Playwright browser binary, a segfaulting test runner) is already turned into an honest `"fail"` by `runGate`'s own signal-killed floor (`check-honesty.js`: "signal-killed → treated as failure") — never a silent hang, never a false pass. It gets the SAME one re-run the flake protocol gives any other failure; if the crash is a genuine infra defect rather than a flaky script, `runGate`'s own captured stdout/stderr rides along in the fix-task or agreement pass brief so a real environment failure is never mistaken for test flakiness.

**Suite too slow.** Each `record-journey-run` call's own `duration_ms`, summed across a full pass, is recorded timing — never a reason to truncate the ordered list or skip a journey. This is the exact per-run cost data the adopted verification mechanics name as something "only dogfooding can settle" — it feeds the dogfood-calibration threshold for when a lighter-weight affected-only pass becomes worth the accuracy trade-off, never a verification-phase shortcut taken unilaterally here (the law: "verification floor never scales down").

**Suite drift mid-run.** If the assembled suite itself changes between `start-run` and `compute-suite-state` (a genuinely unusual sequence — normally the whole failing-first dance for one `runId` runs against one fixed suite, per step (a)/(b) above) — `compute-suite-state` reports `"suite-digest-mismatch"` for every journey rather than silently computing against whichever suite happens to be passed. The sanctioned recovery is a fresh `start-run` against the CURRENT suite, not a forced recompute against the stale one.

## Known, disclosed scope limits (this revision)

- `check-honesty.js`'s `runGate` still executes `cmd` via `spawnSync(cmd, {shell: true, ...})` — a single interpolated command string, not an argument array. This revision closes the specific exploit path an independent review demonstrated (a `script_path` carrying shell metacharacters, e.g. `"...; exit 0"`) entirely at `assembleSuite`'s own charset-allowlist validation, BEFORE any harness command is ever derived from it — a malicious or malformed `script_path` can no longer enter the assembled suite at all. Moving `runGate` itself to argument-array execution was considered and deliberately deferred: `runGate` is the ONE sanctioned execution mechanism for this entire product (onboarding preflight, the toolchain install step, the milestone regression floor, `security-scanner`'s own scan step, and this phase's `runJourney` all call it with the identical `{gateId, cmd, ledgerPath}` shape, documented that way in multiple product files), so changing its calling convention is a cross-cutting change this fix pass's own scope — bounded to `machine/src/{verification,quarantine,phases}.js` and this document — deliberately does not reach into.
- `verification/security-scan-<YYYY-MM-DD>.md`'s date-only filename (two verification passes on the same UTC date target the same file) is unchanged this revision — a disclosed MINOR the independent review named, left for a future pass; it does not affect suite gating.
