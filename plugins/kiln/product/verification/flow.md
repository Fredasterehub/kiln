# Verification flow — how the hundred eyes runs

Binds `product/charter.md`'s phase-sequencing contract (its own §"Phase sequencing", §"Do/route boundary", §"Bash, narrowly" point 5, §"Communication protocol", §"Verification doctrine", §"Blocker ladder → agreement pass") to the product law's verification architecture (read verbatim: two test families, criteria register, the suite decides "done", model judgment never gates, flake quarantine re-run-once, the failing-first dance, the post-green discovery agent, the light security lane, verification-floor-never-scales-down) and its fix-loop cap (2 passes per same/similar problem → agreement pass), to the standing tree law (the `verification/` shape, below), to the verification mechanics this phase's own machinery implements, and to `machine/src/{verification,quarantine,check-honesty,phases}.js`'s APIs. Same class of artifact as `product/architecture/flow.md` and `product/implementation/flow.md` — Kiln's own operating knowledge for one phase, read by Kiln and by whichever verification-phase agents need to know their place in the sequence, never scraped for state: a script reads records, never prose.

The hundred eyes (phase 7, `machine/phases-registry.json`'s `verification` entry) is `interactive: false` — no operator judgment is required to run it; every escalation this flow names routes through the blocker ladder (`product/charter.md`'s own section, which this flow uses as-is and never extends) and, beyond that, the pipeline-wide agreement pass default, never a hosted operator conversation mid-pass.

The suite's verdict is bound to a complete, current, evidenced run — every part of that binding is structural, below. A nonexistent run, a partial run, and a stale (superseded) run each fail this phase's own checks rather than computing green.

## The tree

Quarantine state is `verification/quarantine.json` (`machine/src/quarantine.js`) — an atomically-rewritten JSON *document* (`{schema_version, entries:[{journey_id, since_run, reason, history}]}`), never an append-only stream — because the flake protocol's own question ("is this journey CURRENTLY tracked, and what's its live decision?") is a snapshot question, not a history-of-events one. There is no `flakes.jsonl` anywhere in this phase: `machine/src/scaffold.js` does not seed one, and neither `machine/phases-registry.json`'s `verification` `exit_emits` nor `delivery`'s `entry_requires` names one. The tree this phase owns:

```
verification/
  journeys.json         JSON   implementation's own JIT-authoring step   the assembled catalog
                                (see "journeys.json provenance," below)   {schema_version, journeys:
                                                                          [{journey_id, criterion_id,
                                                                          script_path, harness,
                                                                          added_in_milestone}]}
  affected-map.json     JSON   machine/src/verification.js's            TIA-lite queue: {schema_version,
                                recordAffected (sole writer)             generated_at, entries:
                                                                          [{journey_id, affected_by[],
                                                                          status}]}
  quarantine.json       JSON   machine/src/quarantine.js (sole writer)   {schema_version, entries:
                                                                          [{journey_id, since_run,
                                                                          reason, history}]}; history is
                                                                          [{outcome, run_id}, ...]
  fix-attempts.jsonl    JSONL  quarantine.js's capTracker (sole writer)  the fix-loop cap,
                                                                          one "fix-attempt" record per
                                                                          recordAttempt(problemKey) call
  runs/<run-id>.jsonl   JSONL  machine/src/verification.js (sole writer) one file per run; a leading
                                                                          "run-start" record (startRun),
                                                                          then per-journey
                                                                          "journey-result" records
  runs-index.json       JSON   machine/src/verification.js's            {schema_version, runs:
                                startRun (sole writer)                   [{run_id, seq, suite_digest,
                                                                          started_at}]}, append-only,
                                                                          ordered — the run-currency
                                                                          ledger the "suite-state-green"
                                                                          exit check cross-references
  suite-state.json      JSON   machine/src/verification.js's            {schema_version, run_id,
                                computeSuiteState (sole writer)          run_seq, suite_digest, status:
                                                                          "green"|"red"|"stale", passing[],
                                                                          failing[], reasons{}, quarantined[],
                                                                          ts}
```

## Roster

This phase charters no agent of its own. It reuses:

- `implementer-sol` / `implementer-opus` (`agents/implementer-*.md`, routing's `implementer`/`implementer_ui_creative` seats) — fix-task work, step (c) below.
- `chunk-reviewer-sonnet` / `chunk-reviewer-sol` (routing's `chunk_review_of_gpt_work`/`chunk_review_of_claude_work` seats) — cross-family review of every fix, step (c).
- `agreement-pass` (already in Kiln's roster since brainstorm) — the fix-loop-cap escalation seat, step (c).
- `discovery-agent` (`agents/discovery-agent.md`, sonnet-5 high) and `security-scanner` (`agents/security-scanner.md`, sonnet-5 medium) — the post-green parallel lane, step (e). Both are named in `product/charter.md`'s worker roster, so Kiln spawns them under its own law.

**No dedicated suite-runner seat, stated plainly**: nothing charters a "run the already-authored suite" worker seat. `machine/src/verification.js`'s core functions (`assembleSuite`, `orderRun`, `startRun`, `recordRun`, `computeSuiteState`, `recordAffected`) are pure/self-contained over their own arguments — none of them reads `architecture/criteria-register.json`, `verification/journeys.json`, or `verification/affected-map.json` from disk on its own; every one of those is a caller-supplied argument (or, for `recordAffected`, a caller-supplied `entries` list the function itself validates and writes). `runJourney` closes the *execution* half of the gap by wiring `check-honesty.js`'s `runGate` (the one sanctioned command-execution-plus-ledger-evidence mechanism, never a second one) directly into a single per-journey execute-and-record call. This is enough for **Kiln's own narrowly-scoped Bash** (`product/charter.md` point 5) to drive the whole failing-first loop directly, the identical way it already drives `milestones.js`'s create/record-chunk/close. `recordAffected` is `verification/affected-map.json`'s sole, validating, sanctioned writer — never an unnamed worker's own generic `atomicJson.writeAtomic` call — and the milestone-designer/implementer flow's chunk-green step is where each chunk's own affected journeys are fed into it, by the machine and not by a seat (`product/implementation/flow.md`'s chunk lifecycle; the `chunk-affected` transition — the chunk's own green moment, its own rung and its own envelope, distinct from the post-seal repair that catalogues what the chunk ADDED — calls `recordChunkAffected`, which derives the journeys that chunk's own sealed diff touched and merges them in through `recordAffected`, below).

## Machine layer

- `machine/src/verification.js`:
  - `assembleSuite(treeRoot, criteriaRegister, journeysIndex)` — pure; `{ok, errors, journeys}`. Fails closed on a malformed criteria register itself (`validators.validateCriteriaRegister` — a duplicate criterion id, a missing required field), the criterion↔journey 1:1 mapping (missing/duplicate/orphan), and an unsafe `script_path`: only a relative, contained path (no absolute paths, no `..`/`.` segments) drawn from an allowlisted charset (letters, digits, `.`, `_`, `-`, `/`; no shell metacharacters of any kind) is accepted. A `script_path` is later interpolated into a shell command by this document's own harness-to-cmd derivation (below), so this validation runs BEFORE that derivation ever happens, closing the class of attack structurally rather than only at execution time.
  - `orderRun(previousResults, affectedMap, allJourneys)` — pure; returns `allJourneys` reordered: previously-failed first, then affected, then the rest. Only an affected-map entry whose `status` is exactly `"pending"` (never `"green"` or `"quarantined"`) is treated as affected — a journey the map itself already marks resolved no longer re-prioritizes. A non-null `affectedMap` is validated via `validators.validateAffectedMap` and rejected (thrown) if malformed, rather than silently degrading to "no affected entries"; a `null`/`undefined` `affectedMap` (the very first pass, before the file exists) is still tolerated as empty.
  - `startRun(treeRoot, runId, suite)` — the sole writer of a run's own leading `"run-start"` record and of `verification/runs-index.json`'s append-only ordering. Binds `runId` to `digestSuite(suite)` — a deterministic, order-independent digest of the assembled suite's own journey identities — and enforces monotonic run identity: a `runId` already present in `runs-index.json`, or one whose own `runs/<run-id>.jsonl` already carries records, refuses to start again. This is the machine-owned "current run" identity the "suite-state-green" exit check (below) cross-verifies against.
  - `recordRun(treeRoot, runId, results, ledgerPath, opts)` — the sole writer of `runs/<run-id>.jsonl`'s per-journey records. Every result MUST carry a non-empty `gate_id` AND a matching ledger record (`kind: "gate"`, this exact `gate_id`, a present `exit_code`) proving that gate actually ran; a caller-attested "pass" with no execution behind it is refused outright, not merely logged as such. `opts.unverifiedImport` (default `false`) is a documented escape hatch for scenario/mock use ONLY: it skips the ledger check and stamps the record `unverified: true`, which `computeSuiteState` (below) then treats as a failure unless its OWN caller opts into the symmetric `opts.allowUnverified`. Production callers — `runJourney`, and therefore Kiln's own `record-journey-run` loop — never set either flag; both exist for deterministic replay fixtures and nothing else.
  - `computeSuiteState(treeRoot, runId, quarantine, suite, opts)` — the sole writer of `suite-state.json`. **`suite` — the assembled journey universe from step (a) — is a REQUIRED argument**: green is not whatever the run's own records happen to contain, it is EVERY journey in `suite` either decided-quarantined or backed by exactly one verified, current-run passing record. A missing record (`"no-result"`), an ambiguous duplicate (`"duplicate-result"`), an unverified one (`"unverified-result"`, unless `opts.allowUnverified`), a malformed run stream — parse errors or header violations anywhere in it (`"malformed-run-stream"`, applied to every non-quarantined journey at once, fail-closed) — or a run whose own `"run-start"` record names a different suite digest than the `suite` this call was given (`"suite-digest-mismatch"`) are all red, with the reason recorded per-journey in the returned/persisted `reasons` map. Computing for a `runId` never registered via `startRun` throws (a caller defect, not a legitimate verdict — "was this run ever actually started" is a yes/no protocol question, not a shade of red). `run_seq` and `suite_digest` are recorded into `suite-state.json` alongside `status`/`passing`/`failing`/`reasons`/`quarantined` — the same facts the "suite-state-green" exit check (below) needs to verify currency without duplicating this module's own run-lookup logic there.
  - `recordAffected(treeRoot, entries)` — the sole sanctioned writer of `verification/affected-map.json`; validates the assembled document via `validators.validateAffectedMap` before it ever reaches disk, and stamps `generated_at` itself (never caller-supplied).
  - `recordChunkAffected(treeRoot, repoRoot, milestoneId, chunkId, commit, nomination)` — the implementation ladder's per-chunk feeder for that map, called from the `chunk-affected` rung, and the one function in this module that reads a file of its own: it derives the affected set (`verification/journeys.json`'s catalogued `script_path`s, PLUS the chunk plan's own journey `nomination` — the chunk's own journey is not catalogued yet, because that write is the post-seal rung that comes next — each intersected with the paths the chunk's sealed `commit` actually changed), merges it into whatever the map already holds (append-`affected_by`, one scoped `<milestone>/<chunk>` ref per affecter), and writes it THROUGH `recordAffected`, which stays the file's only writer. A read-modify-write of the map belongs to the map's owner and to nobody else. The nomination is held to the same rule a catalogued entry is: a nominated script this commit did not change is not this chunk's doing. A resolved entry (`"green"`/`"quarantined"`) returns to `"pending"` only for an affecter it does not already carry — a genuinely new chunk moved the ground under a resolved verdict, whereas a replay of a recorded affecter decides nothing and must change no byte. Idempotent on content: when the map already carries this chunk against every journey it affected, nothing is written at all, which is what keeps a replayed `chunk-green` byte-stable against `recordAffected`'s own `generated_at` stamp. Fail-closed per entry as well as per file: an ABSENT catalog is a legitimate state (the build's first journey is affected by the chunk that authors it, whose nomination is the only record of it yet), while a catalog whose envelope OR whose individual entry this module cannot read is refused outright, never silently skipped as "unaffected". Honest boundary, stated where the claim is made: the derivation reaches journey SCRIPTS the diff touched, not "an existing journey whose underlying code the chunk modified" — no record on this tree maps a source file to the journeys that exercise it, and inventing one would be a claim rather than a derivation.
  - `runJourney(treeRoot, runId, journeyId, cmd, ledgerPath)` — runs one journey's reporter-flagged command through `runGate`, derives `status` from the real exit code, and calls `recordRun` with the one-element result, passing the SAME `ledgerPath` through so `recordRun`'s own evidence-binding check always finds the record `runGate` just wrote. `gate_id` is deterministic as `journey-<journeyId>-<runId>`, so the flake protocol's re-run-under-a-new-runId never collides with the original attempt's ledger record.
  - CLI: `verification.js {assemble-suite <treeRoot> <criteriaRegisterJson> <journeysIndexJson> | order-run <previousResultsJson> <affectedMapJson> <allJourneysJson> | start-run <treeRoot> <runId> <suiteJson> | record-run <treeRoot> <runId> <resultsJson> <ledgerPath> [--unverified-import] | compute-suite-state <treeRoot> <runId> <quarantineJson> <suiteJson> [--allow-unverified] | record-affected <treeRoot> <entriesJson> | record-journey-run <treeRoot> <runId> <journeyId> <cmd> <ledgerPath>}` — every JSON-shaped argument a literal JSON string, the same convention `milestones.js record-chunk <milestoneId> <jsonRecord>` already uses.
- `machine/src/quarantine.js`:
  - `decideFlake(history)` — pure; requires an array of EXACTLY 2 `{outcome, run_id}` objects — never a bare outcome string, never an open-ended trailing window — and the two `run_id`s MUST be distinct (a verdict decided over the same run counted twice is not a re-run at all, and throws). All-fail → `"fix-task"`; all-pass → `"clear"`; mixed → `"quarantine"`.
  - `recordOutcome(quarantinePath, journeyId, outcome, opts)` — `opts.runId` is REQUIRED (throws otherwise); a re-run under the SAME `runId` as the tracked entry's first outcome is refused. A journey already carrying a DECIDED entry (`history.length === 2`, a `"quarantine"` verdict already persisted) refuses a THIRD `recordOutcome` call outright — `release()` (the repaired path) is the ONLY sanctioned way to reopen tracking for it — a quarantined journey never clears organically by accumulating further passes. Any call that actually mutates `quarantine.json` marks a persisted `suite-state.json` `status: "stale"` (a non-destructive rewrite, not a delete — it fails the exact same "status !== green" branch the exit check already had) so a green snapshot computed before the mutation can never be consumed as if it still reflected current quarantine membership.
  - `release(quarantinePath, journeyId)` — explicit administrative removal (the "repaired, right after a fix's `chunk-green` lands" path), and the sanctioned way to reopen a DECIDED entry for further tracking. Also marks a persisted `suite-state.json` stale when it actually removes an entry.
  - `capTracker(treeRoot)` — `{recordAttempt(problemKey), countFor(problemKey), atCap(problemKey), checkAndRecord(problemKey)}`, backed by `verification/fix-attempts.jsonl`; `FIX_LOOP_CAP = 2`. **`checkAndRecord`** is the atomic combined operation: it checks the cap BEFORE recording, refusing (`{allowed: false, agreement_pass_required: true}`) rather than letting a caller record a third attempt in the window between a separate `atCap` check and its own `recordAttempt` call. Prefer it over the separate two-call sequence. Note, honestly: `problemKey` identity ("is this the same/similar problem as a prior attempt") remains caller judgment — a semantic boundary the machine cannot itself draw. Two failures the caller judges to share a root cause must be given the SAME `problemKey` for the cap to bind them together; nothing here can verify that judgment was made honestly, and a caller that mints a fresh key per attempt resets the count. This is a load-bearing limit of the mechanism, stated plainly rather than papered over.
  - CLI: `quarantine.js {decide-flake <historyJson> | record-outcome <quarantinePath> <journeyId> <outcome> --run-id X [--reason Y] | release <quarantinePath> <journeyId> | cap-record-attempt <treeRoot> <problemKey> | cap-at-cap <treeRoot> <problemKey> | cap-check-and-record <treeRoot> <problemKey>}` — the cap commands curry `capTracker`'s factory shape into flat commands, since a factory has no direct CLI shape of its own.
- `machine/src/check-honesty.js`'s `runGate({gateId, cmd, ledgerPath})` — the execution-evidence law this whole phase (via `runJourney`, above) and `security-scanner.md`'s own scan step both route every real command execution through, never a second one.
- `machine/src/phases.js`'s `EXIT_CHECK_KINDS['suite-state-green']` — reads `verification/suite-state.json`, requires a non-empty `run_id` string and `status === "green"` (a `"stale"` status — quarantine.js's own post-mutation marker — fails this the same way any other non-`"green"` status does), then reads the sibling `verification/runs-index.json` and requires the persisted `run_id` to equal that index's own LATEST entry. A run that computed green honestly, but has since been superseded by a newer `startRun` call, is rejected here as stale — currency is verified structurally, never assumed from a bare `status === "green"` read.

## journeys.json provenance — the one addendum to implementation's own flow

`assembleSuite`'s `journeysIndex` argument (`{schema_version:1, journeys:[{journey_id, criterion_id, script_path, harness, added_in_milestone}]}`) has to come from *somewhere* before the hundred eyes ever runs `assemble-suite` — and nothing in `machine/src/*.js` derives it automatically from milestone metadata (a milestone's own `chunks.jsonl` `chunk-journeys` record, per `product/implementation/flow.md` step (d).3, carries only `{chunk_id, journey_ids}` — no `script_path`/`harness`/`criterion_id`). This flow document is the canonical source for the missing link: **the same JIT-authoring step that logs a chunk's `chunk-journeys` bookkeeping record also appends one entry per authored `journey_id` directly to `verification/journeys.json`** (`atomicJson.writeAtomic`, read-current-array-append-write — the file may not exist yet on the very first journey authored in the build; the writer creates it fresh with `{schema_version:1, journeys:[]}` as its own starting point), in the exact shape `assembleSuite` expects and in a `script_path` that already satisfies `assembleSuite`'s own containment/charset floor (a relative, repo-contained path — the authoring step never has reason to produce anything else). One JIT-authoring action produces both records — the audit trail (`chunks.jsonl`) and the assemblable catalog entry (`journeys.json`) — never two disconnected writers of the same fact. By the time the hundred eyes is entered (`milestones-all-green` having already closed the anvil), `journeys.json` already reflects every milestone's own authored journeys; this phase only ever cross-checks it against `architecture/criteria-register.json`, per the law's "phase 7 assembles, never writes."

Each chunk's own `chunk-green` step (`product/implementation/flow.md`) is also this build's named producer for `verification/affected-map.json`'s entries, and it is the machine that produces them: the `chunk-affected` transition — the chunk's own green moment, a lifecycle point distinct from the post-seal repair that catalogues what the chunk ADDED — calls `recordChunkAffected` (above), which intersects the catalog's `script_path`s and the chunk plan's own journey nomination with the paths the chunk's sealed commit changed, and merges one `{journey_id, affected_by: ["<milestone_id>/<chunk_id>"], status: "pending"}` entry per affected journey into the map, through `recordAffected`. It runs BEFORE the catalog write and not after, which is exactly why the nomination is read: a journey the chunk itself authored has no catalog entry yet at its own green moment, and waiting for one would fold the two lifecycle points back into one. The affecter ref carries its milestone because a chunk id is milestone-local: two milestones both holding a `C1` are two affecters, and an unscoped ref would silently make them one. Nobody is asked what a chunk affected — the catalog, the plan and the commit already say, and a seat's own account of what it touched would be an authority this build refuses everywhere else. What that derivation does NOT reach is named at `recordChunkAffected` itself: a journey whose underlying code (rather than its own script) the chunk modified stays out of the map until some record maps source files to the journeys that exercise them.

## The engine

Every `verification.js` and `quarantine.js` call named below is Kiln's own, and the runtime invocation form for all of them — the full `node "<plugin root>/machine/src/<module>.js" ...` shape — lives in `product/charter.md`'s Bash law point 5, not here. This file is plugin payload: the plugin-root placeholder does not substitute in it, so a command stored here would reach Bash with that prefix expanded to nothing. What this document owns is the protocol — which call runs when, against what, and what its result means — with subcommands and arguments named exactly as the CLI takes them.

### (a) Entry — `assembleSuite`, fail-closed

Kiln reads `architecture/criteria-register.json` and `verification/journeys.json` directly (small, bounded JSON — within its Do/route boundary, the same class of read a routing config already gets), then calls `verification.js`'s `assemble-suite <treeRoot> '<criteriaRegisterJson>' '<journeysIndexJson>'`. `assembleSuite` fails closed (`ok: false`) on:

- a malformed criteria register itself — `validators.validateCriteriaRegister` runs first: duplicate criterion ids, missing required fields, an empty register.
- **missing** — a register criterion with zero matching journey entries (an ACR the architecture phase promised but implementation never actually authored a journey for).
- **duplicate** — a criterion with two-or-more journey entries, or two journeys sharing one `journey_id`.
- **orphan** — a journey entry naming a `criterion_id` the register doesn't have (a journey authored against a criterion architecture never defined, or one whose id drifted).
- a malformed journey entry (empty `script_path`, an unsafe/uncontained `script_path`, an unrecognized `harness`).

Every one of these means the architecture-time promise (`criteria-register.json`, digest-frozen at the plan gate) and the real, shipped implementation have structurally drifted apart — **this climbs the blocker ladder exactly like any other implementation-phase failure** (`product/charter.md`'s "Blocker ladder → agreement pass": one retry with a provably distinct approach — e.g. re-deriving `journeys.json` if a genuinely missing entry was simply never appended — is normal; a second distinct failure escalates to `agreement-pass`, never a silent skip or an invented placeholder journey). A clean `{ok: true, journeys}` result is this pass's fixed universe — the SAME array is now threaded through every remaining step below (`orderRun`'s `allJourneys`, `startRun`/`computeSuiteState`'s `suite`) as the one authoritative suite this pass is bound to.

### (b) The failing-first dance — `startRun` + `orderRun` + `runJourney` + `computeSuiteState`

Kiln reads `verification/suite-state.json` (absent on this phase's very first pass — treated as no prior failures) for its own `failing` array, and `verification/affected-map.json` (absent on the very first pass too — treated as `{entries: []}`) for its `"pending"`-status entries, then calls `order-run '<previousResultsJson>' '<affectedMapJson>' '<allJourneysJson>'` — `previousResultsJson` is a minimal array Kiln constructs itself, one `{journey_id, status: "fail", duration_ms: 0, gate_id: "prior"}` entry per id in the prior `failing` list. `orderRun` returns the assembled `journeys` from step (a), reordered: previously-failing first, then `"pending"`-status affected, then the rest — stably, deterministically. **This IS, by construction, "one full green pass"**: `orderRun` always returns the *complete* journey set, never a subset.

Before running anything, Kiln calls `start-run <treeRoot> <runId> '<suiteJson>'` — `runId` a fresh, never-before-used identifier (e.g. a timestamp or monotonic counter Kiln's own brief tracks) and `suiteJson` the exact `journeys` array from step (a). This binds the run to the suite's own digest and registers it in `verification/runs-index.json` BEFORE any journey executes — the machine-owned "current run" fact `compute-suite-state`'s own currency check (below) and the phase-exit `suite-state-green` check both key off.

For each journey in the ordered list, in sequence, Kiln derives the reporter-flagged `cmd` from the journey's `harness` field (`node --test <script_path>` for `node-test`; `npx playwright test <script_path> --reporter=json` for `playwright` — **`npx playwright` only, never the Playwright MCP tool**; `pytest <script_path> --junitxml=<path>` for `pytest`; the toolchain profile's own CLI/API runner invocation for `cli`), then calls `record-journey-run <treeRoot> <runId> <journey_id> '<cmd>' <ledgerPath>` — one call per journey, runs it via `runGate` (execution evidence law), derives `status` from the real exit code, times it, and appends the `journey-result` record to `runs/<runId>.jsonl` itself. Once every journey in the ordered list has run under this `runId`, Kiln reads `verification/quarantine.json` (or `{schema_version:1, entries:[]}` if absent) and calls `compute-suite-state <treeRoot> <runId> '<quarantineJson>' '<suiteJson>'` — the suite's own verdict, written to `suite-state.json`: `status: "green"` **iff every journey in the suite is either decided-quarantined or backed by exactly one verified, current-run passing record**, `"red"` otherwise (with a per-journey reason). **The suite decides; model judgment never gates** — the law's own words, and nothing about this step involves an agent's opinion of whether the product "looks done."

For every journey in `suite-state.json`'s own `passing[]` list — one that never entered the flake protocol at all because it never failed this run — its outcome is final right here: Kiln runs the telemetry `enabled`/`record` pair (`product/charter.md`'s Bash law point 10, which carries both invocation forms and the caller authority for them) and, when enabled, records `{kind: "journey_result", payload: {outcome: "pass", retry_count: 0}, correlation_id: null}` for it. This and the two flake-protocol branches in (d), below, are the only three points at which a journey's outcome becomes final for a run.

`status === "red"` routes to (c). `status === "green"` proceeds to (e)/(f).

### (c) Failures — fix loop, capped, reusing the chunk protocol

Every `journey_id` in `suite-state.json`'s own `failing[]` is a **fix task**, dispatched through the *identical* cross-family chunk protocol `product/implementation/flow.md` §(d) already defines — never a parallel, verification-specific review mechanism (doctrine rule 6's anti-redundant-enforcement law): the routed implementer (`implementer-sol` default, `implementer-opus` for UI/creative per the same routing seats) fixes the underlying code or the journey script itself, `milestones.js recordChunk`'s own `chunk-spec → chunk-start → chunk-review → chunk-green` lifecycle runs unchanged, and the cross-family reviewer (`chunk-reviewer-sonnet`/`chunk-reviewer-sol`, mirroring which family implemented) reviews the diff exactly as any other chunk. Only after `chunk-green` does the affected journey re-run — a fresh `record-journey-run` call under a **new** `runId` (via a fresh `start-run` call first) — before the next full `compute-suite-state` pass.

**Fix-loop cap**: before dispatching a fix attempt, Kiln calls `quarantine.js`'s `cap-check-and-record <treeRoot> <problemKey>` (`problemKey` — the failing `journey_id`, or a shared bug-signature string when several journeys trace to one root cause, the caller's own choice) — the atomic combined op: `{allowed: false, agreement_pass_required: true}` means the loop is exhausted (2 recorded attempts, `FIX_LOOP_CAP`) and convenes `agreement-pass` (`agents/agreement-pass.md`) with the blocker, every fix attempt already tried, and the project constraints bounding a remedy — the same brief shape `product/architecture/flow.md`'s own agreement pass triggers already document; `{allowed: true}` both checks AND records the attempt in the same call, so a third dispatch can never slip in between a separate check-then-record pair the way a `cap-at-cap` followed by `cap-record-attempt` would allow.

### (d) Flake protocol — `decideFlake` + `recordOutcome`, one re-run only, machine-enforced

A journey that fails in a run gets **exactly one** re-run before anything routes to (c) as a confirmed bug: a second `start-run`+`record-journey-run` sequence, under a **new** `runId` (never the same one — both `runJourney`'s own deterministic `gate_id` shape and `recordOutcome`'s own distinct-run-id requirement depend on this), immediately after the original failure. Kiln calls `quarantine.js`'s `record-outcome <quarantinePath> <journeyId> fail --run-id <the original runId>` for the original failure, then `record-outcome <quarantinePath> <journeyId> <re-run-outcome> --run-id <the re-run's runId>` for the re-run — `recordOutcome` refuses a re-run call carrying the SAME `runId` as the original failure, and refuses a third call outright once a verdict is DECIDED (2 outcomes persisted):

- **consistent fail-fail, across two distinct runs → `"fix-task"`**: a real bug, not flake noise — no `quarantine.json` entry persists (or an existing one is removed); it stays in `suite-state.json`'s own `failing[]` and routes to (c) exactly like any other confirmed failure. This journey's outcome is final for this run right here: Kiln runs the same telemetry pair (Bash law point 10) and, when enabled, records `{kind: "journey_result", payload: {outcome: "fail", retry_count: 1}, correlation_id: null}`.
- **fail-then-pass (or pass-then-fail) → `"quarantine"`, DECIDED**: the flakiness the re-run-once protocol exists to catch — an entry persists in `quarantine.json` (`since_run`/`reason` stamped from the call's own `opts` when supplied), and `compute-suite-state`'s own `quarantine` argument (read from this same file) strips that journey's vote from every subsequent pass, **provided the entry is DECIDED** (2 outcomes) — a PENDING entry (1 outcome, the original failure alone, awaiting its one re-run) still votes normally, exactly like any other journey, so a journey mid-incident can never accidentally turn a genuinely-failing pass green before its re-run has actually happened. It is never silently forgotten — the law: "repaired or honestly listed in the last-mile report" — `delivery`'s own last-mile report is where an unresolved quarantine entry surfaces if it is still open at that phase. This journey's outcome is also final for this run right here: Kiln runs the same telemetry pair (Bash law point 10) and, when enabled, records `{kind: "journey_result", payload: {outcome: "quarantined", retry_count: 1}, correlation_id: null}`.
- **A DECIDED quarantined journey clears exactly one way**: `quarantine.js`'s `release <quarantinePath> <journeyId>`, right after its own fix's `chunk-green` lands. **This is the ONLY sanctioned reopen path** — `recordOutcome` refuses a third outcome for a decided entry outright, so a quarantined journey never clears organically by accumulating further passes. The re-run-once discipline is machine-enforced, and `release` is the only door out of it.

### (e) Post-green parallel lane — discovery + security, neither gates

Once `compute-suite-state` reports `status: "green"`, Kiln spawns `discovery-agent` (time-boxed exploration — dead paths, unwired UI, edge inputs the JIT suite's happy-path assertions never exercised) and `security-scanner` (one scripted dependency-audit scan per applicable toolchain ecosystem, via `runGate`, never a second execution mechanism) **in parallel** — both are named in `product/charter.md`'s worker roster. Both re-verify the precondition themselves before doing any work (`discovery-agent.md`'s own "Precondition — verify green before you roam" section) rather than trusting the spawn brief's say-so. **Neither gates**: discovery-agent's findings queue as a proposed journey (a genuine criterion gap — never self-authored into the digest-frozen register) or a fix-task record; security-scanner's findings queue as a severity-tagged scan report. Both feed `delivery`'s own last-mile report via their envelopes; neither has write access to `suite-state.json`, `architecture/criteria-register.json`, `verification/quarantine.json`, or `.kiln/last-mile.jsonl` — every one of those stays its own sanctioned writer's alone.

### (f) Exit — registry conformance

`machine/phases-registry.json`'s `verification` entry:

```json
{
  "id": "verification",
  "exit_emits": [
    "verification/suite-state.json",
    "verification/affected-map.json"
  ],
  "exit_checks": [
    { "file": "verification/suite-state.json", "check": "suite-state-green" },
    { "file": "verification/affected-map.json", "check": "file-nonempty" }
  ]
}
```

`suite-state-green` requires a non-empty `run_id` string, `status === "green"` (a `"stale"` status — quarantine.js's own post-mutation marker — and any other non-`"green"` value both fail here identically), AND that `run_id` to equal the LATEST entry in the sibling `verification/runs-index.json`: a genuinely-green-when-computed run that has since been superseded by a newer `start-run` call is rejected as stale, not silently accepted on its own historical say-so. **"Runs recorded" is not a separately re-checked fact beyond that** — `phases.js`'s `EXIT_CHECK_KINDS` vocabulary has no per-dynamic-filename check (`runs/<run-id>.jsonl` is named per-run, never a fixed path an `exit_checks` entry could name), and adding one would duplicate `computeSuiteState`'s own logic inside `phases.js` — exactly the redundant-enforcement pattern doctrine rule 6 forbids.

`verification/quarantine.json`, `verification/journeys.json`, and `verification/runs-index.json` are internal working artifacts, never registry-declared exit facts (the law's phase-boundary "load-bearing subset" framing, the same distinction `architecture/flow.md` draws between its seven emitted artifacts and `judge-verdict.md`, which is never one of the five digested content artifacts either).

Once both `exit_checks` pass, a worker's own `phases.advance()` call (per "Phase sequencing" — the worker whose brief closes a phase's `exit_emits` runs `advance()` as its closing step, never Kiln's own Bash directly) carries the project into `delivery` — the handover.

## Failure paths

**Harness crash.** A journey's own toolchain command crashing the harness process outright (a missing Playwright browser binary, a segfaulting test runner) is already turned into an honest `"fail"` by `runGate`'s own signal-killed floor (`check-honesty.js`: "signal-killed → treated as failure") — never a silent hang, never a false pass. It gets the SAME one re-run the flake protocol gives any other failure; if the crash is a genuine infra defect rather than a flaky script, `runGate`'s own captured stdout/stderr rides along in the fix-task or agreement pass brief so a real environment failure is never mistaken for test flakiness.

**Suite too slow.** Each `record-journey-run` call's own `duration_ms`, summed across a full pass, is recorded timing — never a reason to truncate the ordered list or skip a journey. That per-run cost is the only data that could ever settle whether a lighter-weight affected-only pass is worth the accuracy trade-off; until it does, the full pass runs, and no verification-phase shortcut is taken unilaterally here (the law: "verification floor never scales down").

**Suite drift mid-run.** If the assembled suite itself changes between `start-run` and `compute-suite-state` (a genuinely unusual sequence — normally the whole failing-first dance for one `runId` runs against one fixed suite, per step (a)/(b) above) — `compute-suite-state` reports `"suite-digest-mismatch"` for every journey rather than silently computing against whichever suite happens to be passed. The sanctioned recovery is a fresh `start-run` against the CURRENT suite, not a forced recompute against the stale one.

## Scope, stated honestly

- `check-honesty.js`'s `runGate` executes `cmd` via `spawnSync(cmd, {shell: true, ...})` — a single interpolated command string, not an argument array. The exploit that shape invites — a `script_path` carrying shell metacharacters, e.g. `"...; exit 0"` — is closed one layer earlier, at `assembleSuite`'s own charset-allowlist validation, BEFORE any harness command is ever derived from it: a malicious or malformed `script_path` cannot enter the assembled suite at all. The shell itself stays, deliberately. `runGate` is the ONE sanctioned execution mechanism for this entire product — onboarding preflight, the toolchain install step, the milestone regression floor, `security-scanner`'s own scan step, and this phase's `runJourney` all call it with the identical `{gateId, cmd, ledgerPath}` shape — so its calling convention is a single cross-cutting contract, not a per-phase choice. The containment guarantee here is the allowlist, never the shell.
- `verification/security-scan-<YYYY-MM-DD>.md`'s filename is date-only: two verification passes on the same UTC date write to the same file, and the second overwrites the first. It does not affect suite gating.
